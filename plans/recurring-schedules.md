# 반복 일정 기획

상태: grill-with-docs 인터뷰의 제품 정책 21개 확정. Figma 설계와 오프라인 기능·화면 구현을 완료했다. 세부 구현·검증 범위는 `recurring-schedules-delivery-plan.md`와 `docs/design/recurring-schedules/README.md`에 기록했다.

## 사용자 요청으로 확정된 방향

- 기능 기획 → Figma 디자인 추가 → 기능 구현 → 화면 구현 순서로 진행한다.
- 반복 일정마다 전용 준비과정을 저장하고 해당 반복 일정에서 재사용한다.
- 향후 기본 준비과정 외에도 여러 커스텀 준비과정을 추가할 수 있도록 고려한다.
- 현재 로컬 전용 제품 경계를 유지한다.

## 확정 결정

### 1. 반복 일정 전용 준비과정의 독립성

- 사용자 답변: “독립적 관리”.
- 생성 시 기본 준비과정 또는 향후 선택한 준비과정 템플릿의 내용을 복사하여 반복 일정 전용 준비과정으로 소유한다.
- 원본 기본 준비과정이나 템플릿의 이후 수정은 기존 반복 일정 전용 준비과정에 전파하지 않는다.
- 반복 일정 전용 준비과정의 수정도 원본 또는 다른 반복 일정에 전파하지 않는다.
- 해당 반복 일정의 회차들이 전용 준비과정을 재사용하며, 수정 적용 범위는 아래 ‘수정·삭제 범위’ 결정에 따른다.
- 여러 준비과정 템플릿을 선택·관리하는 화면은 사용자의 ‘나중에’ 요청에 따라 향후 확장으로 남기며, 이번에는 반복 전용 준비과정에 집중한다.

### 2. 반복 주기 지원 범위

- 사용자 최종 범위 조정: “매년만 제외”.
- 일간: 매일 및 N일마다.
- 주간: 매주 및 N주마다, 복수 요일 선택. 평일·주말도 표현한다.
- 월간: 매월 및 N개월마다, 날짜 지정 또는 순번과 요일 조합(예: 매월 두 번째 화요일, 마지막 금요일).
- 연간: 매년 및 N년마다의 반복은 이번 기능 범위에서 제외한다.
- 위 일간·주간·월간 반복과 간격 지정은 이번 기능 범위에 포함한다.
- 존재하지 않는 날짜, 종료 조건, 첫 회차는 아래 결정에 따른다. 존재하지 않는 다섯 번째 요일도 건너뛰며, 마지막 요일은 별도 규칙으로 제공한다.

### 3. 존재하지 않는 월간 반복 날짜

- 추천안에 대한 사용자 답변 “ㅇㅇ”를 건너뛰기 동의로 해석하고 사용자에게 명시했다.
- 지정한 날짜가 없는 달에는 해당 회차를 만들지 않는다. 예: 매월 31일은 4월에 발생하지 않는다.
- 말일로 자동 보정하지 않는다.
- 매달 말일을 원하는 경우를 위해 ‘매월 마지막 날’을 별도 반복 규칙으로 제공한다.
- 없는 날짜로 건너뛴 달의 횟수 계산은 결정 15에 따른다. 다섯 번째 요일처럼 존재하지 않는 순번의 처리는 세부 규칙으로 구체화한다.

### 4. 반복 종료 조건

- 사용자 답변: 세 가지 모두 제공하고 기본값을 ‘종료 없음’으로 하는 추천안에 “ㅇㅇ”.
- 종료 없음: 사용자가 직접 중단할 때까지 반복한다.
- 날짜 지정: 사용자가 선택한 날짜까지 반복한다.
- 횟수 지정: 사용자가 정한 총 회차 수만큼 반복한다.
- 기본 선택은 ‘종료 없음’이다.
- 개별 삭제 시 대체 회차를 추가하지 않는다(결정 8). 없는 날짜로 건너뛴 달은 횟수를 소모하지 않는다(결정 15). 날짜 지정의 시간대·경계는 세부 규칙으로 구체화한다.

### 5. 수정·삭제 범위

- 사용자 답변: ‘이번 일정만’ / ‘이번 및 이후 일정’ 두 범위와 이전 기록 유지 추천안에 “ㅇㅇ”.
- 이번 일정만: 선택한 회차의 일정 정보 또는 준비과정만 수정하며 다른 회차의 기존 설정을 유지한다.
- 이번 및 이후 일정: 선택한 회차부터 이후 회차에 변경을 적용한다. 준비과정도 같은 적용 범위를 따른다.
- 삭제도 동일한 두 범위를 제공한다.
- 선택한 회차보다 이전 회차의 기록은 유지한다.
- 개별 수정값 유지와 진행 중 회차 보호는 아래 결정에 따른다. 완료한 회차의 경계 조건과 반복 규칙 자체의 변경은 후속 결정에서 구체화한다.

### 6. 개별 수정값과 일괄 변경의 충돌

- 사용자 답변: 개별 수정값 유지 추천안에 “ㅇㅇ”.
- ‘이번 및 이후 일정’으로 공통 값을 수정해도, 각 회차에서 따로 수정한 항목은 보존한다.
- 개별 수정하지 않은 항목에만 새 공통 값을 적용한다.
- 예: 기본 출근 09:00, 다음 금요일만 10:00인 상태에서 공통 시간을 09:30으로 바꾸면 해당 금요일은 10:00을 유지한다.
- 한 회차의 준비과정을 따로 수정한 경우 해당 준비과정은 공통 준비과정 변경으로 덮어쓰지 않는다.
- 이 결정은 항목 값의 수정에 관한 것이다. 반복 규칙에서 빠지는 개별 수정 회차는 결정 9에 따라 보존한다. 명시적인 삭제의 효과는 별도로 정한다.

### 7. 준비가 시작된 회차 보호

- 사용자 답변: 진행 중인 회차를 보호하는 추천안에 “ㅇㅇ”.
- 준비가 시작된 회차는 반복 설정 또는 공통 준비과정 변경의 적용 대상에서 제외한다.
- 해당 회차의 준비 단계, 시간, 진행 상태는 그대로 유지한다.
- 반복 종료 시에도 진행 중인 회차는 유지하고 아직 시작하지 않은 이후 회차부터 종료를 적용한다.
- 예: 오늘 출근 준비 중 반복 준비과정을 수정해도 오늘은 기존 준비과정으로 마치고 이후 미시작 회차부터 변경한다.
- 진행 중인 회차 자체의 직접 중단·삭제 흐름과 완료·미실행 과거 회차의 경계 조건은 별도로 검토한다.

### 8. 횟수 지정 반복에서 개별 회차 삭제

- 사용자 답변: 삭제한 회차를 자동 보충하지 않는 추천안에 “ㅇㅇ”.
- 총 10회 중 한 회차를 삭제하면 남는 일정은 9회이며, 뒤에 새 회차를 추가하지 않는다.
- 개별 삭제를 이유로 기존 반복 종료를 뒤로 연장하지 않는다.
- 마지막 회차 자체를 삭제한 경우에도 대체 회차를 추가하지 않으며 실제 남은 마지막 일정은 앞당겨질 수 있다.
- 원래 존재하지 않는 날짜를 건너뛰는 경우의 총 횟수 계산과는 구분한다.

### 9. 반복 규칙에서 빠지는 개별 수정 회차

- 사용자 답변: 단독 일정으로 보존하는 추천안에 “ㅇㅇ”.
- 반복 규칙 변경으로 새 규칙에 해당하지 않게 된 개별 수정 회차는 반복 묶음에서 분리하여 단독 일정으로 남긴다.
- 분리된 일정의 시간·준비과정을 보존한다.
- 예: 월·수·금 반복에서 다음 금요일만 개별 수정한 뒤 반복을 월·수로 바꾸면, 해당 금요일은 단독 일정으로 유지한다.
- 저장 전에 분리되는 일정을 보여주고 ‘단독 일정으로 남습니다’라고 안내한다.
- 이 정책은 반복 규칙 수정에 적용한다. 사용자가 명시적으로 ‘이번 및 이후 일정 삭제’를 선택한 경우와 혼동하지 않는다.

### 10. 반복 일정 생성 흐름

- 사용자 답변: 기존 생성 흐름에 통합하는 추천안에 “ㅇㅇ”.
- 기존 이름 → 날짜·시간 → 장소·이동시간 → 여유시간·준비과정의 4단계를 유지한다.
- 날짜·시간 단계에 기본값 ‘반복 안 함’인 반복 설정 항목을 추가한다.
- 해당 항목에서 반복 주기·간격·요일·종료 조건을 설정한다.
- 설정 후 ‘매주 월·수·금 · 종료 없음’처럼 선택한 규칙을 요약해서 보여준다.
- 마지막 단계에서 이 반복 일정의 전용 준비과정을 편집한다.
- 반복 일정 생성만을 위한 별도 진입 메뉴는 만들지 않는다.

### 11. 기존 일정과 겹치는 반복 회차

- 사용자 답변: 충돌 회차를 확인하여 제외한 뒤 나머지를 저장하는 추천안에 “ㅇㅇ”.
- 반복 회차가 기존 일정의 준비·이동 시간과 겹치면 충돌 날짜와 관련 일정을 보여준다.
- 사용자가 제외할 회차를 명시적으로 선택한 뒤 나머지 회차를 저장할 수 있다.
- 겹치는 회차를 사용자 확인 없이 자동으로 누락시키지 않는다.
- 충돌 검사의 범위, 반복 묶음 간 충돌, 나중에 추가·변경한 일정과의 충돌 및 모든 후보가 충돌하는 경우는 구현 설계에서 구체화해야 한다.

### 12. 시작일과 첫 회차

- 사용자 답변: 시작일 이후 처음 규칙에 맞는 날부터 생성하는 추천안에 “ㅇㅇ”.
- 시작일은 포함 경계이며, 그날부터 반복 규칙을 만족하는 첫 날짜를 첫 회차로 잡는다.
- 시작일 자체가 규칙에 맞지 않으면 그날을 추가 회차로 만들지 않는다.
- 예: 화요일을 시작일로 선택하고 월·수·금 반복을 설정하면 첫 회차는 수요일이다.
- 설정 화면에 실제 첫 일정 날짜를 보여준다.
- 생성 시 오늘의 준비 시작 시각이 이미 지난 경우는 결정 18에 따라 다음 유효 회차부터 시작한다.

### 13. 앱 미실행 기간의 지난 회차

- 사용자 답변: 지난 회차를 ‘진행 기록 없음’으로 남기는 추천안에 “ㅇㅇ”.
- 앱을 열지 않은 동안 지나간 반복 회차도 달력에서 예정됐던 일정으로 확인할 수 있다.
- 준비 시작·진행·완료 기록이 없는 지난 회차는 ‘진행 기록 없음’으로 표시한다.
- 앱 미실행이나 시각 경과만으로 완료·지각 결과를 만들지 않고 정시 도착 점수에도 반영하지 않는다.
- 실제 진행·완료 기록이 있는 회차는 해당 기록을 보존한다.
- 사용자가 삭제하거나 제외한 회차, 존재하지 않는 날짜로 건너뛴 회차를 과거 일정으로 복구하지 않는다.

### 14. 반복 일정 관리 화면

- 사용자 답변: 마이페이지에 반복 일정 관리를 추가하는 추천안에 “ㅇㅇ”.
- 마이페이지에 ‘반복 일정 관리’ 진입점을 추가한다.
- 출근·운동 등 반복 묶음을 목록으로 보여준다.
- 반복 규칙, 다음 일정, 전용 준비과정을 확인하고 수정하거나 반복을 종료할 수 있다.
- 달력의 개별 회차 선택·수정 흐름을 유지한다.
- 관리 화면의 수정 적용 시작점, 종료된 묶음의 표시와 빈 상태 등은 화면 설계에서 구체화한다.

### 15. 없는 날짜와 총횟수 계산

- 사용자 답변: 실제 날짜가 있는 회차만 세는 추천안에 “ㅇㅇ”.
- 지정 날짜가 없어 건너뛴 달은 총 반복 횟수를 소모하지 않는다.
- 예: 1월부터 매월 31일 총 3회는 1월 31일, 3월 31일, 5월 31일이다.
- 그 뒤 사용자가 한 회차를 삭제하면 보충 없이 2회만 남는다. 규칙상 유효한 회차 수와 삭제 후 남은 일정 수를 구분한다.

### 16. 서머타임으로 존재하지 않는 현지 시각

- 사용자 답변: 해당 회차만 건너뛰고 총횟수에서도 제외하는 추천안에 “ㅇㅇ”.
- 선택한 시간대의 시계 이동으로 약속 시각이 존재하지 않는 날은 해당 반복 회차를 생성하지 않는다.
- 임의로 다른 시각으로 보정하지 않으며 총 반복 횟수를 소모하지 않는다.
- 설정 화면에 건너뛰는 날짜와 이유를 안내한다.
- 기존 일반 일정의 존재하지 않는 현지 시각 저장 거절 정책은 유지한다.
- 시계가 뒤로 이동하여 동일한 현지 시각이 두 번 발생하는 경우는 결정 17에 따른다.

### 17. 두 번 발생하는 현지 시각

- 사용자 답변: 반복 설정에서 첫 번째/두 번째 시각을 한 번 선택하여 재사용하는 추천안에 “ㅇㅇ”.
- 중복 시각이 생기는 시간대·시각의 반복 설정에서 첫 번째 또는 두 번째 시각을 명시적으로 선택한다.
- 선택은 반복 규칙에 보존하며 이후 중복 시각 회차에도 동일한 순번을 적용한다.
- 중복 시각이 발생하는 날에도 선택한 실제 시각에 일정 한 건만 생성한다.
- 일반적인 시간대·시각에는 불필요한 선택 항목을 표시하지 않는다.
- 선택은 고정 UTC 오프셋이 아니라 중복된 현지 시각 중 시간순 첫 번째/두 번째를 뜻한다.

### 18. 생성 시 준비 시작 시각이 지난 회차

- 사용자 답변: 오늘을 제외하고 다음 유효 회차부터 시작하는 추천안에 “ㅇㅇ”.
- 새 반복 일정을 저장하는 시점에 준비 시작 시각이 이미 지난 회차는 생성 시작 범위에서 제외한다.
- 다음으로 준비 시작 시각이 아직 지나지 않은 유효 회차부터 반복을 시작하고 총횟수도 그 회차부터 계산한다.
- 예: 현재 08:30, 매일 09:00 출근, 준비·이동 1시간이면 오늘은 제외하고 내일부터 시작한다.
- 저장 전에 준비 시작 시각이 지나 제외된 첫 후보와 실제 반복 시작 날짜를 안내한다.
- 이 정책은 새 반복 일정의 시작 범위에 관한 것으로, 기존 반복 일정의 지난 회차를 지우는 정책이 아니다.

### 19. 반복 묶음 간 지속 충돌

- 사용자 답변: 반복 시간·요일을 수정한 뒤 저장하는 추천안에 “ㅇㅇ”.
- 두 반복 규칙이 매주 같은 시간처럼 지속적으로 충돌하면 반복 시간·요일을 조정해야 저장할 수 있다.
- 지속 충돌을 개별 회차의 무한 제외로 해결하지 않는다.
- 특정 날짜에 한정된 충돌은 결정 11에 따라 사용자가 해당 회차를 확인·제외할 수 있다.

## 기획 시작 시 코드 확인 (구현 전 조사)

- 기본 준비 단계: `lib/data/tables/preparation_user_table.dart`.
- 일정 한 건의 준비 단계: `lib/data/tables/preparation_schedule_table.dart`.
- 이름 있는 준비과정 템플릿 및 순서 있는 단계 테이블, DAO, 저장소가 이미 존재한다.
- `Schedules`에는 준비 모드와 템플릿 메타데이터가 있으나 반복 규칙 및 반복 묶음 식별자는 없다.
- 기존 용어 `Custom Preparation`은 한 일정에만 속하는 준비과정이다. 향후 재사용 가능한 커스텀 준비과정과 구분해야 한다.
- 기획 시작 시 이 체크아웃에는 `rule/`과 `docs/design/`이 없었다. 과거 Figma 매핑은 현재 상태의 증거로 사용하지 않는다.
- 기존 일정 생성은 이름 → 날짜·시간 → 장소·이동시간 → 여유시간·준비과정의 4단계다(`ScheduleMultiPageForm`). 결정 10에 따라 날짜·시간 단계에 반복 설정을 추가한다.
- `ScheduleDateTimeState.isValid`는 `isOverlapping`일 때 다음 단계 진행을 막는다. `ScheduleDateTimeCubit`은 다음 일정의 준비 시작 시각과 비교하여 해당 상태를 계산한다. 이 기존 검사를 반복 일정의 모든 회차에 그대로 적용할 수 있다고 가정하지 않는다.
- 기존 승인 ADR `docs/adr/0019-schedule-future-notifications-by-platform-capacity.md`는 가까운 미래 일정부터 플랫폼 예약 용량 내에서 알림을 예약하고 실행·복귀·일정 변경 등의 계기에 재조정하는 정책이다. 반복 일정에도 이 경계를 유지하며, 앱 장기 미실행 시 무제한 알림을 약속하지 않는다. 실제 반복 회차 공급과 예약 상태 안내 방식은 추가 설계·검증이 필요하다.
- 기존 ADR 0034는 명시적 삭제 전까지 일정 이력을 보존하고, ADR 0025는 실제 완료 결과 중 정상·지각만 점수에 포함한다. 반복 회차의 과거 기록을 복원하더라도 완료·지각 결과를 추정해 만들어서는 안 된다.
- 기존 ADR 0021과 `CivilTimeResolver`는 선택한 이름 있는 시간대를 유지하며, 존재하지 않는 현지 시각과 두 번 발생하는 현지 시각을 구분한다. 일반 일정의 없는 시각은 저장을 거절하고, 중복 시각은 사용자가 어느 시각인지 선택한다. 반복 일정의 없는 시각은 결정 16에 따라 건너뛰며, 중복 시각은 결정 17의 명시 선택을 재사용한다.

## 진행 상태

정책 1–21 및 오프라인 전용 제약을 확정했다. 현재 사용자 답변을 기다리는 제품 질문은 없다. Figma와 도메인·저장·백업·알림 후보·화면 구현 상태 및 검증은 `recurring-schedules-delivery-plan.md`에 기록한다.

- 사용자 명시 제약: 반복 일정 기능은 오프라인 전용 앱으로 구현한다. 기기 내부 DB·로컬 알림·기존 로컬 백업을 사용하며 서버·원격 동기화·계정 의존성을 추가하지 않는다.

### 20. 이후 수정 시 남은 횟수

- 사용자 답변: 남은 횟수 유지.
- 총 10회 중 3회가 지난 뒤 규칙을 수정하면 이후 7회만 새 규칙으로 이어간다.
- 횟수 자체를 수정할 때만 적용 범위에 새 횟수를 지정한다. 삭제·제외는 기존과 같이 보충하지 않는다.

### 21. 분리되는 단독 일정과 남은 횟수

- 사용자 답변: 추천안에 동의.
- 남은 7회 중 2회가 규칙에서 빠져 단독 일정으로 분리되면 반복 5회와 단독 2회로 총 7회를 유지한다.
- 규칙 변경으로 일정을 추가 보충하지 않는다.
