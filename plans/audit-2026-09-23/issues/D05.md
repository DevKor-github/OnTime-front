## 문제와 영향

현재 파일 선택은 크기 확인 전에 전체 파일을 메모리에 읽는다. 암호문, 복호문 chunk 목록, 결합된 복호문, UTF-8 문자열, JSON 객체와 모델이 중첩해서 살아 있을 수 있다. 암호 header/frame별 상한은 있지만 파일·전체 복호문·레코드·문자열 한도가 없어 정상 암호를 가진 대형 파일 또는 잘못된 입력으로 모바일 프로세스가 종료될 수 있다. 인증만 통과한 파일이 제품의 관계·시간대·자료 표현 규칙까지 만족한다는 뜻은 아니다. 정상 데이터 복원과 손상 데이터 Recovery가 같은 검증기를 사용해야 한다.

기존 암호화 suite와 비밀번호 규칙을 교체하는 작업이 아니다. Android/iOS local-only, envelope crypto version 1, payload format 1/2, schema 2 및 반복 일정·소유 preparation·exclusion 호환을 유지한다. 완전한 검증 전에는 활성 DB/키/runtime/delivery를 바꾸지 않는다.

## 확정 결정: 총량과 스트리밍

| 항목 | 초기 수용 상한 |
|---|---:|
| 암호화 파일 실제 bytes | 72 MiB |
| 복호문 UTF-8 JSON 실제 bytes | 64 MiB |
| JSON object/array 중첩 | 32 |
| 일정 레코드 | 100,000 |
| 전체 레코드 | 500,000 |
| preparation 정의 하나의 단계 | 1,000 |

각 상한을 동시에 만족해야 한다. 100,000개 일정의 모든 조합이 64 MiB에 들어간다는 보장이 아니다. 최소 10,000개 정상 일정 fixture를 검증한다. 상한은 성능 보장/SLA가 아니며 실제 모바일 메모리·시간 측정을 별도 증거로 남긴다. 수치를 바꾸려면 근거와 제품 결정을 기록하며 테스트만 맞추기 위한 은밀한 축소는 금지한다.

사전 file length와 실제 stream 누적 bytes를 모두 검사한다. unknown/inaccurate length, 길이 검사 후 커진 provider 자료, chunk 경계에서 넘어가는 입력도 안전하게 실패해야 한다. final 인증 이전 provisional staging 적재는 사용자에게 노출하거나 활성화하지 않으며 final marker/EOF/전체 관계 검증 후에만 후보가 된다. giant frame/token을 할당한 후 제한하는 방식, 전체 JSON map 재결합, plaintext 임시 파일은 허용하지 않는다. 동일 정책을 export preflight/스트리밍 쓰기에 적용해 스스로 복원할 수 없는 새 파일을 성공으로 제공하거나 freshness를 갱신하지 않는다. 초과 자료를 자르거나 이력을 삭제하지 않고 지원 한도 오류와 원본 보존을 제공한다. 한도 오류는 암호 오류/파일 손상과 구분한다.

## 확정 결정: 하위 자료 한도와 역사 호환

- ID/참조 ID는 UTF-8 512 bytes 이하이며 UUID 형식으로 새로 제한하지 않는다. object key도 UTF-8 512 bytes 이하이고 unknown field의 key/value도 byte/depth/token 검사 대상이다.
- 개별 문자열은 UTF-8 64 KiB 이하, note는 16,384 Unicode scalar와 UTF-8 64 KiB 중 먼저 닿는 상한을 적용한다. scalar 수와 UTF-16 code unit, UTF-8 bytes를 혼동하지 않는다. 기존 DB/domain 이름 길이는 해당 필드의 현행 의미대로 검사한다. backup 문자열을 임의 NFC 정규화/trim/절단하지 않는다. 비밀번호의 기존 NFC 규칙은 별도다.
- 전체 레코드 예산은 일정, place 입력, template, preparation 정의와 각 단계, recurring segment/exclusion, profile/preferences를 포함한다. 관계 검증에서 ID를 deduplicate하기 전에 원본 입력 항목을 계수하므로 중복 ID 반복으로 예산을 우회할 수 없다. staging preview의 고유 객체 count와 입력 자원 예산 count는 서로 다른 목적이다.
- duration은 원래 domain 상한이 명시된 필드에만 그 상한을 적용한다. **legacy 모든 duration을 1440분으로 제한하거나 총 준비 시간을 1,440,000분으로 새로 제한하지 않는다.** Q2의 초기 제안은 root가 정정했다. 0분이 합법인 legacy/recurring 자료를 신규 form의 최소 1분으로 거절하지 않는다. 음수, 분→microseconds 단위 곱셈 overflow, 합계 overflow, DB 정수 표현 불가, civil/instant 차감 후 year 1..9999 이탈을 모델 생성/산술 전에 검사한다.
- counter/revision은 정수 0..2^53−1 및 실제 저장·후속 증가가 안전한 범위다. `dataRevision + 1` 같은 후속 연산이 넘치는 후보를 ready로 제공하지 않는다. lateness의 기존 -1 등 sentinel은 일반 nonnegative 정책에 묶어 없애지 않는다. 점수의 onTime≤eligible 등 기존 불변식을 유지한다.
- 날짜는 year 1..9999이며 실제 calendar day/time 구성 요소를 strict round-trip 검증한다. 2월 30일·13월·24:xx·초 overflow를 DateTime의 자동 보정에 맡기지 않는다. civil 표현과 UTC instant 표현의 parser를 구분하여 offset 표기가 민간 시각을 조용히 이동시키지 않는다. 기존 format 1/2의 합법적인 ISO 표현은 golden fixture로 보존한다.

## 확정 결정: timezone와 DST

1. bundled IANA registry 및 지원 alias/UTC 존재를 직접 확인한 뒤 resolver를 호출한다. unknown zone은 명확한 검증 실패이며 UTC fallback 금지다. 네트워크 tz 조회를 추가하지 않는다.
2. strict civil 및 저장 offset 안전성을 먼저 검사한다. 과거/미래 판정에는 검증 시작 때 고정한 현재 UTC와 명시적 occurrence·완료 fact를 사용한다. 파일 cutoff가 인증됐다는 사실만으로 현재 시간이거나 믿을 수 있는 과거 분류 기준이 되지는 않는다.
3. 과거/완료 일정은 civil/zone/명시적 offset을 유지한다. 현 tzdb의 mismatch만으로 과거를 재작성하거나 백업 전체를 손상이라고 판단하지 않는다. offset 없는 legacy 과거 자료는 현재 규칙으로 유일한 occurrence를 해석할 수 있어도 원래 불확실성을 유지하며, 추정 offset을 원래 확정값으로 저장하지 않는다.
4. 미래의 유일 occurrence는 civil+zone을 보존하고 현재 규칙에 맞는 instant를 계산한다. 변경된 일정의 목록/개수와 영향은 verified preview 및 최종 확인에 포함한다. 이는 데이터를 조용히 정규화한 뒤 일반 성공으로 취급하는 동작이 아니다.
5. 미래 overlap에서 저장 선택이 후보에 대응하면 선택을 유지한다. absent/stale choice로 확정할 수 없거나 gap이면 ready/apply를 막고 명시적인 시간대 선택/규칙 확인 상태를 제공한다. A10의 사용자 선택/수정 계약으로 연결하며 임의 첫 offset/UTC/gap 앞으로 이동은 금지한다.
6. format 1/2에는 tzdb version이 없으므로 과거 규칙 변화와 원래 잘못된 자료를 완전히 판별할 수 있다고 주장하지 않는다. 반복 일정도 동일 원칙 아래 실제 materialized slot·override·exclusion·ordinal·segment 경계를 검증한다. 무한 series 전체를 펼치는 검증은 금지다.

## 확정 결정: 관계와 연산 예산

- nonempty preparation은 원본 nextId 기준으로 head/tail 각 하나, indegree≤1, 모든 노드 정확히 한 번 도달하는 chain이어야 한다. self-link, cycle, 분리 chain, 여러 head/tail, 병합 edge, 다른 소유자 step 참조를 `ordered`/DAO 재연결 **전에** 검증한다. 빈 default 등 기존 도메인에서 합법인 상태는 신규 form 정책으로 거절하지 않는다.
- ID 유일성은 실제 table/owner namespace로 확인한다. 다른 table의 합법 동일 ID를 전역 금지하지 않으며 같은 table 안의 소유 경계 침범을 허용하지 않는다. duplicate JSON key를 마지막 값으로 덮지 않고 parser 단계에서 거절한다. 동일 place ID의 상충 내용, 참조 없는 template/definition/segment, 중복 occurrence slot, 잘못된 scope-owner 연결을 검사한다. 도메인상 합법인 삭제 template snapshot 및 보존용 orphan immutable definition은 임의 삭제/거절하지 않는다.
- 반복 정의/단계/소유자/segment/slot 인덱스를 한 번 만들고 재사용한다. 각 record에서 모든 정의나 원점부터의 slot을 반복 검색하는 n×m 검증을 피한다. 실제 staging의 foreign-key/uniqueness 제약 및 read-back은 순수 validator를 대체하지 않고 보완한다.
- 파일당 **2,000,000 logical work unit**을 초기 지원 예산으로 둔다. 구현 상수와 문서에서 단위를 고정한다: 레코드 admission/관계 검증을 위한 노드 방문 1회=1, graph/reference edge 검사 1회=1, recurrence 후보 civil slot 생성·검사 1회=1, zone offset 후보 round-trip 검사 1회=1. 재방문은 다시 계수하며 재사용 cache의 lookup도 해당 관계 확인 1회로 센다. 검증 함수 안에서 중첩 expansion을 새 독립 예산으로 초기화하지 않는다. 알고리즘 변경으로 단위를 바꾸면 근거와 fixture 영향을 기록한다.
- byte/token parsing 비용은 별도의 Q1 byte/depth/string 제한으로 다루며 1 byte=1 work unit으로 세지 않는다. work unit은 CPU 시간이나 모든 기계 instruction 수가 아니다. 단계별 계수/잔여 예산의 증감은 overflow-safe하게 처리하고 안전한 cancel/yield 경계를 둔다. index/cache 메모리도 레코드 한도와 모바일 peak memory 측정에 포함한다.
- 총량/연산 예산 초과는 지원 한도 오류다. 원본 손상/암호 오류로 보고하거나 데이터를 잘라 정상 backup으로 꾸미지 않는다. 최소 10,000 일정과 다중 segment 정상 fixture를 예산 안에서 통과시키고 결과를 기록한다.

## 의미 있는 검증 행렬

아래는 실행할 계획이며 현재 통과 기록이 아니다. 성공 receipt나 호출 순서만 검사하지 않고 원본 durable rows/key/runtime/등록 상태 및 후보 read-back을 비교한다. 실패 시 raw secret이나 원문을 테스트 artifact에 남기지 않는다.

## 실제 grill 문답

아래는 전담과 root의 실제 순차 문답이다. root는 사용자 지시에 따라 대리 답한다. 구현과 GitHub 게시를 완료했다는 뜻이 아니다.

### Q1 — 전체 크기와 bounded stream

**전담 질문 원문**

> D05 Q1 — bebf2a31에서 readAsBytes→복호문 전체 결합→jsonDecode가 겹치며 ADR 0031의 bounded stream 약속과 다릅니다. 총량 제한만 추가하고 이 경로를 유지하면 ADR를 충족하지 못합니다. 추천: 정상 A09·Recovery D02 공통 검증 입력을 bounded stream으로 바꾸고, 파일 제공자의 사전 length와 실제 누적 읽기/복호문 바이트를 모두 검사하며, 인증 final marker 이전에는 preview/활성 DB 변경을 금지합니다. 초기 제품 수용 한도는 암호화 파일 72 MiB, 복호문 UTF-8 JSON 64 MiB, JSON 중첩 32, 일정 100,000개, 모든 레코드 합계 500,000개, 준비 단계 1개 정의당 1,000개로 명시하고, 최소 10,000 일정 정상 fixture를 지원합니다. 제한은 자동 이력 삭제/자르기가 아니라 명확한 원본 보존 실패이며, 동일 한도를 export preflight에 적용해 새 앱이 스스로 복원 불가한 파일을 성공 저장하지 않도록 합니다. streaming parser가 전체 map을 다시 쌓거나 giant 문자열을 먼저 할당하지 않게 token/count 한도를 증가 단계에서 검사하고, 중간 산출물은 암호화 staging만 허용합니다. 이 정책/초기 숫자를 확정할까요? 숫자는 성능 보장 수치가 아니며 실제 모바일 peak memory/시간을 별도로 측정하고, 기존 유효 format 1/2 데이터가 넘으면 손실 변환 없이 명시적 지원 한도 오류와 현재 데이터 보존을 제공합니다.

**root 답변 원문**

> Q1을 확정합니다. 정상 A09와 손상 복구 D02가 같은 bounded input/인증·검증 경계를 사용하고, 사전 length와 실제 누적 암호문/복호문 크기를 모두 검사합니다. 초기 수용 한도는 암호문72MiB, UTF-8 복호문64MiB, 중첩32, 일정100,000개, 전체 레코드500,000개, 준비 정의당 단계1,000개로 명시합니다. 이는 각각의 상한이지 어떤100,000일정 조합도64MiB 안에 들어간다는 보장이 아니며 최소10,000일정의 정상 fixture를 실제로 검증합니다. export에도 같은 수용 규칙을 적용해 새로 내보낸 파일이 자체 정책 때문에 복원 불가하지 않게 합니다. 초과 입력을 자르거나 기존 이력을 삭제하지 않습니다. 인증 final marker 전 preview/active DB 변경 금지, 실제 streaming에서 giant token/frame 선할당과 전체 map 재결합을 막고 중간 파일은 암호화 staging만 허용합니다. 기존 유효 format1/2라도 한도 초과 시 명확한 지원 한도 오류와 원본 보존을 제공하고 이를 손상/암호 오류로 표시하지 않습니다. 실제 모바일 memory/시간 측정 결과에 따라 수치를 바꾸려면 근거와 변경 결정을 별도 기록하며, 테스트 통과를 위해 몰래 축소하지 않습니다.

**추가 조사 전달 원문**

### Q2 — 문자열·레코드·숫자·날짜 한도

**전담 질문 원문**

> D05 Q2 — 현재 단순 String/int 수용 때문에 거대한 ID·note·분 값이 모델 생성/정렬/날짜 산술까지 갑니다. 추천 수용 규칙은 ID와 참조 ID 최대 512 UTF-8 bytes(기존 UUID만 강제하지 않음), 표시 이름·note는 기존 schema 표현 가능성을 보존하되 모든 개별 문자열 64 KiB UTF-8 이하, JSON object key 512 bytes 이하, 이름은 실제 해당 DB/도메인 한도(예: place/recurring step 30) 적용, 일반 note는 16,384 Unicode scalar와 64 KiB 중 먼저 닿는 한도로 합니다. UI 신규 입력의 1~1440분을 legacy restore에 그대로 강요하지 않고 저장된 0분을 허용하되 move/spare/profile spare/step은 각각 0~1440분, 준비 정의 합계도 checked arithmetic으로 검증합니다. 전체 preparation lead는 최대 1,440,000분(1,000×1,440)이며 일정 순간에서 차감 시 표현 범위를 벗어나면 실패합니다. 일반 카운터/revision은 0..2^53−1 및 실제 저장/증가 여유를 검사하고, lateness -1 sentinel 등 기존 특수값은 별도 계약으로 보존합니다. 모든 날짜는 year1..9999와 월/일/시/분/초의 strict round-trip으로 overflow 자동 보정을 금지합니다. native schema/과거 합법 데이터와 충돌하는 추가 길이 제한은 임의 정규화·절단 대신 명시적 미지원이며, unknown field도 depth/token/byte 제한을 우회하지 못하게 검사합니다. 이 하위 한도 정책을 확정할까요? record 총량에는 일정·고유 place·template·준비 정의·모든 준비 step·segment·exclusion과 profile/preferences를 포함하고 중복 ID로 count를 회피하지 못하게 입력 항목 수부터 셉니다.

**root 답변 원문 — duration 상한 정정**

> Q2는 문자열/ID/record count/strict 날짜/checked arithmetic 방향을 확정하되 duration 상한은 정정합니다. 512-byte ID/reference, 512-byte object key, 개별 문자열64KiB, note16,384 Unicode scalar와64KiB 중 먼저 닿는 한도, 실제 DB/domain 이름 제약을 적용합니다. 입력 항목부터 count하여 중복 ID로 총량을 피하지 못하게 하고 unknown field도 token/depth/bytes를 소비합니다. 날짜는 year1..9999와 strict round-trip, counter/revision은 정수0..2^53−1 및 저장/후속증가 여유, 기존 lateness sentinel 의미를 보존합니다. 다만 legacy restore에 각 duration0..1440분과 합계1,440,000분을 새로 강제하지 않습니다. 큰 duration 값 자체가 처리량을 늘리지 않는 경로라면 UI 한도보다 컸던 합법 데이터를 굳이 미지원으로 만들 이유가 약합니다. 실제 도메인에 원래1440분 상한이 명시된 필드만 따르고, 나머지는 음수 금지·Duration/DB 정수의 안전 표현·합계 checked arithmetic·civil/instant 차감 결과의 year1..9999 범위를 검증하세요. 생성 전에 단위 곱셈 overflow를 차단하고 불변식 위반과 자원 한도 초과 오류를 구별합니다. 기존 UI1..1440 규칙을 legacy backup decoder로 확대하지 않는 A08 결정과도 맞춰 주세요. 큰 문자열/파일/records 초과는 명시적 자원 한도 오류이며 자동 절단/정규화하지 않습니다.

**root의 다음 질문 조사 지침 원문**

> 다음 timezone 결정에는 ADR0021도 함께 대조해 주세요. tzdb 업데이트 후 미래 일정은 civil meaning을 유지하며 instant를 재계산·사용자에게 알리고, 과거 일정은 unchanged라는 계약입니다. 현재 tzdb offset과 다르다는 이유만으로 과거의 합법적 완료 일정/선택 offset을 임의 재작성하거나 모든 백업을 손상으로 처리하지 않도록, 실제 알려진 zone/불가능 civil time 검증과 규칙 버전 변경의 경계를 질문에서 구분해 주세요.

### Q3 — 시간대 규칙 변경과 역사 보존

**전담 질문 원문**

> D05 Q3 — timezone 검증은 unknown zone과 tzdb 변경을 구분합니다. 추천: bundled tz registry에 실제 존재하는 IANA ID/지원 alias(UTC 포함)를 확인한 후 civil resolver를 호출하고 UTC fallback은 금지합니다. strict civil 구성 요소와 저장 offset의 안전 범위를 먼저 검증합니다. 과거/완료 일정은 명시적 저장 offset·원래 civil 의미를 보존하고 현재 tzdb와 다르다는 사실만으로 손상/재작성하지 않습니다. 미래 일정은 현재 tzdb에서 유일한 occurrence이면 원래 civil+zone을 유지한 채 instant/offset 재계산 차이를 verified preview에 명시합니다. overlap은 저장된 선택 offset이 현재 후보에 대응할 때만 그 선택을 유지하고, absent/stale offset으로 선택을 확정할 수 없거나 현재 규칙상 gap이면 '시간대 선택/규칙 확인 필요'로 정상 ready preview와 apply를 막습니다. 임의 첫 offset 선택·UTC 대체·gap 앞으로 밀기는 금지하며 사용자 수정/선택은 A10의 명시적 시간대 UX 계약으로 연결합니다. format1/2에 tzdb version이 없으므로 현재 mismatch만으로 공격/원래 무효 데이터를 판별했다고 주장하지 않고, 과거 offset 없는 유일 occurrence는 기존 호환대로 현재 규칙으로 해석하되 역사적 instant 보존이 증명됐다고 표시하지 않습니다. 반복 규칙은 시작점뿐 아니라 실제 materialized slot/override/exclusion의 civil/ordinal/구간 관계를 검증하되 무한/수만 년 전체 expansion을 하지 않고 bounded 검증 계산을 사용합니다. 이 과거 보존·미래 변화 설명·불명확 선택 보류 정책을 확정할까요?

**root 답변 원문**

> Q3을 확정합니다. 알려진 IANA ID/지원 alias를 직접 확인하고 unknown zone을 UTC로 대체하지 않습니다. 과거/완료 일정은 저장된 civil/zone/명시적 offset을 보존하며 현 tzdb 불일치만으로 손상 처리하지 않습니다. 과거 offset 없는 유일 occurrence는 호환 해석이 가능해도 원본 필드의 불확실성을 보존하고, 역사 instant가 입증됐다고 하거나 추정 offset을 원래 확정값처럼 조용히 저장하지 않습니다. 미래의 유일 occurrence 재계산 차이는 verified preview의 영향 목록/개수와 최종 확인에 포함합니다. overlap 선택이 현재 후보에 대응하지 않거나 gap이면 ready/apply를 막고 A10의 명시적 선택/수정 경계로 연결합니다. 임의 첫 offset/UTC/gap 이동은 금지합니다. 과거·미래 판정에는 인증된 백업 cutoff만 믿지 말고 검증 시 고정한 현재 UTC 시각과 보존된 명시적 occurrence/완료 fact를 사용하고, offset 없는 legacy 판정의 불확실성을 표시하세요. 반복 자료는 bounded 관계 검증으로 slot/override/exclusion/ordinal을 확인하고 무한 expansion을 하지 않습니다. tzdb version이 없어 원래 무효와 규칙 변경을 판별할 수 없는 경우를 정확히 남깁니다.


### Q4 — 그래프·처리 예산·검증 증거

**전담 질문 원문**
