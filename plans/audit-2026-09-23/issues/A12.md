# [P1][A12] 종료 상태의 알림 탭을 준비 완료까지 보존하고 정확한 일정으로 한 번만 진입

## 문제와 사용자 영향

`NotificationService`는 실행 중 `onDidReceiveNotificationResponse`만 등록하고 `getNotificationAppLaunchDetails`를 호출하지 않는다. 따라서 앱이 종료된 상태에서 Android/iOS Fallback Notification을 탭하면 앱은 열리지만 대상 일정 진입 의도가 사라질 수 있다. 실행 중 callback도 `NavigationNotificationTapRouter`에서 곧바로 `NavigationService.push`로 전달되어 DB/Local Profile/router 준비 전에 실패하거나 startup/onboarding/permission gate redirect에서 유실될 수 있다.

별도의 자체 native alarm launch 처리에는 pending map이 있지만 Auth authenticated와 navigator context만 확인하고 push 전에 pending을 지운다. notification/alarm gate 해소, 초기 launch와 callback의 수신 순서, 데이터 교체, 중복 전달은 공통으로 다루지 않는다. 플러그인의 launch details를 단순히 한 번 추가하는 것으로 끝내지 않고 진입 의도의 수명과 준비 상태를 함께 고친다.

감사 우선순위는 **P1**이다. 누락과 위험 경로는 코드로 확인했고 Android/iOS 종료→탭 현상의 실제 기기 재현은 아직 수행하지 않았다. 이 문서는 설계 및 실제 문답 기록이며 구현 완료나 기기 통과 증거가 아니다.

## 도메인 및 기존 결정

- Local-only OnTime은 Android/iOS 제품이며 네트워크·서버·로그인·원격 push를 추가하지 않는다(ADR 0011, 0016).
- Fallback Notification을 통해서도 현재 Schedule에 진입할 수 있어야 한다(ADR 0010).
- Recovery Mode에서는 일반 제품 화면으로 이동하지 않는다. 같은 DB 재시도와 Backup Restore/Local Data Reset을 구별한다(ADR 0023).
- A11의 최소 allowlist, 현재 DB 재검증, 명시적 시작 확인, `requiresConfirmation` 보호를 유지한다. 알림 payload는 준비 시작/완료 명령이 아니다.
- pending tap/receipt sequence/generation은 일반 구현 개념이다. CONTEXT에 새 도메인 용어를 넣지 않는다. 기존 정책을 지키는 되돌릴 수 있는 구현 수정이므로 새 ADR도 만들지 않는다.

## 확정 범위와 설계

### 1. 초기 launch와 실행 중 callback의 수집

1. Android/iOS plugin 초기화 후 공개 `getNotificationAppLaunchDetails`를 조회한다. `didNotificationLaunchApp` 및 유효 response가 있을 때만 최소 route 정보를 제출한다. null/false/손상 payload는 일반 시작을 방해하지 않는다.
2. 성공 응답(null 포함)을 받은 뒤에는 같은 서비스 수명에서 초기 launch 조회를 반복하지 않는다. 실패에는 완료 표시를 하지 않고 callback 수신을 유지한다. 다음 명시적 initialize/resume/retry가 재시도를 할 수 있다.
3. 동시 setup/initialize/launch 조회는 single flight로 묶는다. 반복 초기화가 callback을 중복 설치하거나 같은 초기 진입을 반복하지 않아야 한다.
4. 초기 조회를 시작할 때 receipt sequence와 `LocalDataOperationGate.shared.generation`을 캡처한다. 반환 전에 callback/native로 더 최신 의도 B를 받았거나 데이터 세대가 바뀌면 늦은 초기 A를 버린다. 느린 cold 조회가 최신 사용자 의도를 덮지 않는다.
5. 입력 경계부터 A11 route allowlist로 축소한다. raw payload, 준비 이름, 과거 fingerprint, arbitrary start 명령을 보존하거나 로그로 내보내지 않는다.

### 2. pending과 준비 상태

1. DB/Local Profile, onboarding, notification/alarm gate, 실제 router가 준비되기 전에는 마지막 형식상 유효한 Schedule 진입 의도 하나만 현재 프로세스 메모리에 보관한다.
2. A→B 순서로 탭하면 B를 보관한다. malformed/unknown 입력은 기존 유효 pending을 덮지 않는다. 이후 B가 없어져도 A나 nearest 일정으로 돌아가지 않는다.
3. Auth authenticated만으로 준비 완료로 간주하지 않는다. 실제 router redirect가 해소된 상태에서만 전달하며 gate에 진입한 것을 성공 소비로 처리하지 않는다.
4. 알림 권한을 거부했더라도 안내 gate를 통과한 이후에는 이미 받은 탭을 현재 DB로 검증하고 확인 화면을 열 수 있다. 탭 처리 때문에 새 권한 요청을 추가하지 않는다.
5. 별도 SharedPreferences/DB 영속 큐는 추가하지 않는다. 프로세스가 다시 종료되면 OS가 다음 launch에 제공하는 정보로 새로 수집한다.

### 3. 현재 DB의 정확한 대상과 실패 구별

1. 준비 완료 후 해당 ID가 현재 DB에 존재하고 unfinished인지 확인한다. payload의 과거 데이터나 현재 nearest Schedule로 대체하지 않는다. domain use case/repository 경계를 유지한다.
2. 존재·미완료가 확인된 일정의 최신 시작 확인 화면만 연다. 탭 자체로 준비 시작, 완료, outcome 생성, 자동 재시작을 수행하지 않는다.
3. definitive not found/completed이면 의도를 소비·거절하고 안전한 현재 화면을 유지하거나 home으로 종료한다. LoadingScreen에 무한히 남거나 다른 일정을 표시하지 않는다.
4. DB 일시오류는 not found와 구별한다. 같은 generation의 최소 pending을 유지하고 readiness 회복/명시적 retry에서 다시 검증한다. 필요한 경우 catch-all not-found를 최소한의 typed outcome 경계로 분리한다.
5. raw payload/내부 예외를 사용자 문구로 표시하지 않고 자동 무한 polling을 추가하지 않는다.

### 4. 중복 수신 및 데이터 세대 교체

1. 동일 schedule+route 종류가 pending/inflight/현재 같은 확인 화면에 있으면 중복 push하지 않는다. 초기 launch, callback, 자체 native 경로가 같은 의도를 전달하는 경우도 포함한다.
2. 그 확인 화면을 나간 뒤 새로운 사용자 callback 탭이 오면 다시 열 수 있다. 영구 schedule-ID blacklist나 임의 시간 TTL로 별도 의도를 차단하지 않는다.
3. ‘한 번만’은 현재 프로세스에서 같은 진입 의도를 중복 push하지 않는 범위다. OS가 tap ID/consume를 보장하지 않으므로 글로벌 exactly-once라고 부르지 않는다.
4. 같은 DB의 Recovery retry는 메모리 pending을 유지하며 Recovery/onboarding 동안에는 이동하지 않는다.
5. restore/reset으로 기존 operation gate generation이 바뀌면 pending, inflight 검증, 늦은 cold 조회 결과를 모두 무효화한다. 복원 데이터가 우연히 같은 schedule ID여도 이전 탭으로 자동 진입하지 않는다.
6. 모든 비동기 검증/전달은 수신 sequence와 데이터 generation을 완료 시점에도 재확인한다. 새로운 B나 새 데이터 세대 위에 오래된 A의 결과가 적용되지 않아야 한다.

플랫폼 fake 테스트는 plugin 초기 응답/오류/동시 조회/callback 경합을 검증한다. coordinator 단위 테스트는 last-valid-wins, dedupe, generation, 오류 분류를 검증한다. 실제 router+gate+대상 확인 화면을 포함하는 widget 회귀는 redirect 후 의도 유실 및 잘못된 Schedule 표시를 검증한다. 기존 알림 routing, A11 privacy, 일정 시작 확인 회귀도 실행한다. 단순 fake navigation 호출만으로 전체 UI 경로가 통과했다고 판단하지 않는다.

기본 검증은 필요한 생성 산출물 재생성(비추적), 변경 Dart format, 관련 Flutter tests, flutter analyze이며 통합 변경에는 전체 Flutter suite를 실행한다. 실제 기기 증거는 자동 테스트와 별도 기록한다.

## 실제 기기 검증 계획과 현재 한계

Android와 iOS 각각 Fallback Notification을 실제 예약하고 프로세스 종료→알림 탭→정확한 일정 시작 확인 화면을 기록한다. ordinary app icon cold start, 실행/백그라운드 상태 탭, 느린 startup/gate, 삭제·완료된 일정, 화면 이탈 후 재탭, native와 fallback 중복 수신을 가능한 OS 조건에서 확인한다. OS 버전·앱 빌드 SHA·기기·예약/탭 시각·기대/실제 화면·중복 화면 수를 증거로 남긴다. 앱 프로세스 종료와 Android 설정의 force-stop은 구별하고 force-stop 상태의 OS 알림 전달을 일반 종료 보장으로 과장하지 않는다.

현재 기기 시나리오는 **미실행**이다. fake/widget 통과가 향후 확인되어도 실제 Android/iOS cold tap 검증은 별도 pending으로 표시한다. D01의 runApp 이전 bootstrap 실패/복구 UI 문제, OS가 보관하지 않는 종료 후 tap의 영속 복원, 글로벌 exactly-once 보장은 A12 완료 주장에 포함하지 않는다.

## 의존성 및 제외 범위

- A11의 privacy allowlist/confirmation/current-DB 정책 위에 구현한다. 기존 변경을 되돌리지 않는다.
- A01–A05의 플랫폼 등록/재등록/노출 정책은 보존하고 알림 scheduling redesign이나 새 permission 흐름은 만들지 않는다.

- 서버·로그인·네트워크·원격 push·분석 이벤트·백그라운드 메시징·플러그인 fork·DB schema 또는 영속 tap queue 추가는 제외한다.
- 구현/원격 이슈 생성은 root의 별도 지시 후 수행한다. 이 문서는 GitHub 이슈 본문으로 사용하도록 준비했다.
