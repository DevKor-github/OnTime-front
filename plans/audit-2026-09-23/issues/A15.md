# [P1][A15] 진행 중 재조정에 들어온 변경을 유실 없이 반영하고 데이터 교체와 알림 작업을 직렬화

## 문제와 사용자 영향

알림 재조정이 일정 목록을 읽은 뒤 새 일정이 저장되면, 새 호출은 진행 중 Future에 합류하고 새 목록을 읽지 않는다. 첫 실행이 오래된 목록으로 OS 예약과 registry를 저장하면 새 일정의 알림이 빠지거나 수정 전 시각·내용이 남을 수 있다. 삭제·완료의 표적 취소 역시 재조정과 별도로 실행되어 오래된 재조정이 삭제된 예약을 다시 쓰거나 취소 증거를 덮을 수 있다. 상세 표시 OFF도 같은 경합에서 최신 선택이 적용되지 않을 수 있다.

Backup Restore/Local Data Reset과 겹치면 영향이 더 크다. registry 저장 직전에 세대만 확인하는 것으로는 이미 OS에 보낸 구세대 예약이 데이터 교체 이후 늦게 성공하는 것을 막지 못한다. 새 데이터에 같은 일정 ID가 있으면 구세대 정리가 신세대 예약을 취소하는 역방향 경합도 생긴다.

감사 판정은 **P1 · 경쟁 조건 확인, 결정적 재현 필요**다. 이 문서는 읽기 전용 조사와 실제 grill 문답으로 확정한 구현 명세다. 현재 A15 구현·자동 테스트·실기기 재현 완료를 주장하지 않는다.

## 도메인과 기존 결정

- Local-only OnTime은 Android/iOS 제품이다. 서버·로그인·원격 push·분석 수집을 추가하지 않는다(ADR 0011, 0016).
- Schedule은 원본 로컬 일정이고 Schedule Notification/Alarm은 재구성 가능한 전달 상태다. DB 저장 성공과 OS 예약 성공은 같은 사건이 아니다.
- ADR 0019에 따라 현재 유효한 미래 Schedule/반복 Schedule Occurrence 중 가장 가까운 대상부터 플랫폼 용량 60개를 적용한다. 이미 지난·완료·삭제 대상을 재생하지 않는다.
- ADR 0013은 restore의 원자적 데이터 교체 후 미래 알림 재구성을, ADR 0020은 reset의 구세대 상태 제거를 요구한다.
- ADR 0030과 A05/A11의 private 기본값, 원문 최소화, 취소 ownership/tombstone을 유지한다. 재조정 경합을 해결하면서 상세 OFF 선택을 되돌리거나 원문을 새 큐에 저장하지 않는다.
- A13의 actual exact/inexact 결과와 A14의 present/absent/unknown·provider 교체·부분 실패 계약을 유지한다. 최종 registry 존재를 OS 도착 보장으로 해석하지 않는다.
- request revision, dirty, drain, generation은 구현 조정 개념이다. 새로운 제품 용어나 ADR는 필요하지 않으며 CONTEXT를 구현 명세 저장소로 사용하지 않는다.

## 확정한 처리 계약

### 요청 접수와 각 Future의 의미

1. 한 알림 조정 소유자가 side effect를 실행한다. 요청 접수는 첫 await 이전에 동기적으로 메모리 순번을 증가시키고 해당 호출의 대기자를 등록한다.
2. pass 시작 때 그 pass가 책임지는 revision cutoff를 캡처한다. 같은 세대에서 cutoff 이후 새 요청이 접수되면 다음 pass가 현재 DB·설정·권한·언어·시간대를 새로 읽는다.
3. burst는 하나의 후속 pass로 합쳐도 된다. 후속 pass 도중 다시 변경이 들어오면 또 다음 pass가 필요하다. 단순 `_inFlight` Future 반환으로 새 요청을 소비하지 않는다.
4. 각 call은 최소 자기 요청까지 포함한 pass의 결과 또는 실패로 정확히 한 번 완료한다. 첫 pass의 오래된 결과로 다음 revision의 호출을 완료하지 않는다.
5. 모든 대기자를 전역 quiet 시점까지 붙잡지 않는다. 계속 편집하더라도 이미 처리한 cutoff의 대기자는 해당 결과로 끝나고 새 요청은 다음 pass가 맡는다.
6. 마지막 요청 검사·idle 전환·새 drain 시작 사이의 경합도 유실 없이 처리한다. 구현의 동기 상태 전이와 finally 정리에서 이를 보장한다.
7. 일반 저장 UI는 OS 예약 완료를 기다리도록 확대하지 않는다. commit 이후 요청 접수는 반드시 이뤄지고 비동기 오류는 관찰한다. 이미 성공한 DB 저장을 알림 실패 때문에 롤백하지 않는다.
8. request revision은 프로세스 내 접수 순번이다. 백업 freshness용 durable dataRevision, DB schema version, lifecycle generation과 혼용하지 않는다.

| 상황 | 계약 |

| pass 부분 실패/조회·OS·registry 예외 | 해당 cutoff 대기자를 실패/부분 결과로 완료한다. 무기한 성공 대기로 붙잡지 않는다. |
| 실패 도중 실제 새 요청 접수 | 새 요청을 유실하지 않고 최신 상태로 다음 pass를 수행한다. |
| 새 요청 없이 실패만 반복 | 오류만으로 dirty를 재설정하지 않는다. 다음 시작/resume/명시적 retry/실제 mutation까지 멈춘다. |

| 영속 저장소 자체 실패 | 메모리의 최소 ownership과 실패를 보존하고 A14 후속 관측으로 복구한다. 프로세스 사망까지 보장한다고 쓰지 않는다. |
| generation 변경 | 일반 OS 실패와 구별되는 typed invalidation 결과/예외로 구세대 대기자를 완료한다. |
| provider 무응답/timeout | 성공·취소 완료로 바꾸지 않는다. timeout이 native 호출을 실제 취소한다는 가정을 금지한다. 늦은 반환도 ownership/정리 경계가 회수해야 한다. |

startup/resume, 실제 준비 완료, mutation coordinator 등 fire-and-forget 호출부는 failure/invalidation을 관찰한다. raw 일정·준비 내용이나 내부 예외를 사용자 문구/로그에 추가하지 않는다. UI의 기존 결과 모델에는 실제 예약 실패/확인 필요를 연결하되 일반 설정 UI 전체 개편은 U03과 구분한다.

### 취소·restore/reset의 직렬 경계

1. reconcile의 OS 작업 및 registry 저장, 표적 취소, 전체 취소, restore/reset의 알림 정리는 작은 명시적 coordinator/port를 통한 하나의 직렬 소유권을 사용한다. 새 전역 작업 프레임워크나 중첩 lock을 도입하지 않는다.
2. 기존 `LocalDataOperationGate.generation`을 재사용한다. A12의 최종 readiness/ChangeNotifier 인터페이스와 통합하고 별도의 데이터 세대 체계를 만들지 않는다.
3. replacement 시작 즉시 구세대 신규 예약 작업의 접수를 막고 대기자를 invalidated로 완료한다. 아직 provider에 보내지 않은 오래된 예약은 실행하지 않는다.
4. 이미 provider에 보낸 호출은 반환 결과를 회수하고 최소 ownership/취소 증거를 보존한다. 구세대 결과를 새 registry의 정상 예약으로 쓰지 않는다.
5. lifecycle은 구세대 in-flight side effect의 반환·정리 경계를 거친 뒤 DB 교체/완료를 허용한다. 데이터 교체 완료를 먼저 표시하고 늦은 구세대 알림을 방치하지 않는다.
6. 같은 stable ID의 신세대 예약은 구세대 호출·정리가 정리된 이후에만 수행한다. 구세대 cleanup이 새 등록을 취소할 수 있는 순서를 허용하지 않는다.
7. restore 후 재등록은 gate가 해제된 새 generation에서 현재 복원 DB를 읽는다. reset은 기존 재시작 정책에 따라 신규 예약을 막는다.
8. gate를 소유한 restore가 gate 해제를 기다리는 drain을 다시 await하는 교착을 만들지 않는다. lifecycle quiesce/cleanup과 일반 재조정 진입을 분리해 테스트한다.
9. 취소 오류를 이미 없음으로 처리하거나 A05/A11 tombstone을 deleteAll/replaceAll로 지우지 않는다. 실패 시 성공하지 않은 정리를 완료로 표시하지 않는다. A14가 정한 플랫폼별 취소 증거 한계를 지킨다.
10. 전체 재시작 후 reset marker·프로세스 사망·디스크 오류의 crash consistency는 D03 의존이다. A15가 실행 중 경합을 막았다고 완전한 reset 복구까지 완료한 것으로 보고하지 않는다.

### 실제 요청 경로와 반복 일정

구현에서 현재 제품 경로를 다시 추적한다. 일반 일정 생성·수정·삭제, 실제 준비 완료, 반복 생성·회차/이후 수정·삭제, 알림 ON/OFF·상세 표시 변경, permission/locale/timezone 재조회, 시작/resume, restore 완료가 commit/refresh 이후 적절한 요청을 접수하는지 확인한다.

Default/Custom Preparation 저장은 현재 미래 일정의 준비 시작 시각·내용에 실제 영향을 주는 경로에 한해 같은 진입점을 연결한다. 무관한 템플릿 라이브러리 변경까지 전역 감시하지 않는다. 반복 회차 materialize나 registry 갱신 자체를 새 요청으로 돌리는 DB watcher, 주기 polling, 임의 TTL, 새 background scheduler를 만들지 않는다.

upstream recurrence 규칙·DB schema2·backup v2를 유지한다. nearest eligible 60개가 바뀌면 최종 집합이 최신 후보를 반영해야 한다. 한 pass 내 여러 DB 읽기의 transaction snapshot 일관성이 별도 결함이면 A08/C01 경계를 명시하되, committed mutation 후 실제 새 요청이 접수됐을 때 다음 pass가 최신 상태를 읽는 A15 계약은 반드시 보장한다.

## 수용 기준과 결정적 회귀

테스트는 sleep에 기대지 않고 Completer/barrier를 가진 blocking fake로 실제 snapshot/OS 호출/registry 저장 경계에 mutation을 끼운다. 요청 횟수만 검사하지 말고 provider의 최종 owned 예약 집합·내용·시각·registry·각 호출 Future 결과를 함께 확인한다.
