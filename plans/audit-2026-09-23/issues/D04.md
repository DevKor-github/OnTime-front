# [P1][D04] 암호화 저장소의 v1→v2 마이그레이션을 원자적으로 수행하고 과거 schema·실패 보존을 검증

## 현재 문제와 감사 기준 정정

현재 앱에는 schema 2와 v1→v2 마이그레이션이 있다. 2026-09-23 감사의 “DB v1의 onUpgrade는 명시적으로 실패한다 / 다음 schema 변경 전 기반이 필요하다”는 당시 관찰이며, 반복 일정 upstream 반영 이후 현재 결함을 그대로 설명하지 않는다. 기존 일회성 일정을 보존하면서 반복 일정용 4개 테이블과 5개 schedule column을 추가하는 구현과 파일 재열기 테스트가 이미 있다.

남은 문제는 실제 업그레이드의 원자성, 미래 버전 입력 거부, 독립적인 역사 schema 기준, 실제 암호화 엔진 연결 및 실패 보존 증거다. 현 `onUpgrade`는 DDL을 차례로 실행하며 transaction을 만들지 않는다. locked Drift의 native migration 경로도 이를 자동 transaction으로 감싸지 않는다. 중간 실패 시 앞 DDL만 남고 버전은 이전 값인 상태가 가능하다. 또한 from=3, to=2 같은 미래 파일 입력은 현재 guard를 통과하여 버전이 낮아질 수 있다.

네이티브 opener는 `PRAGMA key`를 실행하지만 실제 SQLCipher 엔진인지 확인하지 않는다. Android SQLCipher loader override도 없다. 이는 암호화가 입증되지 않은 위험 경계이며 **현재 APK에서 평문 유출이 실제 확인됐다는 뜻은 아니다**. 실제 번들의 암호화 연결을 검증하지 않고 host plain SQLite 성공만으로 암호화 마이그레이션 완료를 주장할 수 없다.

우선순위 **P1**. 조사 기준 **`b81259bf66881289bf6bca9ac7cca2548de6a326`**. 이 문서는 전담 `grill-with-docs`의 조사와 root 결정 기록이다. 구현·새 테스트 실행·실기기 검증은 아직 수행하지 않았다. 다른 agent의 A15 WIP는 수정하지 않았고 D04의 DB/migration/opener 근거 파일은 기준 SHA와 동일함을 확인했다.

### Locked dependency 내부 조사 근거

다음은 설치된 pub cache의 실제 파일을 읽은 결과다. 최신 온라인 문서를 임의 적용한 것이 아니며 lock 변경 시 재검증한다.

- `drift-2.31.0/lib/src/runtime/executor/helpers/engines.dart:495–530`, `DelegatedDatabase._runMigrations`: `beforeOpen`을 호출한 다음 `setSchemaVersion`을 실행한다. 해당 경로에서 전체 migration을 자동 transaction으로 묶지 않는다. 515–518은 user_version=0을 신규로 정규화한다.
- `drift-2.31.0/lib/src/runtime/api/db_base.dart:118–138`, `GeneratedDatabase.beforeOpen`: onCreate/onUpgrade를 직접 await하고 그 뒤 beforeOpen hook을 실행한다.
- `drift-2.31.0/lib/src/runtime/query_builder/migration.dart:609–628`, `OpeningDetails.hadUpgrade`: 이전 버전과 새 버전이 다르면 참이다. 버전 감소도 포함된다.
- `sqlite3-2.9.4/lib/src/ffi/load_library.dart:32–48`, `_defaultOpen`: Android 기본 loader는 `libsqlite3.so`다.
- `sqlcipher_flutter_libs-0.6.8/README.md:24–38,55–72,77–93`: Android SQLCipher loader 선택, background isolate에서도 별도 설정, cipher_version 검사 필요를 설명한다. 일반 SQLite에서 PRAGMA key를 실행하는 것만으로 암호화가 확인되지 않는다.
- `sqlcipher_flutter_libs-0.6.8/lib/sqlcipher_flutter_libs.dart`, `openCipherOnAndroid`: `libsqlcipher.so`를 선택하는 실제 함수다.

## 제품 계약과 용어

[CONTEXT의 Local Data Store/Recovery Mode](https://github.com/DevKor-github/OnTime-front/blob/b81259bf66881289bf6bca9ac7cca2548de6a326/CONTEXT.md#L413-L420), [ADR 0018](https://github.com/DevKor-github/OnTime-front/blob/b81259bf66881289bf6bca9ac7cca2548de6a326/docs/adr/0018-encrypt-active-data-with-a-device-bound-key.md), [ADR 0022](https://github.com/DevKor-github/OnTime-front/blob/b81259bf66881289bf6bca9ac7cca2548de6a326/docs/adr/0022-use-encrypted-drift-as-the-local-data-source.md), [ADR 0023](https://github.com/DevKor-github/OnTime-front/blob/b81259bf66881289bf6bca9ac7cca2548de6a326/docs/adr/0023-preserve-local-data-when-migration-fails.md)를 따른다.

- Local Data Store의 schema version과 portable OnTime Backup의 format version은 다르다. D04는 schema migration이며 backup format 1/2 정책을 변경하지 않는다.
- schema1은 local-only 암호화 저장소의 역사적 schema다. 이전 서버 기반/legacy DB를 버전 숫자 하나만 보고 schema1로 간주하지 않는다.
- migration 성공은 저장소 변환의 사실이다. 복원, 준비 자동 시작, OS 알림 도착 또는 새 key 생성과 같은 뜻이 아니다.
- 새 제품 용어 결정은 없다. 기존 원자적 migration/보존 Recovery 계약을 구현하는 작업이므로 glossary에 구현 상세를 추가하지 않는다. 기존 ADR 0018/0023과 충돌하는 새 정책도 없으므로 새 ADR를 불필요하게 만들지 않는다.

## 확정 범위

### 실제 migration과 지원 버전

1. 역사적 local v1→현 v2 경로를 유지하고 실제 파일에서 transaction의 원자성을 보장한다. 성공한 전체 변경에만 schema version을 적용한다.
2. callback DDL만 transaction으로 감싼 뒤 version 기록이 외부에 남는다는 이유로 완료 판정하지 않는다. Drift의 실제 version 적용/commit 순서, beforeOpen 실패와 재열기까지 검증하여 반쯤 바뀐 schema와 이전 version 조합을 남기지 않는다. 구체 API는 구현 시 locked source에 맞춰 선택한다.
3. 기존 부분 DDL/알 수 없는 미래 schema는 `IF NOT EXISTS`, DROP, 자동 재생성으로 숨기지 않는다. 보존한 제한 Recovery로 보낸다.
4. v2 재열기는 no-op이어야 하며 일정/점수/준비 이력/재료화 결과를 다시 쓰거나 revision을 증가시키지 않는다. fresh v2와 upgraded v2의 의미적 schema를 비교한다.
5. D01 신규 설치/기존 store 구분을 따른다. 신규로 증명된 empty store는 허용하되 비어 있지 않은 user_version=0 또는 중단 파일을 신규 설치로 추정하지 않는다.

### 실제 암호화 opener

1. 실제 SQLite를 사용하는 isolate에서 첫 SQLite API 이전 Android SQLCipher loader를 설정한다. UI isolate 설정만으로 background 연결이 안전하다고 추정하지 않는다.
2. `cipher_version` 결과가 없거나 빈 값/조회 오류이면 schema read, migration, durable write를 시작하지 않는다. typed 실패와 자원 close를 D01 Recovery 경계로 전달한다.
3. 올바른 기존 Installation Data Key 적용 후 schema를 실제로 읽어 키/파일 조합을 검증한다. getOrCreate로 새 키를 발급해 실패를 덮지 않는다.
4. 기존 plaintext 가능 파일은 보존하며 자동 변환/삭제하지 않는다. D02의 검증된 백업 복원 또는 명시적 reset은 별도 사용자 작업이다.
5. 테스트 전용 plain NativeDatabase 경로는 순수 migration 로직 테스트에 사용할 수 있다. 제품 opener의 cipher guard를 테스트 편의를 위해 끄거나 약하게 만들지 않는다.
6. Android/iOS 실제 번들, 해당 번들의 SQLCipher 라이브러리와 실제 파일 경로로 encrypted historical v1 생성→v2 upgrade→close/reopen→잘못된 key 거부→일반 SQLite 읽기 거부를 검증한다. host/mock 성공은 이 증거를 대체하지 않는다.

### 독립 역사 자료와 CI

- schema1의 독립 출처는 `ccc6272bde15937a87dd577157b3330593718759`다. 그 source에서 생성한 snapshot/DDL과 합성 fixture를 생성 명령, tool/engine 버전, source commit, 파일 hash와 함께 추적한다. 실제 사용자 DB를 fixture에 넣지 않는다.
- 현재 entity의 직렬화 결과만으로 과거 데이터를 만들지 않는다. 과거 table/column/default/제약/인덱스/참조 및 당시 값을 고정한다.
- 현재 schema2 snapshot을 별도로 둔다. 지원 버전 목록과 경로는 명시적으로 유지하고 schema bump에 snapshot이나 경로가 빠지면 CI가 실패하도록 한다.
- JSON/SQL/합성 fixture는 의도된 기준 자료다. `*.g.dart`, `*.config.dart`, `*.freezed.dart`, `*.mocks.dart`는 기존 정책대로 로컬/CI에서 재생성하며 커밋하지 않는다.
- 기존 역제거 테스트는 보조로 유지 가능하다. 역사 fixture와 실제 migration opener 검증을 대체하지 않는다.
- Architecture의 DB schema 예시만 현재 계약에 맞게 정정한다. 서버/로그인 등 전체 문서 정리는 O01에서 수행한다.

## 실패·중단 결과 계약

- 정상 실패 이전에 확정되지 않은 migration은 기존 v1의 논리적 schema/data/user_version을 보존한다. 다만 외부 호출이 오류를 반환했어도 권위 있는 재열기가 완전한 v2를 보여주면 “v1으로 rollback됐다”고 표시하지 않는다. 응답과 commit 사실을 구분하고 현재 저장소 상태에 맞는 Recovery/재시도를 제공한다.
- 실제 같은 원자 경계에서 schema와 version이 확정되는지 검증한다. DDL commit 후 Drift의 version write가 별도로 실패하는 gap을 방치하지 않는다.
- 오류 fixture는 실제 SQLite 파일과 독립 연결을 사용한다. DDL별 실패, version/commit 실패 및 `SQLITE_FULL`, read-only, locked, constraint 상태가 실제로 발생했는지 코드·명령·관측 오류 코드로 입증한다. 아직 지정하지 않은 fault injection 기법은 구현 시 선택하고 기록한다. 어려운 경계를 단순 Future throw로 대체하지 않는다.
- 앱/별도 process를 강제 종료한 뒤 실제 재열기에서 이전 v1 또는 완전 v2만 허용한다. version만 바뀌거나 일부 DDL만 남은 중간 상태를 성공으로 취급하지 않는다. process-kill 검증을 기기 전원 손실 내구성 보장으로 확대하지 않는다.
- rollback 시 DB 파일 바이트 전체 hash가 항상 같아야 한다고 요구하지 않는다. SQLite journal/WAL/checkpoint가 물리적 배치를 바꿀 수 있다. 논리적 데이터·schema·version, key identity, 소유 파일군 보존을 검사한다. wrong-key/거부 경로에서는 불필요한 변경이 없다는 별도 증거도 수집한다.
- 파일 존재 여부 하나로 보존 성공을 판단하지 않는다. 원래 관계/데이터를 기존 schema의 독립 reader로 읽고 integrity/FK 상태를 확인한다. key 값은 출력하지 않고 테스트 소유 identity 또는 비노출 비교를 사용한다.
- 실패를 D01 typed Recovery로 전달하고 정상 UI, Schedule Notification 재등록, 준비 자동 시작을 차단한다. 정상 startup 재시도는 D01 단일 attempt를 재사용한다. 실패한 DB handle/백그라운드 isolate를 남긴 채 새 연결을 중첩하지 않는다.

## 수용 기준

- [ ] 감사의 과거 “migration 없음” 표현을 현재 v1→v2 존재와 검증 공백으로 정정한다.
- [ ] 역사 v1 snapshot/DDL/합성 데이터 fixture 및 provenance가 현재 모델과 독립적이다.
- [ ] 정상 historical v1 파일을 actual onUpgrade/opener 경로로 upgrade하고 7개 표의 모든 durable 필드·관계·인덱스·제약·default를 보존한다.
- [ ] 신규 recurring 테이블/컬럼은 올바른 empty/default 상태이고 기존 일정이 임의 recurring으로 바뀌지 않는다.
- [ ] upgraded v2와 fresh v2가 의미적으로 동등하며 v2 재열기는 데이터/이력/revision을 바꾸지 않는다.
- [ ] 미래 버전, 지원하지 않는 predecessor, 비어 있지 않은 version0, 이미 부분 DDL인 파일을 보존 거부한다. 실제 파일의 version이 낮아지지 않는다.
- [ ] 모든 DDL과 version/commit 원자 경계에서 실패 후 독립 재열기가 v1 또는 완전 v2만 보여준다. 애매한 응답은 권위 있는 상태로 판정한다.
- [ ] 실제 SQLite FULL/read-only/locked/constraint 오류와 별도 process-kill 결과를 기록한다. mock-only 성공으로 대체하지 않는다.
- [ ] 각 SQLite 사용 isolate의 Android loader 선택과 cipher_version fail-closed guard가 제품 opener에 적용된다.
- [ ] 키 적용 후 schema read를 검증하고 missing/invalid/wrong key/cipher 실패에서 기존 파일군·key를 보존하고 연결을 닫는다. 자동 key 생성·plaintext fallback이 없다.
- [ ] Android/iOS 실제 번들에서 암호화 historical v1→v2, close/reopen, wrong-key 거부, 일반 SQLite 읽기 거부를 증명한다.
- [ ] D01 Recovery UI/정상 화면·알림 차단 통합 검증이 있다. 호출 오류를 무조건 rollback으로 표시하지 않는다.
- [ ] schema bump/snapshot/지원 경로 누락이 CI에서 실패한다. 생성 Dart는 커밋하지 않는다.
- [ ] DB Architecture 예시 최소 정정, 재현 명령/환경/commit/결과/한계를 issue와 PR에 기록한다.

**Root 답변:**

> Q3을 확정합니다. 고정 역사 commit의 schema1에서 독립 생성한 snapshot/DDL·합성 fixture와 provenance를 추적하고 현재v2 snapshot을 별도로 유지합니다. 미래 fixture가 현재 entity 직렬화에만 의존해 과거 필드 손실을 숨기지 않게 실제 과거 형태/값을 고정하세요. 일곱 표의 durable 필드와 관계·인덱스·제약·기본값, 완료/진행 facts/score, 한글/null/타임존 경계를 포함하며 fresh/upgraded v2 의미적 동등성을 비교합니다. 생성 Dart는 ignore 유지, 의도된 SQL/JSON/합성 fixture만 추적합니다. schema bump마다 snapshot/지원 경로 누락이 CI에서 실패하는 재현 가능한 검사를 포함합니다. 기존 역제거 테스트는 보조 증거로 유지할 수 있습니다. 미래 버전 downgrade 경로도 다음 문답에서 보존 거부 계약을 확정하겠습니다. 패키지 내부 근거는 locked version 파일/함수와 줄 위치를 명시해 주세요.

### Q4 — 실패와 중단의 실제 보존 증거

**Agent 질문:**

> D04 Q4: 실패·중단 검증의 완료 기준을 확정하겠습니다. 추천: (1) 실제 opener에서 미래 user_version, unsupported local predecessor, 비어 있지 않은 version0/부분 DDL 입력을 읽기만 하고 보존 거부하며 legacy server DB를 local v1로 추정하지 않습니다. (2) 각 DDL 전후, version 기록/commit 경계, SQLite FULL/read-only/locked/constraint 오류를 실제 파일에서 주입하고 연결을 닫은 뒤 독립 재열기로 schema/data/user_version/key identity 보존을 검사합니다. 단순 Future throw는 fault handling만 증명하며 SQLite rollback/암호화 검증을 대신하지 않습니다. (3) 실제 별도 process 종료 후 재열기로 v1 또는 완전 v2만 남는지 확인하되 power-loss 보장으로 확대하지 않습니다. (4) 파일 hash 전체 동일을 일반 rollback 기준으로 삼지 않습니다. 정상 WAL/journal 동작이 바이트 배치를 바꿀 수 있으므로 논리적 원본 내용/schema/version/key와 파일군 보존을 기준으로 하되 wrong-key/거부 경로는 불필요한 변경이 없음을 별도 확인합니다. (5) 실패는 D01 typed Recovery, normal UI·알림 시작 차단, 성공만 1회 준비 완료입니다. 암호화 파일 오류·disk full을 fake-only로 통과시키지 않고 모바일 native 검증과 정확히 구분합니다. 이 정도를 D04 필수 AC로 할까요?

**Root 답변:**

> Q4를 확정합니다. 미래 버전/지원하지 않는 predecessor/비어 있지 않은 version0/이미 부분 DDL인 입력을 현재 schema로 조용히 낮추거나 수선하지 않고 보존 거부합니다. legacy server DB를 local v1로 추정하지 않습니다. 실제 파일에서 DDL·version·commit 실패, FULL/read-only/locked/constraint를 주입하고 독립 reopen으로 논리적 schema/data/version/key identity와 파일군 보존을 검사합니다. 파일 전체 hash 일치를 모든 rollback의 필요조건으로 삼지 않는 이유도 기록해 주세요. 별도 process kill 재열기는 v1 또는 완전v2만 허용하고 power-loss 내구성으로 확대하지 않습니다. fake-only 실패 주입, host SQLite, 실제 모바일 암호화 검증의 증거를 분리하며 D01 typed Recovery/정상 UI·알림 차단을 실제 통합합니다. 지금 원래 문답 4개 및 root/agent 보충 전체, locked dependency 내부 근거, 재평가된 현재 문제를 상세 D04.md로 작성·동결하세요. 구현 중 아직 미지정인 fault injection 방식은 각 실제 SQLite 오류가 발생했음을 확인하는 검증 명령/코드와 함께 결정하도록 명시하고, 어려운 테스트를 단순 throw로 대체하지 않습니다.

**Root 최종 구현 경계 보충:**

> 구현 시 주의할 추가 경계도 문서에 넣어 주세요. onUpgrade 안의 DDL만 transaction으로 묶고 Drift의 user_version 갱신이 바깥에서 일어나면 DDL commit→version write 실패 gap이 남습니다. 동일 원자 경계에서 schema와 version이 함께 확정되는 실제 방법을 locked Drift executor 경계로 검증해야 합니다. 외부 호출이 오류를 반환했더라도 authoritative reopen이 완전v2이면 'v1으로 rollback됨'이라고 표시하지 않고 현재 사실에 맞는 Recovery/재시도로 처리합니다. 이 사항은 구체 구현을 선결하는 것이 아니라 Q4의 v1 또는 완전v2 AC를 실질적으로 충족시키기 위한 경계입니다.
