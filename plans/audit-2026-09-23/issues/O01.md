# [O01][P1] 개발·아키텍처·출시 문서를 local-only 제품과 일치시키고 두 모바일의 새 checkout 실행 경로 검증

## 문제와 기대 결과

새 개발자가 README를 따르면 현재 소스에 없는 API 환경 파일과 Firebase 설정을 준비하고 Web을 제품으로 실행하게 된다. 출시 담당자는 동일한 Release Checklist 안에서 “제품에 API/Firebase 설정이 없어야 한다”와 “Firebase 설정·로그인·FCM 등록을 확인하라”를 동시에 요구받는다. generated Dart를 commit하라는 문장도 저장소의 현행 ignore 정책과 충돌한다.

현행 개발·아키텍처·출시 진입 문서는 Android/iOS local-only 제품의 실제 코드와 검증 수준을 설명해야 한다. 과거 서버 제품 자료와 실행 증거는 지우거나 현재 성공으로 재해석하지 않고 역사 자료로 구분한다. 새 문서만 따라 깨끗한 checkout에서 두 모바일의 정상 진입·일정 저장·실제 프로세스 재실행을 재현한 뒤 완료한다. 문서 변경 자체는 앱 수정, 실제 기기 QA, 서명 릴리스, 스토어 제출·승인·배포 완료가 아니다.

- 우선순위: P1. 개발 시작 실패, 잘못된 비밀 설정 요구, 제거된 제품 기능을 전제로 한 출시 판단을 유발한다.
- 원 감사: `docs/App-Improvement-Audit-2026-09-23.md:141`, 총 64개 감사 항목 중 O01.
- 고정 조사 소스: [`aa2fda68fbf3ac431738de3792f5d587d35b6dda`](https://github.com/DevKor-github/OnTime-front/tree/aa2fda68fbf3ac431738de3792f5d587d35b6dda).
- 이 이슈 작성은 source/document read-only 조사와 root 대리 문답이다. 이 이슈의 새 checkout·모바일 실행·문서 검사·외부 문서 게시를 이미 수행했다고 주장하지 않는다.
- A08의 현재 schema 3 작업은 조사 소스의 출시 사실에 포함하지 않는다. 고정 소스 `lib/core/database/database.dart:55`는 schema 2다. 구현 시 새 SHA를 고정해 다시 확인한다.

## 적용할 문서 계약과 책임

1. `README.md`는 새 개발자의 단일 시작 경로다. 제품 지원은 Android/iOS, Web/desktop 폴더 존재는 제품 지원 근거가 아니다. Widgetbook의 dependency install/codegen/Chrome/Hosting 경로는 별도 catalog 절로 구분한다.
2. `docs/Architecture.md`는 해당 SHA의 실제 소스 구조·데이터 흐름을 설명한다. encrypted Local Data Store, Local Profile, startup Recovery, domain workflow/receipt, OS notification/alarm, durable 데이터와 재구성 가능한 runtime의 경계를 실제 경로에 연결한다. 미구현 목표는 명시적으로 구현 대기다.
3. 현행 release/smoke 문서는 요구사항·절차와 실행 결과를 구별한다. “필수 확인”과 “확인 완료”를 혼용하지 않는다. 실제 source, artifact digest, build/OS, 명령, 시각, 결과, 증거 링크가 있는 행만 통과다.
4. `CONTEXT.md`는 용어집, ADR은 정책 결정, 날짜 있는 QA 자료는 당시 증거다. CONTEXT에 파일·명령·test count·구현 메모를 추가하지 않는다. 중복 Schedule/Preparation/Preparation Step 정의를 발견했지만 O01에서 새 의미를 만들거나 전체 용어집을 임의 재설계하지 않는다.
5. historical/superseded 문서는 적용 시점, 현재 제품에는 적용되지 않는 범위, 대체 정책/현행 문서 링크를 첫 부분에 둔다. 과거 원문과 실제 증거는 보존한다. 기존 경로 보존을 우선하고 이동이 꼭 필요하면 원래 위치에 명시적 대체 링크를 둔다.
6. 현재 문서가 인용하는 정책과 코드가 다르면 코드의 부족함을 숨기지 않는다. 정책상 목표·현재 동작·연결 이슈·검증 대기를 함께 적는다. 아직 없는 기능을 문장만 바꿔 현재 기능으로 만들지 않는다.

1. 고정 조사 SHA와 구현 시작 SHA를 기록하고 `git ls-files '*.md'` 기반 inventory를 생성한다. 현재 링크 그래프에서 README→setup→architecture→release→smoke로 실제 독자가 이동하는 경로를 먼저 검토한다.

3. current 문서를 고치고 historical/pending/dated 표지를 추가한다. 경로를 유지하고 모든 대체 링크가 실제 존재하는지 확인한다. 소스 코드 예시를 실제 코드처럼 소개한다면 해당 SHA에서 존재하고 의미가 일치해야 한다. 교육용 예시는 그 사실을 명시한다.

   - encrypted durable DB는 source of truth이고 device-bound key와 Backup Password는 다르다. 복원은 검증된 backup으로 교체이며 실행 중 timer/OS registry를 백업 데이터로 소개하지 않는다.

   - debug transport/Widgetbook Hosting과 product release boundary를 구분한다.
5. 기존 generated checker를 재사용하고 가벼운 docs 검사를 추가/연결한다. current Markdown의 local file·anchor와 현재 소스 인용·명령 파일 존재를 검사하되 임의 코드블록 실행을 하지 않는다. 파일명 대소문자·경로 URL 인코딩·헤딩 중복 anchor·historical 링크 예외를 명시한다. 날짜 증거의 옛 경로는 명시적 historical 문맥/고정 commit 링크로 처리한다.

## 명령과 검증 기록

최종 README에는 실제 실행한 순서와 Android/iOS별 전제 조건을 기재한다. 아래는 구현 시 검증할 명령 집합이며 이 이슈 작성에서 실행 완료한 명령이 아니다. Flutter SDK 버전 3.44.4/Dart 3.12.2를 기록하고 `pubspec.yaml`의 Dart 최소 제약과 동일 개념으로 서술하지 않는다.

```sh
flutter --version
dart --version
flutter doctor -v
flutter pub get
dart run build_runner build --delete-conflicting-outputs
dart run tool/check_generated_dart_policy.dart
dart run tool/check_local_only_boundary.dart
flutter analyze
flutter test --coverage
dart run tool/check_coverage.dart --min=80
flutter devices
flutter run -d <new-owned-android-device-id>
flutter run -d <new-owned-ios-simulator-id>
git diff --check
git status --short
```

`<...>`는 사용자가 실제 나열된 device ID로 치환할 값임을 설명한다. 첫 install 시 네트워크가 필요한 toolchain/package fetch와 앱 runtime network-free 계약은 다르다. pub get 후 lock diff가 있다면 locked 재현 성공으로 처리하지 않는다. 같은 source·같은 명령·환경의 검증 가능한 CI 결과를 재사용할 때는 run/attempt, 실제 checkout SHA, 결과/로그를 연결한다. 오래된 run 이름이나 다른 synthetic merge의 성공을 현재 성공으로 사용하지 않는다.

서명 release APK/AAB/IPA 명령은 필요한 signing 입력 이름과 안전한 주입 경로만 설명한다. debug emulator/simulator 재현은 서명 release/실제 물리 기기/Play App Signing/스토어 처리 증거가 아니다. O01을 이유로 실제 signing/upload/rollout 또는 wiki publish를 실행하지 않는다. Widgetbook은 별도 디렉터리 dependency/codegen/build/run 순서로 검증하고, 확인하지 못한 경로는 미검증으로 표시한다. 코드베이스의 실제 플랫폼 최소 버전은 native 설정에서 확인하며 오래된 commented Podfile 값을 제품 최소 지원의 근거로 쓰지 않는다.
