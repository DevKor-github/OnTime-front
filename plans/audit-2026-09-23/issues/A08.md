# [P1][A08] 일정·장소·준비 저장을 원자화하고 일관된 조회·충돌·재시도 계약을 보장

## 문제와 사용자 영향

일반 일정 생성/수정은 일정과 장소를 먼저 저장한 뒤 준비 단계를 별도로 저장한다. 그 사이 알림 reconciliation이 시작하고, 각 저장의 backup revision도 따로 증가한다. 준비 또는 revision 쓰기가 실패하면 일정 일부만 바뀌었는데 화면은 전체 저장 실패를 안내한다. 재시도는 이미 존재하는 일정 ID와 충돌할 수 있다. 현재의 repository stream은 revision 저장보다 먼저 새 준비를 발행하기도 한다.

쓰기 transaction만 추가해서 끝낼 수 없다. 알림 계획과 편집 초안은 일정·기본 준비·개별 준비를 여러 await로 읽으므로, 다른 정상 commit 사이에 이전 일정과 새 준비를 섞을 수 있다. 오래 열어 둔 편집 화면은 이미 시작/완료된 일정의 보호 필드를 기본값으로 덮을 수 있다. A08은 **한 사용자 저장 의도의 durable aggregate commit과 그 aggregate의 일관된 읽기**를 책임진다. C01은 이를 호출하는 workflow 및 저장 성공/후속 delivery 실패 결과를 책임진다.

우선순위 **P1**. 데이터 부분 저장과 잘못된 알림 시각을 방지한다. 구현 순서는 **C01 이후 A08**이며, A04/A07 및 A14/A15/D03의 선행 계약을 재사용한다. 아래는 합의된 구현 명세이며 구현·회귀 테스트 완료 보고가 아니다.

## 용어와 범위

- **Schedule**, **Place**, **Preparation**, **Default Preparation**, **Custom Preparation**, **Preparation Mode**는 CONTEXT의 기존 의미를 쓴다. 일정 저장은 알림 등록과 같은 성공 경계가 아니다.
- **Recurring Schedule Preparation**은 반복 일정 소유의 독립 준비이며 default/template 원본을 직접 바꾸지 않는다. **Schedule Occurrence**와 series 전체를 혼동하지 않는다.
- **Local Data Store**가 durable 값의 유일한 권위다. 수동 stream/cache는 최신 DB aggregate를 조합하는 권위가 아니다.
- **Backup Freshness**는 실제 durable 변경의 commit과 일치한다. 알림 재등록 자체와 no-op 저장은 사용자 데이터 revision 증가 이유가 아니다.
- ADR 0022(단일 encrypted Drift), 0027(일관 Backup Cutoff), 0035(단조 durable revision)를 적용한다. transaction/version/receipt는 일반 구현 용어이므로 glossary에 추가하지 않는다. 새 전역 ledger나 아키텍처를 확정하지 않았으므로 ADR를 임의 추가하지 않는다.

포함: 일반 create/edit aggregate port·data transaction·읽기 snapshot, 준비 출처와 소유권 안전한 전환, revision/no-op, stale edit/conflict 및 안정된 저장 의도, 반복 기존 transaction의 동일 계약 검증과 필요한 최소 보완, C01 workflow 통합에 필요한 typed 결과/편집 기준 전달, 실제 DB와 사용자 저장 경로 회귀 검증.

범위 밖: A07 준비 시작 전이 자체의 재구현, A04 프로필·점수 전체 재설계, A09 restore 전체 프로토콜, D03 reset/OS journal, C03 전반적 N+1 성능 개선, 새로운 반복 기능, 일반 템플릿 편집 정책, 전역 event sourcing/동기화/서버. 정합성을 위해 필요한 batch read는 허용한다.

## 확정 계약

### 1. 원자적 쓰기와 소유권

1. 한 일반 일정 저장은 Schedule의 사용자 편집 값, 일정 소유 Place 변경, 최종 Preparation Mode·참조/owned steps, 필요한 이전 owned 데이터 정리, durable revision을 하나의 DB transaction으로 commit한다.
2. 어떤 단계에서 실패해도 장소·일정·준비·출처·revision 전부 이전 상태로 rollback한다. 생성 실패는 일정이나 장소/준비 orphan을 남기지 않는다. 수정 실패는 이전 준비를 온전히 보존한다.
3. 참조 mode의 의미를 보존하고 default/template 원본은 변경하지 않는다. 편집한 custom 준비만 해당 일정의 독립 복사본으로 소유한다. 공유 Place의 이름을 다른 일정까지 변경하는 upsert를 허용하지 않는다.
4. custom→default/template 등 유효한 mode 전환과 이전 owned steps/definition 정리는 같은 transaction에서 참조 안전하게 수행한다. 다른 일정/회차가 참조하는 준비·장소는 삭제하지 않는다. 이미 비어 있는 custom과 default fallback은 같은 의미로 취급하지 않는다.
5. 사용자 편집 경로는 소유한 필드만 부분 UPDATE한다. startedAt/finishedAt/outcome/scoreContribution/frozen/recurring identity는 각 목적 경로 소유다. 편집 submission의 기본값이 이 필드를 초기화해서는 안 된다.
6. 실제 사용자 aggregate 변경당 revision 정확히 1회. 실패/동일 값/같은 의도의 재시도는 추가 revision·durable timestamp 변경이 없다. A04의 export metadata·first timestamp 보존을 유지하며 중첩 DAO/helper의 이중 증가를 막는다.
7. Drift watch의 commit 경계와 수동 stream 발행 경계를 구분한다. 성공 stream과 C01의 후속 delivery 요청은 commit 후에만 실행한다. OS query/schedule/cancel/reconcile을 DB transaction 안에서 await하지 않는다.
8. 반복 생성/이번 회차/이후 회차 수정은 기존 transaction을 재사용한다. rule·owned preparation·exclusions·split/detach·회차 materialization·revision이 부분 commit되지 않는지 검증하고 필요한 지점만 보완한다. 시작·완료·frozen 회차 및 명시적 overrides 보존, daily/weekly/monthly/count/until 정책과 60개 알림 capacity를 유지한다.

### 2. 편집 충돌과 멱등 재시도

1. 편집 초안은 일관된 aggregate 읽기의 기준값/버전 및 data generation을 가진다. 저장 transaction 내부에서 최신 상태와 비교한다. 전역 dataRevision만 비교해 무관한 일정의 편집을 충돌로 취급하지 않는다.
2. 다른 편집, 시작/완료, 삭제, restore/reset 세대 변경으로 초안의 근거가 달라졌으면 typed conflict/stale 결과로 거부한다. 초안을 보존하고 현재 데이터를 재조회·재검토하도록 한다. 마지막 쓰기 승리나 자동 upsert로 조용히 덮지 않는다.
3. 시작/완료된 일정을 일반 편집 가능하게 만드는 새 정책은 추가하지 않는다. 화면에 편집 버튼이 보였더라도 commit 시점의 기존 보호 조건을 적용한다. 반복 변경은 해당 segment/영향 회차/materialization의 현재 상태를 transaction 안에서 확인한다.
4. 한 저장 의도는 안정된 mutation identity를 유지한다. 같은 의도의 동시/중복 요청은 한 commit·한 revision으로 끝나고, 진짜 rollback 뒤에는 같은 초안으로 재시도가 가능하다.
5. 같은 ID에 다른 입력의 create는 typed conflict다. 일반 insert 충돌을 무조건 성공으로 바꾸거나 반복 series exists를 무조건 성공으로 처리하지 않는다.
6. commit receipt를 caller가 받지 못한 뒤 앱이 재시작되어도 durable 근거로 같은 의도임을 확인할 수 있어야 한다. 내용이 같다는 것만으로 이전 성공을 추측하지 않는다. 중간 다른 편집, 삭제·재생성(ABA), 새 generation의 동일 ID를 과거 요청으로 변경하지 않는다.
7. semantic 동일 update는 no-op이다. 단계 ID를 불필요하게 새로 만들고 revision을 증가시키지 않는다. 기존 owned 단계 ID를 안전하게 유지하며, default/template에서 독립 custom으로 복사하는 실제 소유권 변경은 구분한다.
8. 최소 aggregate version/receipt 설계를 택하고 새 전역 mutation ledger를 선행 가정하지 않는다. durable 멱등성에 schema 변경이 필요하면 해당 migration과 기존 DB/backup 호환성 검증은 A08 완료 조건에 포함한다. D04를 이유로 미완성 호환성을 남기지 않는다.

### 3. 유효성 및 일관된 읽기

1. 잘못된 mode/reference/steps 조합, 존재하지 않는 대상, 잘못된 owned 참조는 transaction에서 전체 거부한다. empty custom은 새 유효 상태로 저장하지 않는다. 기존 default fallback 의미는 유지한다.
2. 현재 preparation form은 단계 1개 이상과 유효한 이름/시간을 요구한다. UI 시간 입력은 1–1440분이며 반복 repository의 내부 검증은 0분을 허용하는 차이가 있다. A08은 UI 유효성 우회에 의한 부분 저장을 막되, 기존/복원 데이터의 정당한 읽기를 새 규칙으로 일괄 파괴하지 않는다. 구현 시 사용자 저장 validator와 legacy/backup decoder를 분리하여 기존 유효 계약을 명시하고 회귀 검증한다.
3. 알림 planning용 일정+실제 준비 및 edit baseline은 한 DB snapshot 또는 동등한 일관 aggregate read port로 얻는다. 여러 await 사이 다른 정상 commit이 있어도 이전 전체 또는 새 전체여야 하며 혼합 값이면 실패다.
4. 기존 materialization transaction이 끝난 뒤 immutable snapshot을 만든다. 그 snapshot 밖에서 OS 작업을 한다. 수동 preparation stream의 현재 값을 authoritative join으로 사용하지 않는다.
5. 저장 중 backup snapshot도 aggregate의 이전 전체 또는 새 전체를 담아야 한다. 백업 암호화/외부 파일 저장 전체를 DB lock 안에 넣지 않는다.
6. 원자성은 UI 호출 순서나 프로세스 메모리 singleflight만으로 주장하지 않는다. 실제 Drift transaction·repository 조회와 실패 주입이 증거다.
