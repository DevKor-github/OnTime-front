# [P1][R04] PR·Android 배포 품질 검사를 재사용하고 검증한 AAB와 실제 전송 바이트를 연결

## 문제와 결과 목표

일반 PR은 coverage 80%와 Android release APK manifest 검사를 통과해도, 수동 Play 배포는 그 검사를 동일하게 요구하지 않는다. 두 배포 workflow가 각각 분석과 테스트를 복제하고 별도 AAB를 만들어 전송하므로 **같은 소스의 검사가 성공했다는 사실과 전송하는 바이너리를 검증했다는 사실**이 연결되지 않는다.

R04는 PR·push·dispatch·두 Android 후보 배포가 동일한 품질 정의를 사용하게 하고, 그 품질을 통과한 정확한 소스로 만든 AAB를 검증한 뒤 **검증한 바이트만 업로드 경계에 도달하도록** 만든다. 단순 coverage 명령 추가에 그치지 않으며 기존 테스트 전체를 배포 단계에 또 복제하지 않는다.

- 실제 root 문답 3개와 마지막 보충 정정을 아래 원문으로 보존한다. root는 사용자에게서 위임받은 결정자로 답했다.

## 공식 문서로 확인한 기술 경계

- 저장소 내부 reusable workflow 상대 참조는 caller와 같은 commit의 정의를 사용한다. caller/checkout SHA를 기록하고 movable branch 이름으로 검증 소스를 다시 선택하지 않는다. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
- reusable workflow의 environment secret 동작과 caller secret 전달은 같지 않다. 품질 workflow에 environment 또는 `secrets: inherit`를 넣지 않고 privileged job을 분리한다. [GitHub reuse workflows](https://docs.github.com/en/enterprise-cloud%40latest/actions/how-tos/reuse-automations/reuse-workflows)
- upload-artifact v4 artifact는 immutable이며 job 간 전달이 가능하다. download의 digest 불일치는 문서상 경고이므로 그 경고만으로 차단을 보장하지 않고 파일 SHA256을 독립 검사한다. [GitHub artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data)
- bundletool은 AAB에서 APK set을 생성해 지정 기기에 설치할 수 있다. 서명정보 미지정 시 debug key를 시도하므로 검증 서명을 명시한다. [Android bundletool](https://developer.android.com/tools/bundletool)
- AAB upload key와 Google Play의 사용자 배포 app signing key를 구분한다. 로컬 파생 APK 성공은 Play가 서명한 split/update 검증이 아니다. [Android app signing](https://developer.android.com/studio/publish/app-signing)

이 문서는 위 문서를 설계 근거로 읽었으며 해당 기능이 이 저장소에서 이미 실행된다고 주장하지 않는다. action/tool 버전 pin 전체 정비는 R06과 조정한다.

## 확정 계약

### 1. 하나의 품질 정의와 정확한 소스

1. PR/push/dispatch와 기존 internal(main)/closed(release/**·hotfix/**) 경로가 같은 reusable quality entrypoint를 호출한다. 구성상 하위 workflow로 나누더라도 필수 suite/판정 정의는 하나이고 wrapper별 느슨한 사본을 두지 않는다.
2. Flutter **3.44.4**, Dart **3.12.2**, Java17 및 저장소 lockfile에 맞춘 의존성, generator, generated policy, local-only policy, tracked drift, analyze, full unit/widget coverage80, source manifest/negative contract를 포함한다. R02가 제공하는 양 모바일 build/native/core smoke도 동일 소스 gate에 연결한다.
3. `git rev-parse HEAD`, PR head/base/실제 merge SHA, event, workflow/run/attempt, lockfile hashes와 toolchain을 명시한다. dispatch가 선택한 SHA는 실행 내내 고정한다. 실행 중 branch가 움직여도 checkout을 latest로 바꾸지 않는다. PR synthetic merge 성공을 head 또는 main 성공으로 바꿔 적지 않는다.
4. 일반 PR에는 signing/store secret을 제공하지 않는다. fork 승인을 기다리는 상태는 미실행이며 통과가 아니다. `pull_request_target` 또는 privileged `workflow_run`으로 untrusted 코드를 우회하지 않는다.
5. deploy는 같은 run DAG의 필수 결과가 모두 성공했을 때만 서명/build 단계로 진입한다. 다른 run의 이름이 같은 green 또는 과거 성공만 보고 통과시키지 않는다. 필수 suite/report/identity가 없거나 fail/skipped/cancelled/0 cases/dependency pending이면 업로드 불가다.
6. stable check 이름과 기존 PR 실행 범위는 유지하거나 R01 required-check 목록과 원자적으로 조정한다. R02가 정한 merge_group 경로도 재사용 가능한 정의를 사용한다. 전체 workflow skip/path-filter 때문에 필수 check가 사라지게 만들지 않는다.
7. 동일 run에서 품질 검사를 중복 실행하지 않는다. 후보와 정확히 같은 source/mode/toolchain의 재사용 가능한 build만 identity 검증 후 공유한다. 별도 main 후보 SHA의 검증 필요성을 중복이라며 생략하지 않는다.

**보충 정정:** 정상적인 ignored generated Dart 및 build 출력 생성 자체가 tracked drift는 아니다. 검증 소스·lock/generator 입력·tracked 파일 정책을 판정하며, 검증 후 소스/입력/실제 전송 바이트가 바뀌는 경우를 차단한다. ignored generated 파일은 계속 재생성하고 커밋하지 않는다.

### 2. 검증한 AAB에서 최종 전송까지

| 단계 | 필수 입력/검증 | 생산 비밀·허용 효과 |
|---|---|---|
| quality | 정확 SHA, lock/toolchain, 필수 suite/report 및 coverage | 생산 비밀 없음, 검사만 |
| signing/build | quality receipt, 동일 SHA/입력, 명시 versionName/versionCode | upload signing key만 필요한 단계에 제공; AAB 1회 생성 |
| candidate inspection | 실제 AAB package/version/signing certificate/SHA256, packaged manifest | 공개 certificate 식별자만 증거에 포함; 키·암호 없음 |
| AAB-derived smoke | 그 AAB digest로부터 bundletool APK set, 각 설치 split digest/device spec/검증 서명, T01 release-compatible core smoke | production 비밀 없는 소유 emulator, 명시 validation key, 실제 해당 binary 외부 native UI driver |
| final guard | 같은 run의 고유 artifact ID, AAB 파일 hash, source/inputs/version/cert, 필수 quality 및 smoke receipt | 불일치면 전송 경로 진입 금지 |
| upload | 검증한 bytes에 고정한 파일/stream, 허용 package/track | Play 권한만; 빌드·재생성하지 않음 |

- AAB 검사 후 별도 `flutter build apk`로 만든 binary를 테스트해 AAB smoke라고 하지 않는다. test용 main/channel/network 권한을 release에 추가해 다른 binary를 만들지도 않는다. T01 driver가 해당 release-compatible 경로를 지원하지 않으면 dependency pending이다.
- AAB→APK set→설치된 split의 관계를 기록한다. 원 AAB, 파생 APK, GitHub artifact archive의 digest는 서로 다른 값이며 혼동하지 않는다. app ID/version/ABI/OS/device spec/서명 종류를 포함한다.
- 전송 job은 AAB를 다시 빌드하지 않고 같은 run의 정확한 artifact ID를 내려받는다. 파일명·artifact 이름·latest successful만으로 선택하지 않는다. missing/expired/digest/source/lock/toolchain/version/certificate 불일치면 uploader 호출 **0회**다.
- 검사와 stream open 사이 파일 교체를 막는다. 구현은 검증된 복사본 또는 동등한 바이트 고정 방식을 사용하고, 전송하는 stream의 바이트가 검증된 바이트와 같음을 부정 테스트로 입증한다. 존재 확인 후 나중 path를 다시 여는 방식만으로 끝내지 않는다.
- candidate metadata가 합성되었거나 wrapper 출력에만 존재하는 상태로 통과시키지 않는다. 실제 AAB에서 읽은 package/version/cert를 예상 입력과 비교하고, 검증 결과의 SHA/identity도 교차 확인한다.
- local validation APK 서명은 Play App Signing과 다르다. 이 결과는 로컬 파생 candidate smoke이며 실제 Play 설치·동일서명 업데이트·사용자 배포 완료는 별도 T02/R07/R08 증거다.

### 3. 권한·재시도·진단

- quality에 생산 비밀0, signing/build에 upload signing만, smoke에 생산 비밀0, uploader에 Play credential만 제공한다. 기존 staging의 실제 보호 설정은 R05에서 확인한다. job 분리만으로 원격 환경 보호가 적용됐다고 하지 않는다.
- 키/암호/서비스계정 JSON/사용자 DB/앱 데이터는 로그·cache·artifact에 넣지 않는다. 필요한 임시 키는 가장 늦게 만들고 always cleanup한다. runner 강제 종료에서 cleanup hook 실행을 보장한다고 하지 않는다.
- source/workflow/run/attempt, artifact ID/file digest, lock/toolchain/version/cert 식별자, 필수 suite 및 coverage numerator/denominator/threshold, derived split/device metadata, 원본 결과/log hash, failure reason을 기계 판독한다. signing 종류와 `store_write_not_run`을 분리 기록한다.
- rerun은 원 실패와 새 attempt를 모두 보존한다. 같은 run 재실행도 실제 artifact identity와 필수 결과를 다시 확인한다. 다른 SHA면 전체 검증, 새 version 또는 rebuild면 새 candidate로 artifact smoke도 다시 한다. 단순 “latest green”은 재사용 조건이 아니다.
- R04는 자동 Play 재전송을 추가하지 않는다. version 중복·전송 후 응답 상실·commit 미확정은 R05/R07의 별도 멱등성/상태확인 경계이며 성공으로 추정하지 않는다.
- 입력 branch/package/track 허용 범위를 그대로 유지한다. 자동 production 배포 trigger나 tag 승격을 만들지 않는다. 현재 draft 전송과 사용자 공개 배포는 구분한다.

## 구현 순서와 실패 검증 행렬

1. 현재 workflow/check 이름·동일 소스/입력 정의를 고정하고 R02/T01/T02 entrypoint 및 필수 결과 schema 상태를 확인한다.
2. 기존 Flutter/Android 검사를 reusable 품질 정의로 옮겨 양 PR·deploy wrapper가 호출하게 한다. coverage80 및 tracked drift 어느 쪽도 잃지 않는다.
3. production secret 없는 quality, signing/build, AAB-derived smoke, final guard/upload를 분리하고 정확 artifact 전달을 연결한다.
4. 실제 최종 guard와 file-open/전송 경로를 공유하는 no-store 검증 entrypoint를 만든다. 합성 credential과 local fake transport로 sink에 도달한 bytes를 독립 캡처한다. 상위 job을 건너뛰고 success만 찍는 dry-run은 금지한다.
5. 아래 negative의 guard fixture와 실제 workflow 연결을 각각 검증한다. 실제 compiler/test 실패가 gate로 전달되는 R02 증거는 재사용하고, 별도 fixture 성공을 실제 원격 native 실패 run으로 부르지 않는다.
6. 원격 동일 SHA의 양 wrapper validation, 실제 AAB-derived smoke, artifact 다운로드/재해시를 수행한다. 생산 서명 경로 확인 여부를 별도로 기록한다. 실제 스토어 write는 이 설계의 실행 허가에 포함되지 않는다.
