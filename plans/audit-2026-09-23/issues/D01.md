# [P1][D01] 시작 실패를 DB 비의존 복구 화면으로 전달하고 재시도의 데이터 보존 보장

## 문제와 사용자 영향

현재 `main()`은 지역화 초기화, local lifecycle bootstrap, privacy cleanup, dependency registration을 완료한 뒤에야 `runApp`을 호출한다. secure storage 접근, 파일 삭제, preferences 작업 또는 초기화가 실패하면 기존 Recovery 화면도 만들어지지 않는다. 사용자는 빈 시작 화면에 남고, 실제로 어떤 단계가 끝났으며 무엇을 재시도할 수 있는지 알 수 없다.

단순히 최상위 catch 뒤 기존 App을 띄우는 것으로 해결되지 않는다. App은 정상 DI와 DB에 연결된 Bloc을 생성하고 notification lifecycle 처리를 시작한다. 기존 recovery 화면의 재시도도 AuthBloc 사용자 로드만 반복한다. 또 cutover marker가 없으면 현재 local-only DB까지 삭제하고, 기존 DB에 키가 없어도 `getOrCreate()`가 새 설치 키를 기록한다. 잘못된 시작 재시도가 데이터 보존을 해칠 수 있는 경로다.

D01의 결과는 **정상 DB·정상 DI에 의존하지 않는 최소 시작 화면에서 실패/진행 중 상태를 표시하고, 확인된 단계만 안전하게 재시도하며, 기존 DB·키를 임의 삭제하거나 새 데이터로 대체하지 않는 것**이다. 이미 사용자가 확정한 reset/restore의 남은 작업은 해당 작업의 소유권과 결과를 그대로 이어받는다. 손상 DB에서 백업을 실제 교체하는 전체 기능은 D02가 담당한다.

우선순위 **P1**. 조사 기준 SHA는 **`edfff97c4806fb2d154c324edf8965b1feb218e0`**이다. 병행 A14 WIP와 별개로 아래 startup/key/files/recovery 소스가 이 SHA에서 변경되지 않았음을 확인했다. 생성 DI 출력은 로컬 구조 조사에만 사용했으며 tracked 소스의 대체 근거나 커밋 대상이 아니다. 이 문서는 합의한 계획이고 구현·테스트 통과 보고가 아니다.

## 확정한 구현 계약

### 1. 먼저 표시되는 최소 shell과 단계별 결과

1. Flutter binding 이후 최소 shell을 실행하고 오류가 날 수 있는 locale/bootstrap/privacy cleanup/DI 초기화를 관찰한다. 이 shell 자체가 정상 AppDatabase, GetIt product graph, AuthBloc, ScheduleBloc, product router를 요구해서는 안 된다.
2. 지역화 초기화 자체가 실패해도 한국어·영어 안전 문구를 표시할 수 있어야 한다. 앱 기본 언어 결정은 사용 가능한 OS locale에 기반하며 DB preference 읽기를 화면 표시의 필수 조건으로 만들지 않는다. 전체 앱 번역(U05) 완료와는 별개다.
3. 결과는 최소한 현재 단계, 실제 실행 중/terminal 실패/후속 정리 미완료/완료, 명시적 retry 가능 여부, operation identity와 currentness를 구별한다. 구체 클래스 이름이나 범용 workflow framework를 이 이슈가 강제하지 않는다.
4. 정상 준비가 완료되기 전에는 정상 App, 일정 Bloc, 권한 교육, schedule reconciliation을 생성하지 않는다. 오류를 무시하고 빈 Local Profile/onboarding으로 우회하지 않는다.
5. 복구를 위한 명시적 cleanup과 정상 product notification scheduling은 다르다. D03/A09가 승인된 의도를 이어가는 cleanup은 제한 상태에서 가능하지만 일반 future schedule 등록/준비 자동 시작은 금지한다.
6. 원문 예외, secure storage 값, 파일 경로, 일정·준비 원문, 키/암호를 UI나 로그에 출력하지 않는다. allowlisted 안전 오류 코드와 단계에 따른 문구를 사용한다. raw 예외에 임의 redaction을 적용했다는 것만으로 안전하다고 단정하지 않는다.
7. cutover/reset/restore가 일부 진행된 상태에 일률적으로 ‘아무 데이터도 삭제되지 않았습니다’라고 표시하지 않는다. 확인된 완료 단계와 남은 작업만 설명하고, 보존 여부가 불확실하면 이를 보존 완료라고 보고하지 않는다.

### 2. 단순 시작 재시도와 이미 확정된 파괴 작업 구별

| 관측 상태 | 허용 동작과 제한 |
|---|---|
| 파괴 작업이 시작되지 않은 bootstrap/locale/DI 일시 실패 | 안전한 원인 범주와 명시적 시작 재시도. 실패를 자동 reset으로 치환하지 않는다. |
| 시작 작업이 아직 반환하지 않음 | 진행 단계와 아직 끝나지 않았다는 사실 표시. 중복 작업/새 reset을 시작하지 않는다. 앱 다시 열기 안내는 성공·취소 보장이 아니다. |
| D03에 저장된 명시적 reset intent가 미완료 | 기존 reset engine/journal의 남은 단계만 재개. 새 profile, 정상 App, 중복 destructive confirmation 금지. |
| A09의 restore DB commit 이후 cleanup marker가 미완료 | 복원 완료 사실을 유지하면서 old runtime/delivery cleanup을 재개. DB 교체를 다시 실행하거나 원본으로 rollback됐다고 표시하지 않는다. |
| 일반 scheduling ownership/unknown intent만 존재 | reset 의도를 추정하지 않는다. A14/A15/D03의 일반 delivery 복구 계약을 사용하며 이 사실만으로 DB 삭제/전체 앱 차단 정책을 새로 만들지 않는다. |
| 기존 encrypted store/key를 안전하게 열 수 없음 | 보존한 제한 Recovery Mode. D02의 검증 백업 교체와 C01/D03의 명시적 reset 결과를 같은 경계로 연결한다. |

reset/restore의 단계와 허용 행동은 D03/A09의 권위 있는 journal/marker·실제 결과에서 가져온다. 화면마다 두 번째 cleanup engine을 만들거나 prefs를 일괄 지워 evidence를 없애지 않는다. D03의 필수 pre-runApp 복구 연결을 먼저 구현할 수 있으나 이것만으로 D01 전체를 완료로 처리하지 않는다.

### 3. cutover와 key/store 생성의 최소 데이터 보존 guard

- marker 읽기 실패는 실제 부재와 다르다. secure storage 실패를 null로 치환하거나 실패 뒤 cleanup을 진행하지 않는다.
- cutover marker가 없더라도 기존 local-only DB, SQLite sidecar, 기존 설치 키, reset/restore 진행 증거가 있으면 신규/legacy-only 설치로 추정하지 않는다. 보존한 채 제한 복구로 들어간다.
- 기존 store 열기와 증명된 새 store 생성 경로를 구별한다. 기존 DB/sidecar/중단 operation 증거가 있을 때 키 missing/invalid/unreadable이면 자동 키 재발급, 빈 profile 생성, 파일 덮어쓰기/삭제를 하지 않는다.
- 0바이트 파일, key-only, file-only도 증거 없이 안전한 새 설치나 삭제 가능한 쓰레기로 단정하지 않는다. 신규 생성 중단을 재개하려면 확인된 생성 소유권이 필요하다. 그 근거가 없으면 보존한다.
- 정말 신규 설치 또는 완전히 끝난 명시적 reset이라는 근거가 있을 때만 새 DB·키·profile 생성을 허용한다. 파일을 먼저 만든 다음 ‘파일 존재’만 보고 새 설치/기존 설치를 판정하는 순환 구조를 없앤다.
- 신규 생성과 완료 marker의 crash gap은 실제 상태 조합으로 테스트한다. 새 generic journal을 무조건 추가한다는 결정이 아니며, 선행 D03/A09의 적절한 ownership 계약과 기존 저장 상태로 안전하게 구별하는 구체 방법을 구현 시 명시한다. 증거 없이 성공 marker를 써서 불일치를 숨기지 않는다.
- 검증된 legacy-only 조건에서만 ADR 0015/0033의 cleanup을 멱등적으로 재개한다. 기존 local-only 사용자 데이터를 legacy cleanup 대상으로 확대하지 않는다. 이 판단의 조건과 근거를 코드/테스트에 남긴다.
- 이 guard는 재시도의 비파괴성을 위한 D01 필수 범위다. 손상 store를 살리는 복원/파일 교체(D02), 전체 cutover 재설계, 과거 서버 데이터 이관으로 확대하지 않는다.

### 4. 단일 startup attempt, 대기와 자원 수명

1. startup attempt에는 한 소유자가 있다. double tap/중복 retry는 진행 중 결과를 공유하거나 명확한 busy 결과로 받되 bootstrap/DI/cleanup을 중첩 실행하지 않는다.
2. 관찰 timeout은 화면 상태를 ‘아직 완료되지 않음’으로 바꿀 뿐 실제 native/파일 Future 취소 또는 다음 attempt 시작 허가가 아니다. terminal 또는 안전한 정리 경계 전에는 두 번째 bootstrap/DI/reset을 실행하지 않는다.
3. 대기 임계치는 이유가 있는 구현 상수로 정하고 경계 테스트를 둔다. 제품 완료 보장 시간처럼 표시하지 않는다. 영원한 spinner만 남기지 않고 실제 진행 단계와 가능한 행동을 표시한다.
4. 부분 DI 등록 실패로 만들어진 DB handle, repository subscription, timer/listener/Bloc 등 attempt 소유 자원을 실제로 dispose한다. 단순 `getIt.reset()` 호출 여부가 아니라 시작된 자원이 종료되는지를 검증한다. 기존 실패 graph 위에 두 번째 graph를 겹치지 않는다.
5. dispose/close도 실패할 수 있다. 안전한 정리가 확인되지 않으면 제한 복구 상태를 유지하며 성공 재시도로 넘어가지 않는다. dispose 오류 원문은 사용자에게 출력하지 않는다.
6. resume마다 자동 bootstrap 재시도나 오류 팝업/무한 polling을 만들지 않는다. 명시적 retry 또는 앱 재실행으로 진행한다. 기존 A12의 정상 App resume 처리와 혼동하지 않는다.
7. 최신 유효 attempt만 정상 App으로 한 번 전환한다. 오래된 결과가 이후 attempt/route/generation의 화면·DI·데이터를 바꾸지 못한다. 화면 dispose가 실행 중 작업의 부작용 소유권을 없애는 것은 아니다.
8. 단순 startup 일시 실패 동안에는 A12가 검증한 최소 notification tap을 준비가 끝날 때까지 보류한다. reset/restore는 A12/A09 세대와 identity 계약으로 무효화한다. 시작 준비 실패를 이유로 raw payload를 임의 영속화하거나 정상 화면 readiness를 우회하지 않는다.

**전담 에이전트 질문 원문**

> Q3: 재시도와 오래 걸리는 초기화의 수명을 어떻게 확정할까요? 현재 getIt.init은 부분 등록 뒤 실패할 수 있고 UserRepository 생성자는 즉시 DB watch subscription을 시작합니다. 권고: startup attempt 하나만 소유하는 coordinator에서 동일 재시도는 in-flight 결과를 공유/거절하고, 관찰 대기 시간 초과는 화면을 '아직 완료되지 않음'으로 바꾸되 native/파일 작업이 취소됐다고 처리하지 않습니다. 기존 작업이 terminal/안전하게 정리되기 전 두 번째 bootstrap·DI·reset을 시작하지 않습니다. 실패한 attempt의 DI/subscription/timer/DB handle을 명시적으로 dispose한 후 재구성하고 dispose 실패도 recovery로 남깁니다. resume마다 자동 bootstrap 반복은 금지하고 명시적 재시도 또는 앱 재실행으로 진행합니다. A12의 유효한 최소 notification tap은 단순 startup 일시실패 동안 보류하고, reset/restore 세대 교체에는 무효화합니다. 성공은 최신 attempt 한 번만 정상 App으로 전환하며 늦은 결과는 새 화면/세대를 변경하지 않는 안입니다. 구체 대기 임계치는 제품 SLA로 고정하지 않고 구현 상수·이유·경계 테스트로 명시할까요?

**전담 에이전트 추가 조사 원문**

> D01 추가 조사 사실(아직 별도 질문 아님): open_database_native.dart:10은 DB 파일을 먼저 만들고 :12 getOrCreate를 호출하며, InstallationKeyStore:21-40은 기존 DB 유무와 무관하게 키 null이면 새 키를 씁니다. 따라서 D01 readiness guard 구현은 기존 DB+missing key와 정말 새 설치를 구분해야 합니다. 단순히 marker가 있다고 DI/DB를 열면 보존해야 할 설치 키 증거를 덮을 수 있습니다. Q3 답 후 이 guard의 최소 경계까지 한 번 더 확정하겠습니다.

**root 답변 원문**

> Q3 확정합니다. startup attempt 단일 소유자가 중복 호출을 묶고, timeout은 관찰 상태만 바꾸며 실제 작업 취소나 재시작 허가로 취급하지 않습니다. terminal 또는 안전한 정리 전에 두 번째 bootstrap/DI/reset을 시작하지 않습니다. 부분 DI와 시작된 subscription/timer/DB handle을 실제로 dispose하고, 정리 실패도 제한 복구 상태로 유지합니다. resume 자동 반복은 금지하고 명시적 재시도나 앱 재실행을 사용합니다. 단순 일시 실패 중 최소 알림 탭은 A12 방식으로 보류하지만 reset/restore는 세대 무효화합니다. 최신 attempt만 한 번 정상 App으로 전환합니다. 대기 임계치는 이유가 있는 구현 상수와 경계 테스트로 정하고 완료 보장 시간처럼 표시하지 않습니다. 무한 로딩 대신 아직 진행 중인 단계와 가능한 행동을 정확히 표시해야 합니다. 충분하면 전체 문답과 현재 근거를 포함한 본문을 작성하세요.

### Q4 — 기존 store와 신규 DB/키 생성의 구별

**전담 에이전트 질문 원문**

> Q4(마지막, 키 보존 guard): 추가 조사된 기존 DB+키 null 경로 때문에, startup readiness와 open DB 경계에서 '기존 store 열기'와 '증명된 새 store 생성'을 분리할까요? 권고: 기존 DB 또는 SQLite sidecar/중단 operation 증거가 있으면 키 null·읽기 실패·형식 오류 모두 자동 새 키 생성/빈 profile 생성을 금지하고 원본 보존 recovery로 보냅니다. 빈 파일도 안전한 새 설치라고 추정하지 않습니다. 새 설치나 완료된 명시적 reset이라는 근거가 있을 때만 DB/키 신규생성을 허용하고, 신규생성 중 중단된 key-only/file-only 상태는 확인된 생성 ownership 없으면 보존합니다. D01에서 guard+안전한 retry만 구현하고 D02에서 실제 손상 DB 백업 교체를 담당합니다. 이 최소 guard 없이는 Q1/2의 '재시도가 데이터를 보존'한다는 AC가 현재 getOrCreate에 의해 깨질 수 있어 확정이 필요합니다.

**root 추가 조사에 대한 보충 답변 원문**

> 추가 사실에 대한 최소 경계도 확정합니다. 기존 local DB가 있는데 키가 없거나 읽기에 실패하면 getOrCreate로 새 키를 기록하지 않고 원본 DB를 보존한 제한 복구로 보냅니다. 정말 새 설치인 경우에만 신규 키/DB를 만듭니다. DB 파일을 먼저 만들어 신규 설치 판정을 바꾸는 현재 순서를 함께 고려해야 하며, 0바이트 파일도 증거 없이 안전한 삭제 대상으로 단정하지 않습니다. 파일 존재·키 존재/조회 실패·진행 marker 조합을 테스트하고 기존 사용자 데이터의 덮어쓰기를 막는 최소 guard에 한정하세요.

**root Q4 최종 답변 원문**

> Q4도 제안대로 확정합니다. 바로 전 보충 답변에 SQLite sidecar와 중단 operation 증거를 포함합니다. 기존 store 열기와 증명된 새 store 생성을 분리하고, missing/invalid/unreadable key를 자동 재발급하지 않습니다. 신규 설치 또는 완전히 끝난 명시적 reset이라는 근거가 있어야 신규 DB/키/profile 생성이 가능합니다. 생성 중단의 key-only/file-only는 확인된 생성 소유권 없으면 보존합니다. D01은 guard와 안전한 재시도, D02는 실제 복원/교체를 맡습니다. 네 질문과 보충 답변 원문 모두 기록해 본문을 동결해 주세요.


## 후속 D02 문답에서 확정한 통합 의존성

D02의 active-store manifest는 활성 DB·key-slot의 쌍과 store epoch를 선택한다. D01 startup은 이 manifest와 진행 중 restore journal을 정상 App 생성 전에 판독하고, 손상·불명확한 상태를 legacy fallback 또는 빈 DB 생성으로 우회하지 않는다. store epoch와 DB 내부 runtime generation은 별도 역할이며 정상 A09 restore는 manifest를 다시 쓰지 않는다. 이 문단은 root가 D02 실제 문답을 통해 확정한 후속 통합 사항이며 위 D01 네 문답의 원문을 대체하지 않는다. D02 상세 문답과 검증 계획을 연결해 구현한다.
