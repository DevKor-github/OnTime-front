## 확정한 선정 의미

**Nearest Upcoming Schedule**은 현재 instant 이상인 해석 완료 occurrence instant를 가진 미완료 일정 중 가장 이른 일정이다. `Today's Schedule`이나 현재 활성 `Schedule Preparation Session`과 다른 개념이다. root가 승인한 glossary 문구는 문답 부록에 있다. 구현세부를 CONTEXT에 넣지 않으며 이 가역적인 조회 정책을 위해 별도 ADR은 만들지 않는다.

1. 적격 후보는 `doneStatus == notEnded`이고 A10의 명시적 해석 결과가 resolved이며 `occurrenceInstantUtc >= nowUtc`인 일정이다. 동일 instant이면 안정적인 schedule ID 순서로 결정한다. DB iteration이나 Set 순서에 기대지 않는다.
2. Preparation Start Moment가 이미 지났어도 약속 instant가 미래면 후보에 남는다. 약속 instant가 지난 미진행 일정은 nearest에서 제외하고 기록·상태는 보존한다. 조회 때문에 자동 완료, 삭제, outcome 등록을 하지 않는다.
3. 48시간 제품 cutoff를 제거한다. 단발 일정이나 이미 materialize된 일정이 다음 주·다음 달에 한 개뿐이어도 선택할 수 있어야 한다. UI가 이를 '오늘'이라고 오표시하지 않아야 한다.
4. 반복 미래 전체를 무한히 materialize하지 않는다. 기존 bounded horizon/cap, candidate budget, slot/exclusion, 분할·override 및 frozen/started 회차의 의미를 보존한다. 범위별 탐색·재조회는 중단 가능해야 한다.
5. 탐색 cap/budget에 닿아 더 이른 미탐색 후보가 없음을 증명하지 못하면 이미 발견한 후보도 확정 nearest로 활성화하지 않는다. `queryLimited`로 구분하고 bounded retry를 제공한다. 근거 없이 전체 미래에 일정이 없다고 단정하지 않는다.
6. unresolved/unknown zone 등의 일정은 A10 원칙에 따라 해당 후보만 실행 대상에서 제외한다. 정상 후보를 계속 찾되 제외 사유와 수정 진입을 설명할 수 있어야 한다. 데이터 읽기 실패를 이런 의도적 제외와 혼동하지 않는다.
7. 홈 Today의 device civil day instant 구간과 월 달력의 원래 zone civil 날짜 정책은 A10을 유지한다. nearest를 달력의 좁은 civil 날짜 범위에서만 고르면 다른 시간대 후보를 누락할 수 있다.

## 갱신·수명주기·동시성 계약

| 신호 | 요구 동작 |
| --- | --- |
| 최초 구독 | 현재 clock/zone/generation으로 새 평가. 상수로 박힌 실제 DateTime.now 대신 테스트 가능한 경계를 사용한다. |
| foreground의 device civil 날짜 변경 | 새 날짜 의미로 재평가한다. 다음 자정은 civil 날짜 구성으로 구하며 DST 날에 24시간을 단순 더하지 않는다. |
| 현재 후보의 appointment instant 경과 | 다음 날짜까지 기다리지 않고 다음 후보를 평가한다. equality에서는 여전히 적격이고 그 이후에는 제외한다. 경계 재예약의 0시간 busy loop를 막는다. |
| resume | 지나간 날·초 단위 이벤트를 재생하지 않고 현재 기준 한 번 평가한다. resume burst는 coalesce할 수 있지만 마지막 요청은 유실하지 않는다. |
| 수동 clock/zone 변경 | foreground 경계 timer와 최대 1분 간격의 가벼운 drift 확인으로 놓친 변경을 탐지하고 재평가한다. 매분 전체 DB 조회·반복 expansion을 하는 설계가 아니다. |
| 일정·준비 데이터 변경 | 현재 구독에서 관련 변경을 반영한다. 삭제/완료/시각·준비 변경으로 후보가 바뀌면 최신 데이터 기준으로 평가한다. |
| active session 종료·해제 | 소유권이 해제된 뒤 최신 후보를 적용한다. 종료 전에 쌓인 옛 조회 결과를 적용하지 않는다. |
| pause/dispose | pause 동안 heartbeat 중지. dispose에서는 모든 timer/subscription을 취소한다. 취소되지 않는 underlying Future의 결과는 currentness 검사로 폐기한다. |
| restore/reset/DB 세대 변경 | 기존 구독·현재 결과·stale cache를 무효화한다. 이전 DB 응답이 새 프로필이나 복원 데이터에 반영되지 않는다. A15/D03 공통 lifecycle을 따른다. |

- one-shot 경계 timer와 가벼운 drift 점검의 clock을 주입해 foreground 수일 유지, 앞뒤 시각 이동, 자정과 resume 경합을 재현한다.
- 요청마다 revision을 캡처하고 모든 await 뒤 request revision과 `LocalDataOperationGate` generation을 검사한다. 이전 준비 읽기, materialize, repository 이벤트는 emit/persist/navigation/notification을 만들 수 없다.
- query debounce/coalesce는 허용하지만 최종 요청을 반영해야 한다. A의 느린 응답이 B의 최신 결과를 덮는 상태가 없어야 한다.
- active/early-start session과 notification prompt는 nearest refresh로 교체하거나 persisted state를 clear하지 않는다. 그 소유자가 정상적으로 종료·해제한 뒤 최신 후보를 적용한다.
- 사용자의 삭제/완료/복원 때문에 세션 자체가 무효가 되면 기존 도메인 lifecycle이 처리한다. 'active 보호'를 이유로 실제 무효화를 숨기거나 삭제한 일정을 계속 실행하지 않는다.
- 이 조회 경로 자체는 새로운 start/finish, 단계 알림, OS 알림 예약을 재생하지 않는다. A06의 단계 알림 현재성·freshness와 A15의 단일 delivery owner를 우회하지 않는다.
- 단순 시각/zone refresh는 원래 약속 civil/offset·durable revision을 바꾸지 않는다. 필요한 반복 회차 materialization만 기존 transaction 의미로 허용하며 refresh마다 불필요하게 데이터를 다시 쓰지 않는다.

## 결과·오류·재시도 UX

| 결과 | 의미와 사용자 동작 |
| --- | --- |
| `loading` | 최신 평가 진행 중. 영구 empty로 보이지 않는다. 기존 값은 동일 generation일 때만 stale 읽기 전용으로 잠시 표시할 수 있다. |
| `ready(schedule)` | 필요한 후보 탐색과 해당 준비 읽기가 성공했고 더 이른 미탐색 후보 문제도 해결된 현재 값. A10 해석 완료와 현재성 검증 이후에만 새 준비 시작에 사용할 수 있다. |
| `empty` | 현재 계약의 검색범위에서 적격 후보가 없다고 확인한 값. 조회 실패·budget 제한·missing preparation을 이 상태로 바꾸지 않는다. |
| `recoverableError` | repository watch, 반복 materialize, 선택된 nearest 준비 읽기의 실패 또는 missing 불변식 오류. safe reason, KO/EN 설명, 재시도를 제공한다. missing은 편집/복구 진입도 고려한다. 더 늦은 정상 후보로 조용히 우회하지 않는다. |
| `queryLimited` | bounded 탐색의 cap/budget로 후보 선정의 완전성이 아직 확인되지 않음. 다음 bounded 평가 또는 다시 시도를 제공한다. 확정 nearest로 실행하지 않는다. |

- invalid-zone 설명은 정상 ready 후보와 함께 표시할 수 있다. 잘못된 하나 때문에 정상 앱 사용을 모두 막지 않는다.
- preparation은 명시적 일회성 local read의 found/missing/error를 사용한다. `.where(nonNull).first`로 없는 값을 무기한 기다리지 않는다. 실제 진행 중 읽기 자체를 임의 성공이나 empty로 바꾸지 않는다.
- 마지막 검증값을 보여줄 때는 stale임을 알리고 읽기 전용으로 제한한다. 새 start/자동화에는 사용하지 않는다. 동일 generation이라는 사실만으로 최신 데이터임을 가정하지 않는다.
- restore/reset은 stale 표시까지 즉시 폐기한다. 개인정보가 포함된 이전 데이터가 새 profile/generation에 노출되어서는 안 된다.
- 재시도는 오류 이전 파괴 작업을 반복하는 경로가 아니라 현재 기준의 새로운 bounded query다. 데이터 원본과 기존 활성 세션은 보존한다.
- platform/DB 예외 원문, 일정명, 장소, 준비명, 전체 payload를 로그나 사용자 오류에 넣지 않는다. 진단은 안전한 코드와 비민감 현재성 정보만 사용한다.
- 로딩·오류·조회 제한·수정 진입과 재시도는 KO/EN, 작은 화면 및 200% 글자 배율에서 읽고 조작할 수 있어야 한다. 전체 디자인 재설계가 아니라 새 상태의 실제 표시·접근성을 포함한다.

## 구현 작업 단위와 의존성

1. A10의 resolved occurrence와 civil/instant 소비자 계약을 연결해 nearest 후보 선정 함수를 정의한다. 표면별 날짜 의미를 섞지 않는 repository/query 경계를 사용한다. 기존 civil TEXT를 UTC로 일괄 변환하지 않는다.
2. `GetNearestUpcomingScheduleUseCase`의 고정 now+2일·first notEnded·catch→null을 대체한다. 준비 found/missing/error, 검색 제한, stale generation을 표현한다. 무기한 non-null 대기 경로를 제거한다.
3. lifecycle/clock/zone 경계 신호와 cancel 가능한 구독·타이머 소유권을 연결한다. periodic drift tick은 가벼운 비교만 하고 변화가 있을 때 필요한 평가를 요청한다.
4. `ScheduleBloc`에서 query 상태와 활성 session 소유권을 구분한다. 현재 null/지난 civil 입력으로 persisted state를 지우는 분기에 새 typed query 결과를 그대로 넣지 않는다. notification prompt ownership 및 기존 A03/A06/A07/A15 처리를 보존한다.
5. 실제 routed nearest 화면과 준비 시작 경로에 ready/loading/error/queryLimited/stale 제한을 연결한다. Today·달력은 A10 정책에 맞춘다. 인터페이스 추가만으로 완료하지 않는다.
6. 아래 행동 중심 테스트를 구현하고 실제 프로세스를 수일 기다리지 않는 주입 clock·fake lifecycle·통제된 pending Future로 검증한다. 마지막에 Android/iOS 실제 resume/설정 변경 증거를 확보한다.

## 수용 조건

- [ ] 최초 구독 후 2일 이상 시간이 지나도 새로운 현재·미래 후보를 고른다. resume 없이 foreground로 살아 있는 경우도 동일하다.
- [ ] 48시간 밖의 단발·기존 materialized 미래 일정이 정상 후보로 나타난다. civil 정렬이 UTC instant 순서를 뒤집지 않는다.
- [ ] equality/경과·동률 ID·완료 제외·준비 시작만 지난 경우가 확정 정의와 일치한다.
- [ ] 반복 bounded 검색에서 cap/budget 한계를 숨기지 않는다. 미탐색의 더 이른 후보 가능성이 있으면 확정 ready가 아니다.
- [ ] 날짜·zone·clock 변경·resume burst·DB/preparation 변경·세션 해제마다 최종 최신 요청이 반영된다. dispose 후 timer/subscription·emit이 남지 않는다.
- [ ] 모든 await의 request revision/generation 검증과 old subscription 폐기를 통해 이전 결과가 새 화면·세션·DB에 영향을 주지 않는다.
- [ ] active/early session과 notification prompt를 단순 refresh가 종료·clear·교체하지 않는다. 실제 삭제/완료/restore 무효화는 기존 lifecycle대로 반영한다.
- [ ] repository/materialize/준비 읽기 실패 및 missing을 empty나 후순위 후보로 대체하지 않는다. 무기한 non-null 대기 없이 typed 오류·재시도·필요한 수정 진입을 제공한다.
- [ ] stale 값은 같은 generation의 읽기 전용으로만 표시하며 fresh 검증 전 새 start/자동화에 사용하지 않는다. restore/reset 시 stale도 폐기한다.
- [ ] A10의 invalid-zone 제외·설명과 정상 후보 공존을 지원하며 unknown 값을 UTC/device zone으로 몰래 바꾸지 않는다.
- [ ] refresh 때문에 start/finish/outcome/단계 알림/OS 예약이 재생되지 않는다. 단순 시각 변경이 약속 civil/offset·durable revision을 변경하지 않는다.
- [ ] 실제 앱의 nearest consumer에 loading/empty/error/queryLimited/stale 상태가 KO/EN과 200% 글자에서 구분되고 조작 가능하다.
- [ ] 아래 unit/repository/bloc/widget 통합 검증, analyze 및 관련 전체 회귀를 실행한 정확한 소스와 로그를 남긴다. 실행하지 않은 시나리오를 통과로 기록하지 않는다.
- [ ] Android/iOS 실제 lifecycle/수동 시각·zone 변경 검증을 별도 증거로 기록한다. fake clock·host test·CI는 모바일 OS 동작 증거로 대체하지 않는다. 의존 구현·기기 증거가 남으면 이슈를 OPEN 유지한다.

## 실제 grill 원문

아래는 합의 요약을 대화처럼 재구성한 내용이 아니라 전담 agent와 root의 실제 메시지 원문이다. root가 사용자를 대신해 답했다.

### 질문 1 — 선정 의미

> C08 Q1 — grill-with-docs와 CONTEXT/ADR0021/A10을 읽었습니다. 고정 0efdd3ad 코드의 nearest는 처음 now~now+48시간 civil 범위에서 첫 notEnded를 고릅니다. 단순 날짜 refresh만으로는 '가장 가까운' 의미·48시간 밖 공백·약속이 지난 미완료 일정의 고착이 남습니다. 권고: 홈 nearest를 '아직 끝나지 않았고 resolved occurrenceInstantUtc >= 현재 instant인 일정 중 약속 instant가 가장 이른 일정'으로 정의하고 같은 instant는 안정적인 ID 순서로 고릅니다. 제품상 48시간 cutoff는 제거하여 다음 주 한 개뿐이어도 보여주되 반복 expansion은 기존 bounded horizon/cap으로 실행하고 미래 전체를 무한 materialize하지 않습니다. Preparation Start Moment가 이미 지났으나 약속 instant는 미래인 일정은 후보에 남습니다. 현재 활성 Schedule Preparation Session/알림 확인 화면은 별도 소유권으로 유지하여 날짜 갱신이 중단시키지 않습니다. 과거 미진행 notEnded는 nearest 후보에서 빠지되 DB 상태를 자동 완료/삭제하지 않습니다. 이 의미를 채택할까요? 일정 검색의 미확정 tz는 A10처럼 해당 일정만 제외+설명, 정상 후보는 계속 찾는 것을 권합니다.

질문 1 뒤 코드 근거 보충:

> C08 추가 코드 근거: ScheduleBloc._onUpcomingReceived는 incoming.scheduleTime < now 또는 null 때 persisted session을 지우므로, 단순 subscription 재시작은 현재 진행 세션까지 끊을 위험이 있습니다. repository.watchSchedulesByDate는 civil filter/sort이고 materialize는 시작 시 한 번입니다. 현재 nearest 테스트는 background week load 실패 1건뿐입니다. 이후 Q2에서 active session 보존·latest generation·갱신 trigger/오류 표시를 구체화하겠습니다. 제품/테스트 파일은 수정하지 않았습니다.

root 답변 1:

> Q1 채택합니다. nearest는 현재이상 resolved occurrenceInstantUtc를 가진 notEnded 후보 중 가장이른 instant, 동률 stable ID입니다. 준비시작은 지났어도 약속이 미래면 포함. 48h 제품 cutoff 제거하되 기존 반복 bounded horizon/cap 준수, 현재 materialized/단발 미래 데이터를 조회; 반복 미래 전체를 만들지 않습니다. active session은 별도 소유권 유지, 날짜갱신이 중단/자동완료/삭제하지 않습니다. 과거 미완료는 history/오늘목록에서 상태 보존하되 nearest 제외합니다. invalid/미확정 tz는 A10 원칙으로 해당후보만제외+설명하고 정상후보 계속조회. 추가로 데이터/준비읽기 실패를 빈목록/다음후보로 조용히 바꾸지 말고 empty와 typed recoverable error 구분, retry에원본보존. 이 구분은 다음질문에서 구체화가능.

### 질문 2 — 갱신과 소유권

## 범위 밖과 완료 판정

전체 시간대 정책 재설계, 일정 저장 포맷 일괄 변환, 자동 과거 기록 정리, 무제한 반복 생성, 백그라운드 상시 실행 보장, 새 서버/위치 API는 이 이슈에 포함하지 않는다. 반면 위에 명시한 query 오류 UI·수명주기 연결·준비 읽기 실패 구분·A10 통합·기기 검증은 범위 안이며 별도 이슈 번호가 있다는 이유로 누락할 수 없다.

문서 작성 단계에서 제품 코드·테스트·QA 도구는 수정하지 않았고 Flutter 테스트나 모바일 기기 검증도 실행하지 않았다. 실제 구현·검증 후 commit/CI/기기 증거를 추가하고 충족하지 못한 항목을 정확히 남긴다. 이 문서 또는 GitHub 이슈 생성 자체는 구현 완료가 아니다.
