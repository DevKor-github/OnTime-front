# 반복 일정 설계 및 전달 계획

상태: 제품 정책 21개 확정. Figma 21개 화면, 반복 도메인·로컬 DB·백업·알림 후보 공급·Flutter 화면 연결을 구현했다. 사용자 결정은 `recurring-schedules.md`의 1–21번을 기준으로 한다. 검증 범위와 결과는 아래 실행 기록을 따른다.

## 진행 순서

1. 기능 기획: 합의된 행동, 예외, 수용 기준을 정리한다.
2. Figma: 기존 컴포넌트로 화면과 주요 상태를 추가하고 시각 검증한다.
3. 기능 구현: 반복 계산, 데이터 저장, 수정·삭제, 알림, 백업을 구현·검증한다.
4. 화면 구현: Figma에 맞춰 폼·목록·상세·대화상자를 연결하고 전체 흐름을 검증한다.

반복 묶음끼리 지속적으로 충돌하면 시간·요일을 수정한 뒤 저장하는 것으로 확정했다. 특정 날짜의 충돌은 명시적으로 회차를 제외할 수 있다.

## 범위

- 일·주·월 반복, 양의 정수 간격, 복수 요일, 월 날짜·순번 요일·말일.
- 종료 없음·종료 날짜·총횟수, 실제 첫 회차 및 규칙 요약.
- 반복 묶음이 독립적으로 소유하는 준비과정과 회차별 예외.
- 이번 회차 / 이번 및 이후 수정·삭제, 개별 변경값·진행 중 상태·과거 기록 보존.
- 명시적으로 선택한 충돌 회차 제외 및 새 규칙에서 빠진 개별 수정 회차의 단독 일정 분리.
- 마이페이지 반복 일정 관리, 달력 회차 표시, 기록 없는 과거 회차 표시.
- 이름 있는 시간대, 서머타임의 없는 시각·중복 시각 정책.
- 기존 로컬 암호화 DB, 백업, 알림 예약 경계 유지.

연간 반복과 여러 사용자 템플릿을 선택·관리하는 별도 라이브러리 화면은 이번 범위에 추가하지 않는다. 후자는 사용자가 ‘나중에’ 추가할 기능으로 요청했으므로 데이터 모델의 확장성을 확보한다.

## 기존 정책을 적용할 세부 동작

다음은 추가 사용자 결정을 주장하는 항목이 아니라 기존 결정과 제품 정책에서 도출한 설계 기준이다.

- 존재하지 않는 ‘다섯 번째 월요일’도 없는 날짜와 동일하게 건너뛰고 총횟수를 소모하지 않는다. ‘마지막 월요일’과 구분한다.
- 종료 날짜는 반복 일정 시간대의 달력 날짜를 기준으로 당일을 포함한다. 그 범위 안에 유효한 회차가 없으면 저장 대신 조건 수정을 안내한다.
- 준비 시작 시각은 약속 시각에서 준비·이동·여유 시간을 뺀 실제 시각이다. 생성 직전에도 다시 검사한다.
- 날짜가 바뀌거나 준비과정·시간이 변경되면 첫 회차, 종료 요약, 충돌 검사를 다시 계산한다.
- 명시적인 ‘이번 및 이후 삭제’는 해당 범위의 개별 수정 회차도 포함하며, 삭제 미리보기에 포함 내역을 보여준다. ‘규칙 수정 시 단독 일정 보존’과 구분한다.
- 진행 중·완료·과거 회차의 내용은 미래 일괄 수정으로 다시 쓰지 않는다. 기존 개별 기록 삭제 동작과 현재 준비 중단 동작은 별도로 유지한다.
- 관리 화면에서는 다음 미시작 회차를 변경 기준으로 보여준다. 종료된 묶음은 읽기 가능한 별도 상태로 나타내고 자동 재개 기능은 추가하지 않는다.
- 일정이 한 건도 남지 않는 종료 조건이나 충돌 제외 결과는 빈 반복 묶음으로 저장하지 않는다.
- 알림 예약 실패와 DB 저장 실패를 구분한다. 저장 성공이 알림 예약 또는 실제 전달 성공을 뜻하지 않는다.

## 적용한 데이터 및 도메인 설계

### 반복 묶음과 회차

- 반복 묶음은 식별자, 시간대, 규칙, 시작 경계, 종료 조건, 공통 일정 정보와 전용 준비과정 참조를 소유한다.
- ‘이번 및 이후’ 수정은 적용 시작 회차를 기준으로 구간을 나눠 이전 구간을 유지한다. 과거 회차를 최신 규칙으로 다시 계산하지 않는다.
- 회차 식별은 사용자가 이동시킨 날짜가 아닌 원래 반복 슬롯을 기준으로 한다. 원래 슬롯·묶음 관계를 저장하여 날짜 변경, 중복 생성, 알림 재등록을 구분한다.
- 개별 수정 항목을 명시적으로 기록한다. 공통 시간만 수정할 때 개별 메모나 준비과정까지 덮어쓰지 않는다.
- 삭제·제외한 슬롯도 반복 원본에 예외로 남겨 재조회·재실행·복원 뒤 자동으로 되살아나지 않게 한다.
- 무기한 반복 전체를 미리 일정 행으로 만들지 않는다. 달력 조회 범위와 가까운 알림 후보를 계산하고, 필요한 회차와 실제 사용자 활동을 안정적인 식별자로 저장한다.
- 과거 회차 조회는 보존된 규칙 구간 및 예외를 사용한다. ‘진행 기록 없음’과 실제 완료 결과를 분리한다.

### 재사용 가능한 준비과정

- 준비과정 정의와 순서 있는 단계 테이블을 반복 묶음에서 참조한다. 모든 미래 회차가 단계 원본을 중복 소유하는 구조는 피한다.
- 향후 사용자가 이름 붙인 템플릿과 반복 전용 정의를 같은 기반으로 표현할 수 있도록 소유 범위를 구분한다. 반복 전용 정의는 사용자 템플릿 목록에 자동 노출하지 않는다.
- 기존 기본 준비과정에서 가져올 때 단계 식별자까지 새로 만들어 원본과 분리한다.
- 준비과정 변경 이력을 구간별로 보존한다. 진행 중·완료 회차는 해당 시점의 정의 또는 고정된 사본을 유지한다.
- 회차만 수정한 준비과정은 그 회차의 별도 정의이며, 반복 공통 준비과정 변경으로 덮어쓰지 않는다.
- `PreparationDefinitions`와 `PreparationDefinitionSteps`를 추가하여 반복 공통/개별 회차의 불변 준비 정의를 저장한다. 기존 사용자 템플릿 테이블은 유지하며 단계 ID는 복사할 때 새로 발급한다. 여러 사용자 템플릿을 선택·관리하는 UI는 후속 범위다.

### 저장·마이그레이션·백업

- DB 스키마 버전 2: v1 → v2 추가 마이그레이션으로 준비 정의/단계·반복 구간·제외 슬롯 4개 테이블과 일정 메타데이터 5개 열을 추가한다. Local-only 전환 이전 버전은 기존처럼 지원하지 않는다.
- 기존 일정·기본 준비과정·템플릿을 보존하는 추가 마이그레이션을 작성하고, 실패 시 기존 Recovery Mode 정책을 유지한다.
- 반복 묶음·준비 정의·규칙 구간·회차·예외는 하나의 트랜잭션 경계로 저장하고 백업 변경 상태도 함께 갱신한다.
- 백업 `formatVersion`은 2로 올렸다. 반복 정의·단계·구간·예외와 참조를 검증하고, 기존 v1 백업은 반복 묶음 없는 데이터로 가져온다.
- 백업 복원은 기존의 검증 후 원자적 교체 정책을 유지한다. 알림 등록은 복원된 회차를 기준으로 다시 구성한다.
- 로컬 데이터 초기화와 명시적 삭제 시 새 테이블의 외래키·단계 정리 순서도 포함한다.

## 충돌과 알림의 구현 검토 사항

- 기존 단일 일정 폼의 앞뒤 일정 조회만으로 반복 전체의 충돌을 검증했다고 주장하지 않는다.
- 유한 반복은 종료 범위의 유효 회차를 검사한다. 무기한 반복은 두 규칙의 교차 판정과 미리보기 범위를 분리해야 하며, 유한 미리보기 밖을 검사 완료로 표시하지 않는다.
- 생성·수정 시 충돌 미리보기 이후 데이터가 달라지면 저장 직전에 재검사한다.
- 저장 후 새 일반 일정이나 새 반복 일정을 추가할 때에도 기존 반복 규칙을 충돌 검사 대상으로 포함한다.
- 반복끼리 지속 충돌하면 시간·요일 수정 후 저장한다. 탐색 한도 초과를 ‘충돌 없음’으로 처리하지 않는다.
- 알림 후보는 단독 일정과 반복 회차를 함께 정렬해 플랫폼 용량 내에서 가까운 준비 시작 시각부터 예약한다.
- 앱 실행·복귀·일정 변경·복원·시간대 변경 등 기존 재조정 계기에 다음 후보를 보충한다. 무기한 반복을 등록했다고 무기한 전달이 보장되는 것으로 표시하지 않는다.
- 실제 시간대 변환, 알림 취소·재예약, 준비 타이머 진입은 동일한 회차 식별자를 사용해야 한다.

## 수용·검증 기준

1. 반복 묶음 생성 후 기본 준비과정을 바꿔도 반복 전용 준비과정은 그대로다. 두 반복 묶음도 서로 영향을 주지 않는다.
2. 일·주·월 간격, 복수 요일, 31일·말일·다섯 번째/마지막 요일의 실제 날짜와 횟수가 맞는다.
3. 시작일과 요일 불일치, 생성 도중 준비 시작 시각 경과, 종료일까지 회차가 없는 경우를 검증한다.
4. 존재하지 않는 현지 시각은 건너뛰며, 중복 시각은 선택한 실제 시각의 한 회차만 만든다.
5. 한 회차 수정은 다른 회차에 영향을 주지 않는다. 이후 일괄 수정은 개별 변경 항목을 보존한다.
6. 규칙에서 빠진 개별 수정 회차는 단독 일정으로 남고, 기존 준비과정 및 날짜를 보존한다.
7. 삭제·제외한 회차는 조회·재실행·복원 데이터 재구성 중 되살아나거나 뒤에 보충되지 않는다.
8. 준비가 시작되거나 완료된 회차의 단계·시간·결과는 이후 변경에 따라 바뀌지 않는다.
9. 앱 미실행 기간의 지난 회차는 기록 없음으로 조회되고 점수는 그대로다.
10. 충돌 검토에서 사용자가 고른 회차만 제외한다. 취소하면 어떤 반복 데이터도 저장하지 않는다.
11. 중복 제출·동시 재조회·알림 재조정이 회차나 단계·점수 기여를 중복 생성하지 않는다.
12. 구 DB 업그레이드와 구 백업 가져오기는 기존 단독 일정·기본 준비과정을 보존한다. 새 백업 왕복 후 규칙·예외·준비과정·이력이 같다.
13. 알림 예약 범위·실패를 실제 등록 결과와 대조하며, Android/iOS의 전달 확인과 웹 시각 미리보기를 구분한다.
14. 폼·달력·관리 목록·수정·삭제·준비 타이머까지 연결해 위젯 및 실제 브라우저/가능한 모바일 환경에서 확인한다.

코드 생성물을 재생성한 뒤 관련 단위·위젯·마이그레이션·백업 테스트와 분석을 실행하고, 마지막으로 전체 회귀 테스트를 실행한다. 생성 Dart 파일은 커밋하지 않는다.

## 구현 결과

- 반복 규칙/계산기: `lib/domain/recurrence/`. 일·주·월, 간격, 유효 슬롯 횟수, 월말·순번, DST gap/fold, 생성 시 지난 준비 시작 후보 제외.
- 저장: `RecurringScheduleRepositoryImpl`의 트랜잭션으로 구간·준비 정의·제외·근접 회차를 함께 반영한다. 반복 ID·규칙 구간 ID·원래 슬롯 날짜로 회차 ID를 결정하여 재조회 및 생성 재시도의 중복을 방지한다.
- 식별자: 같은 저장 구간의 재조회는 동일 ID를 재사용한다. 이후 규칙을 바꾸면 보호되지 않은 미래 회차는 새 구간 ID로 생성한다. 이전에 분리된 단독 일정의 날짜를 새 규칙이 다시 포함해도 두 일정의 ID가 충돌하지 않는다.
- 수정: 필드별 변경 마스크, 불변 준비 정의, 이후 구간 분리로 개별 수정값 및 보호 회차를 유지한다. 장소도 수정 시 독립 ID로 분리하여 다른 회차나 과거 장소가 바뀌지 않게 한다.
- 횟수: 10회 중 지난 3회를 제외한 7회를 유지한다. 이 중 2회 분리 시 반복 5회 + 단독 2회이며, 삭제·제외한 회차도 재충전하지 않는다.
- 충돌: 준비·이동·여유 시작부터 약속 시각까지 비교하며 같은 시각의 0분 일정도 충돌로 잡는다. 개별 시간/준비 예외를 반영한 실제 후보끼리도 검사한다.
- 무기한 규칙: 마지막 저장 예외와 번들 시간대 전이 뒤의 규칙 공통 주기까지 검사한다. 일/주에는 간격의 공통 주기를, 월 규칙에는 400년 Gregorian 주기를 사용한다. 단순 미리보기만으로 충돌 없음이라 판정하지 않는다.
- 기술 한도: 확장당 후보 200,000개, 공통 주기 4,000년 한도. 한도 초과 시 종료 조건 조정을 안내하고 저장을 거절한다. 폼 상태에는 무기한 전체 증명 결과 대신 가까운 미리보기와 충돌 회차만 전달한다.
- 알림: 기존 재조정 정책/플랫폼 60개 예약 상한을 유지하고, 반복마다 가까운 최대 64개 후보를 공급한다. 날짜 경계의 UTC/현지 날짜 차이도 포함하여 최종 실제 알림 시각으로 필터링한다.
- 화면: 기존 4단계 생성, 날짜·시간의 반복 설정, 마지막 전용 준비과정, 저장 전 검토·명시 제외·DST 선택, 달력의 범위 선택, 마이페이지 반복 관리/상세/종료를 연결했다.
- 확인 화면은 개별 시간 변경을 반영한 실제 시각, 준비 시작, 유한 반복 건수와 단독 분리 건수를 표시한다.
- 서버·인증·원격 동기화 및 새 네트워크 의존성을 추가하지 않았다.
