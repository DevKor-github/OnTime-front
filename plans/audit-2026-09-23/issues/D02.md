# [P1][D02] 정상 DB 없이 검증된 백업으로 손상 저장소를 안전하게 교체하고 복구 실패를 보존

## 문제와 영향

Recovery Mode는 현재 startup 재시도와 전체 초기화만 제공한다. ADR 0023이 약속한 OnTime Backup 복원 버튼과 실제 손상 DB 교체 경로가 없다. BackupService는 정상 AppDatabase에 의존하고 applyRestore는 그 인스턴스 안에서 transaction을 수행하므로, 열리지 않는 DB나 잃어버린 Installation Data Key를 이 방식으로 복구할 수 없다. reset 직접 호출은 예외 시 busy를 해제하지 않는다.

D02는 정상 저장소를 전제하지 않는 백업 검증·후보 DB 생성·별도 확인·교체·중단 복구를 제공한다. 원본 DB와 설치 키 보존은 교체 성공 전 불변 조건이다. 데이터 교체 성공, runtime 정리, OS delivery 정리 및 재등록 성공은 각각 다른 사실로 보고한다.

우선순위 **P1**. 조사 기준 commit은 **`e2fbdf0bb233ebbbb99426b9c06c0da5b4e47f9c`**. 조사 시 A14 native/notification/reconcile/UI 파일이 WIP였으며 이를 D02 구현 근거로 사용하거나 수정하지 않았다. 이 문서는 전담 grill-with-docs 조사·결정 기록이며 구현·테스트 통과 증거가 아니다. 전담 agent는 제품 코드, 테스트, 공유 tracking, GitHub, commit을 변경하지 않는다.

## 확정한 후보 검증 경계

- A09의 인증·format migration·실제 암호화 staging factory/validator를 정상 AppDatabase 없이 호출할 수 있는 포트로 공유한다. C01 command/result를 통해 D01 최소 shell에서 사용한다.
- DB 손상·기존 키 유실·기존 키 형식 손상은 원본을 열어야만 진행할 수 있는 조건이 아니다. 별도 device-bound secure-storage slot과 앱 소유 보호 경로에 후보를 만든다. slot write/read-back 및 후보 DB read-back을 검증하고 나서 preview를 제공한다.
- secure storage 자체가 사용할 수 없으면 별도 키를 안전하게 지속할 수 없으므로 교체를 시작하지 않는다. 일반 키 유실과 secure-storage 서비스 오류를 구별한다.
- 기존 DB/키 slot을 덮거나 먼저 삭제하지 않는다. 정상 DB 복원 A09의 키를 교체하지 않는다.
- 취소·잘못된 암호·완전성/format/관계 검증 실패 때 후보만 정리한다. 후보 정리 실패는 안전한 typed pending 결과이며 원본 삭제나 전체 reset으로 해결하지 않는다.
- plaintext DB/temp, 암호/키/일정 원문 로그는 금지한다. 후보 DB와 WAL/SHM/journal, 키 slot, 이후 교체 metadata는 외부 portable backup 및 OS-managed transfer 제외 대상이다.
- preview는 cutoff/source app/data categories/counts와 기존 데이터 대체 경고를 제공한다. 손상 원본의 내용/개수를 읽을 수 없으면 현재 데이터 개수 0 또는 원본이 비어 있다고 추정하지 않는다.

## 확정한 활성 저장소 교체와 중단 복구

- DB 파일 이동과 secure-storage 값 변경을 하나의 transaction이라고 표현하지 않는다. 검증된 별도 DB/키 쌍을 준비한 뒤 versioned active-store manifest가 활성 쌍을 한 번에 선택한다. manifest는 DB 식별자, key-slot 식별자, 교체 세대의 최소 metadata만 담고 실제 키/암호/백업 원문을 담지 않는다.
- 경로는 앱 내부 allowlist 식별자로 해석한다. 외부 backup에 manifest/키 slot 경로를 받아 그대로 사용하지 않는다. 임의 경로·상위 경로·다른 앱 파일을 선택하거나 삭제하지 않는다.
- old/candidate identity, 명시적 최종 확인 intent, 단계가 원문 없는 설치 로컬 journal에 영속화된다. 기존 D03/A09 journal/gate를 재사용하는 구체 방법은 구현 시 합의하고 새로운 범용 recovery framework를 만들지 않는다.
- 후보 DB와 sidecar를 안전하게 close/checkpoint하고 재열기·전체 내용 read-back을 검증한다. 닫힌 단일 SQLite 파일이라고 가정해 필요한 WAL을 버리지 않는다. 원본 파일군은 손상됐다는 이유로 정리 대상이 되지 않는다.
- manifest 활성화 응답이 실패/불명확하면 기록된 intent와 권위 있는 manifest read-back으로 commit 여부를 판정한다. 성공 반환만으로 commit을 추정하거나 응답 오류만으로 rollback을 추정하지 않는다.
- manifest가 손상·유실되었고 prior-manifest/중단 작업 증거가 있으면 legacy 경로나 빈 DB 생성으로 fallback하지 않는다. 현재 쌍을 안전히 판단할 수 없으면 보존한 제한 Recovery Mode에 남는다.
- 최초 legacy 고정 경로/키 slot에서 manifest 방식으로 넘어갈 때의 모든 중단 조합도 같은 원칙으로 검증한다. 최초 도입이라는 이유로 manifest 부재를 항상 신규 설치로 해석하지 않는다.
- 새 쌍 활성화 및 **재시작 read-back** 성공 전 old DB와 old key를 제거하지 않는다. commit 후에는 자동 rollback하거나 backup을 다시 import하지 않고 미완료 후속 작업을 이어간다.
- 새 쌍이 안전하게 확인된 뒤 보존된 old 파일군/retired key를 정리한다. 정리 실패는 pending 상태·명시적 retry로 표시하며 비활성 DB/key를 무기한 누적하는 완료 판정을 허용하지 않는다. 실패를 감추려고 active key 또는 새 쌍을 삭제하지 않는다.
- 원자적 manifest 교체의 실제 파일 API/flush/rename/read-back 및 플랫폼 보장 범위는 구현 때 확인한다. 호출 성공과 process-restart 검증을 근거 없이 power-loss 내구성 보장으로 확대하지 않는다.

### 제품 용어 정정 필요

현재 CONTEXT.md:381은 각 설치가 Installation Data Key를 정확히 하나 가진다고 서술한다. 이번 복구 프로토콜에는 검증 후보와 보존 중인 old key material이 일시적으로 필요하므로 root는 **정확히 하나의 active Installation Data Key**로 의미를 정정하기로 결정했다. 후보/retired 재료는 활성 데이터의 두 번째 권위가 아니라 검증·실패 보존을 위한 제한 수명 구현 재료다. 목적, 보존 및 정리 조건을 명시하며 정상 동작에 복수 active profile/key를 도입하지 않는다. 이 전담 agent는 D02.md만 편집할 권한이 있어 CONTEXT를 직접 변경하지 않았다. root가 Q4 확정 시 해당 최소 glossary 정정을 적용했다고 확인했다. manifest/key slot의 구체 구현 세부사항은 glossary에 넣지 않는다.

## 확정한 currentness·작업 소유권

- 손상 DB에서는 durable revision을 읽을 수 없으므로 숫자 0 또는 임의 정상 revision으로 치환하지 않는다. 검증 후보 identity, recovery operation epoch, 원본 active-store descriptor 및 파일군/key-slot의 관측 identity를 preview 확인과 최종 exclusive claim에 연결한다.
- 파일 크기/수정 시각 일치만으로 내용 동일성을 증명하지 않는다. 실제 접근 소유권·변경 경로를 통제하고 필요한 local evidence를 재검증하여 TOCTOU를 막는다. 읽을 수 없는 증거를 성공으로 취급하지 않는다.
- 원본 DB가 retry 후 다시 정상으로 열리면 손상 복구 후보를 그대로 적용하지 않는다. 정상 A09 모드에서 현재 원본과 대체 경고를 다시 확인한다. 다른 restore/reset/manifest 변경 역시 기존 확인을 무효화한다.
- D01 단일 startup attempt, C01 command/result와 기존 data operation gate, A15 단일 OS writer를 공유한다. 살아 있는 이전 DB handle, repository, timer, OS Future를 quiesce하기 전에 새 쌍으로 바꾸지 않는다. UI timeout은 Future 취소가 아니다.
- 이미 영속화된 reset intent가 있으면 신규 restore를 시작하지 않고 같은 reset의 후속 정리만 재개한다. restore commit 뒤 실패도 backup 전체 재실행이 아니라 권위 있는 상태 read-back/남은 정리만 수행한다.
- A09의 old runtime/pending tap 세대 무효화와 D03 journal 보존을 필수 통합한다. 늦게 도착한 old notification을 새 DB의 같은 schedule ID로 연결하지 않는다.

### active store epoch와 runtime generation의 분리

앞서 말한 manifest의 교체 세대와 A09의 DB 내부 runtime generation은 같은 값을 따로 저장하는 두 권위가 아니다. manifest는 **active store identity/epoch**를 선택하고, 해당 DB는 **그 store 내부 runtime generation**을 소유한다. 런타임 현재성은 두 값의 쌍으로 판정한다. D02 후보 DB에는 최초 runtime generation과 pending cleanup marker를 activation 전에 기록하여 manifest가 이미 일관된 후보 쌍을 선택하게 한다. 정상 A09 restore는 같은 active store에서 DB transaction으로 내부 generation만 갱신하고 manifest/key를 다시 쓰지 않는다. 이 분리 없이 두 자원에 '현재 generation'을 따로 저장하는 구현은 수용하지 않는다.
