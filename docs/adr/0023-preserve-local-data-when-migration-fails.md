# Preserve local data when migration fails

Local Data Store schema migrations will be atomic and will never fall back to silently deleting or recreating the database. If OnTime cannot open the encrypted store or complete a migration, it will preserve both the database and Installation Data Key and start in a restricted Recovery Mode rather than creating an empty Local Profile. Recovery Mode will not start normal product screens or background Schedule Notification processing and will offer only a startup retry, an OnTime Backup restore, or an explicit Local Data Reset. The preserved store and key may be removed only after a replacement restore succeeds or the user confirms Local Data Reset. Automatic destructive recovery was rejected because Local-only OnTime has no server from which lost records can be downloaded again. This requires a recovery startup path and transactional migration tests but makes upgrade failure non-destructive and user-controlled.


Initial creation is distinct from opening an existing Local Data Store. A missing cutover marker, missing key, empty database file, or surviving SQLite sidecar does not prove a fresh installation. Only authoritative absence of prior store/key/creation or activation evidence permits a small, versioned, app-owned creation receipt to be recorded and read back before the device-bound key and encrypted store are created. The receipt contains ownership and stage metadata, never key material or user content; creation resumes only with the same verified key and owned store. Existing data with a missing, invalid, or unreadable key remains in Recovery Mode. The receipt is excluded from platform backup and is included in explicit reset cleanup. This bounded ownership record is preferred over requiring manual destructive recovery after every interrupted first launch, but is not a general transaction journal or a claim of power-loss durability. Damaged-store pair activation remains governed by ADR0036.


Migration atomicity includes the schema version, not only callback-local DDL. D04's implementation review confirmed that the locked Drift engine writes user_version after the application's migration and before-open callbacks. Creation and supported upgrades therefore commit DDL, backfill, required validation and the new user_version in one SQLite transaction. A later duplicate version write or callback failure is an uncertain response, not proof of rollback: an independent reopen must establish a complete predecessor or complete current schema/data/version before retry proceeds. Connection configuration such as foreign-key enforcement remains separate where SQLite does not apply it inside a transaction. This approach avoids a Drift fork or generic executor framework while closing the observed DDL/version gap.

Migration permission follows the file's role. The normal legacy startup supports the recorded historical predecessors; an activated recovery pair supports only schema lineage that actually existed for pairs, starting with their introduction at schema4. Candidate creation requires its existing explicit ownership grant, and immutable candidate verification never gains implicit migration permission. The read-only original-store availability probe may recognize a supported historical legacy store and return control to normal startup, but it does not migrate, create or repair that store. Current version and supported-role definitions are shared so a future version bump cannot silently strand a legitimate older active pair behind an unrelated magic constant.

Before migration writes, an existing store must match an independently sourced historical schema contract for app-owned tables, columns, keys, defaults, constraints, indexes and triggers. Missing, unexpected or changed app schema is preserved rather than normalized by destructive repair or IF NOT EXISTS. SQLite-internal metadata and semantically irrelevant SQL formatting are not treated as app schema changes; uncertain semantics remain a preservation failure. Historical fixtures record source/tool/engine provenance separately from mobile-binary evidence. These boundaries preserve user data and reject ambiguous lineage at the cost of deliberately refusing undocumented schema variants. The original D04 issue retains its initial questions and answers; the additional implementation questions, answers and corrections are recorded in the local D04 implementation review, with remote publication tracked separately.


Tracked historical schema snapshots are delivered to the runtime as compile-time constants generated by a small local build_runner builder. Generated Dart remains ignored and is regenerated by the existing build command; snapshots and provenance remain the independently reviewed inputs. This avoids coupling pre-DI database opening to Flutter bindings, rootBundle or a working-directory file path. The builder does not regenerate historical truth from the current model. A separate schema gate checks supported/current versions, provenance and input digests, including stale or missing generated output. Existing locked build tooling is used without a runtime dependency or SDK upgrade. This delivery trade-off was resolved in D04 implementation Q4.

Native migration verification uses dedicated QA bundles, synthetic stores and separately owned simulator/emulator state. D04 implementation Q5 permits the Android QA project to adopt the product's pinned Gradle, Android Gradle Plugin and Kotlin versions, with required build artifacts fetched into its temporary Gradle cache. The installed SDK and system image, production build settings and existing device/app data remain outside this change. Verification records the actual toolchain, adapted QA sources, product inputs, generated contracts and fixture assets consumed by each build. Ordinary SQLite rejection must include a successful ordinary-engine control and an actual attempt to read the encrypted file; inability to load a private system library alone is insufficient evidence. Dedicated-bundle success and complete product startup, physical-device behavior and power-loss durability are reported separately.
