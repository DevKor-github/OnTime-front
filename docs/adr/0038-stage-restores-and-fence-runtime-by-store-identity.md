# ADR 0038: Stage restores and fence runtime by durable store identity

- Status: Accepted for A09 (#602), with startup recovery integration tracked in D01
- Date: 2026-09-24
- Related: ADR 0011 (local only), ADR 0037 (aggregate identity), A15 (actual delivery ownership), D03 (reset journal), C01 (commit/follow-up receipts)

## Context

A valid encrypted backup used to be parsed in memory and written directly into the live store. Restoring the same schedule ID could retain its old early-start preference. A process generation alone also cannot reject an old OS notification after a restart. The old exporter did not preserve first `startedAt` or the preparation freeze flag despite the durable-record intent; those values cannot be reconstructed from old backups.

## Decision

Before offering a preview, materialize the parsed backup into a separate SQLCipher database in the app-owned application-support staging directory. Use a random filename and a memory-only random key. Require a nonempty `cipher_version`; plain SQLite is never a production fallback. Require native backup exclusion, foreign-key/integrity checks, and canonical durable-value read-back equality. Exclusion failure fails preview. Candidate cancellation, validation failure and successful replacement release the staging SQLite family. Cleanup never follows links outside this namespace and excludes currently owned candidates. A process restart can remove abandoned ciphertext without its lost key.

Schema 4 adds `Users.restoreCleanupPending`, `Users.rejectLegacyDelivery` and `Schedules.requiresStartConfirmation`. In the live replacement transaction, replace the local profile so the existing schema-3 store-incarnation trigger assigns a fresh identity, mark cleanup pending and reject legacy delivery. These are installation-local fields; portable backups never choose them. Profile updates and backup metadata updates do not clear the markers. Replacement identity remains distinct from content revision and aggregate mutation receipts.

Runtime preference payloads and minimum notification payload v10 carry the issuing store identity. The receiving process must not attach its current identity to an old callback. Legacy payloads remain accepted before the first restore; after any restore they are permanently rejected, including after restart and later restores. Old OS deliveries may therefore be harmlessly discarded. Android/iOS sanitizers preserve only a valid originally issued opaque identity. Native Android full-screen/boot scheduling remains policy guarded; the active fallback notification path uses the same Dart identity contract.

Existing operation owners await actual old runtime/provider futures before replacement. The existing data gate fences ordinary writes by their operation generation, including transaction checks and stale cache emissions. No second mutation queue is introduced. Ordinary edits remain permitted during the export picker. Restored unfinished rows require explicit start confirmation: a preference-only marker could disappear during cleanup before a crash and allow past-due automatic elapsed-time synthesis. Only the existing explicit start transaction clears the durable flag. It preserves the first historical `startedAt`, frozen preparation and recorded score/outcome; the new runtime start time is a separate event. Future occurrences first materialized after restore use ordinary new-occurrence policy.

Startup performs D03 reset recovery and cutover before opening the store, then removes abandoned staging, loads the durable identity and retries known pending cleanup before DI. Live and startup cleanup share the existing ownership journal and platform-delivery/launch cleanup. They do not run reset, DB deletion, key replacement or blanket journal deletion. Unknown ownership is resolved only by authoritative global absence; when Android cannot enumerate all alarms, verified individual cancellations plus no unknown ownership are required. Runtime preference removal false receipts, exceptions, read-back mismatch, platform uncertainty and marker-commit failure leave the durable marker pending.

The portable payload remains format 2 with optional `startedAt` and `preparationFrozen`. The new first-start instant exports with an explicit UTC suffix; schedule civil time is unchanged. Existing finishedAt offsetless history remains a separate timestamp-policy limitation. Missing fields in historical v1/v2 mean null/false; active `isStarted` always resets false. New readers preserve the fields, but older readers may silently lose these optional fields. Unsupported future versions fail before mutation. Explicit frozen preparation without a first start is rejected because the actual freeze writer records both atomically. No new wall-clock ordering invariant is imposed: a completion earlier than first start can reflect clock changes and remains preserved without generating outcomes. D07's narrow prerequisite adds restore-only template timestamp preservation and UTC export; nonzero subsecond template instants are rejected instead of silently rounded by the seconds-based DB. Offsetless legacy input retains its historical local-time interpretation; no original timezone is invented.

## Failure ownership and limits

A precommit staging cleanup failure is a typed `RestoreStagingCleanupFailure` that retains the original validation cause and cleanup cause for controlled diagnostics. It does not represent a committed replacement or notification retry. The UI says data was not restored and startup will retry temporary-file cleanup. The same candidate may retry disposal. A postcommit staging cleanup failure keeps the durable pending receipt; follow-up retries cleanup without applying the backup again.

Pre-DI store/key/migration failures retain `RestoreStoreUnavailable(cause)` separately from a known pending restore's `RestoreRecoveryRequired(cause)`. Causes are not rendered or logged raw. The current pre-DI surface is retry-only; integrating explicit reset access and the complete startup transaction is a required D01 follow-up, so A09 must not be described as end-to-end complete until that integration is closed.

Host SQLCipher evidence verifies the actual encrypted staging pipeline and encrypted live file reopen with a correct synthetic key. It does not prove the Android/iOS linked runtime. D04 owns device artifact/runtime proof and historical plaintext-file risk. D05 owns broader backup graph/value/resource-limit validation. D07's complete timestamp policy remains separate. Damaged-file/key replacement is D02, outside normal content restore.
