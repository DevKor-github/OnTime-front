# [P2][U04] 결과 화면에서 1시간·2시간이 0분으로 표시되는 오류를 고친다

## 문제와 사용자 영향

준비 완료 결과의 기간을 만드는 `formatEalyLateTime`은 절댓값에서 시간과 남은 분을 계산한 뒤 **시간과 분이 모두 양수일 때만** 시간을 출력한다. 따라서 정확히 ±3,600초와 ±7,200초가 모두 `0분`으로 표시된다. 같은 조건 때문에 ±3,601~3,659초도 `0분`이다. 실제 준비 완료의 나가기 전 남은 초가 결과 화면으로 전달되므로, 일정이나 점수 저장이 정상이어도 사용자는 1시간의 차이가 없어진 잘못된 결과를 읽는다.

P2로 처리한다. 자료 손실이나 준비 완료 저장 실패와는 구별되는 표시 오류지만 정상 흐름에서 확정적으로 발생하며, 결과를 신뢰하지 못하게 한다. 별도 새로운 기간 정책이나 타이머 엔진 없이 기존 현지화 formatter에 연결하여 해결할 수 있다.

예시:

- +3,600초, `isLate=false`: 현재 `0분 일찍 준비했어요` → `1시간 일찍 준비했어요`.
- -7,200초, `isLate=true`: 현재 `0분 지각했어요` → `2시간 지각했어요`.
- 영어의 +3,600초: 현재 한국어 단위가 섞인 `0분 early` → `1 hour early`.
- +3,599초는 `59분`이고 +3,601초는 `1시간`이다. 분 미만 초를 버리는 기존 표시 정책을 유지한다.

## 기존 언어와 결정

[CONTEXT](https://github.com/DevKor-github/OnTime-front/blob/63913cd715a5bf35c5495619ad8fd600e526f43e/CONTEXT.md)의 **Schedule Outcome**, **Preparation Run**, **Preparation Action Event**, **Local Punctuality Score**를 유지한다. 이 결과 headline은 기간의 사용자 표시다. 표시 문자열을 Outcome 자체, 점수 자료, 타이머의 원본 상태로 쓰지 않는다.

[ADR 0029](https://github.com/DevKor-github/OnTime-front/blob/63913cd715a5bf35c5495619ad8fd600e526f43e/docs/adr/0029-derive-preparation-runs-from-action-events.md)의 run/action 기반 시간 계산과 [ADR 0025](https://github.com/DevKor-github/OnTime-front/blob/63913cd715a5bf35c5495619ad8fd600e526f43e/docs/adr/0025-calculate-punctuality-score-locally.md)의 점수 정책을 변경하지 않는다. 기간 출력 조건에 관한 좁고 되돌리기 쉬운 수정이므로 새 용어·CONTEXT 항목·ADR을 만들지 않는다.

## 확정 구현 계약

1. 결과 headline의 기간은 **초의 절댓값**을 사용한다. 부호를 텍스트에 다시 출력하지 않는다. 기존 `isLate` suffix와 색상은 그대로 유지한다.
2. 표시 정밀도는 분이다. 분 미만 초를 버려 0~59초는 `0분`/`0 minutes`로 표시한다. 반올림, 올림, `1분 미만`, 정확히 0초 전용 문구를 추가하지 않는다.
3. 시간은 1 이상이면 반드시 표시한다. 남은 분이 0이면 시간만, 남은 분이 있으면 시간과 분을 표시한다. 24시간을 0시간이나 날짜로 감지 않는다.
4. 실제 유일한 callsite를 `formatDuration(context, Duration(seconds: earlyLateTime.abs()))`로 연결한다. 기존 helper의 양수 Duration 계약을 활용한다. 다른 소비자의 음수 입력 의미까지 바꾸는 전역 formatter 수정은 하지 않는다.
5. 사용하지 않게 된 오타 helper `formatEalyLateTime`과 해당 낡은 테스트를 제거·대체한다. 모든 참조를 검색하여 stale import나 Widgetbook/테스트 참조가 남지 않게 한다. 새 formatter 계층, 동명의 복사 구현, 전체 파일 rename은 만들지 않는다.
6. 기존 KO/EN 단위와 단복수 표현을 재사용한다. 결과 기간만 U05보다 먼저 현지화한다. random 응원 문구나 전체 결과 번역, 12/24시간, 다른 화면 문구를 함께 고치지 않는다.
7. 완료 시점 계산, route의 초값과 `isLate`, Outcome/점수 저장, Bloc의 응원 문구용 ceil, timer 진행·재개·복원은 바꾸지 않는다. 정상 완료 경로에서 실제 부호 불일치를 재현한 증거가 발견되면 T04/C04에 연결하고, 단순 잠재성만으로 별도 버그를 단정하지 않는다.
8. 새로 길어진 결과 기간으로 직접 발생한 headline/버튼의 접근성 실패가 확인되면 필요한 최소 레이아웃 수정과 회귀만 포함한다. 기존 전체 결과 배치 문제는 U08에 근거와 함께 남긴다. 기존 실패를 성공으로 숨기거나 임의로 글자 배율을 낮춰 해결했다고 하지 않는다.

## 검증 실행과 완료 증거

- 먼저 실제 결과 widget의 ±3,600/±7,200 기대를 추가하고 기존 소스에서 실패를 확인한다. 공통 `formatDuration`이 이미 맞는다는 사실만으로 negative 증거를 대체하지 않는다.
- 수정 후 N01–N12의 실제 localization 기반 테스트와 V01–V09 관련 검증을 수행한다. RichText의 부분 단어 존재만 보는 약한 assert 대신 headline의 완성된 텍스트·의미를 확인한다.
- random 응원 문구는 테스트의 exact 기대에 넣지 않는다. 해당 문구의 선택기를 새로 만들거나 product 계산을 복제하지 않고 기간 headline을 정확히 검증한다.
- 화면 증거는 KO/EN, 초값, `isLate`, viewport, 글자 배율, source SHA를 함께 남긴다. widget 렌더와 실제 Android/iOS 실행을 구별해 기록한다.
- 실제 변경 범위에 맞춰 관련 테스트와 analyzer를 실행하고, 감사 통합 branch의 전체 테스트/CI에서 회귀 여부를 확인한다. 이미 검증한 고정 source 결과는 exact SHA가 같을 때 재사용하며 숫자를 추정하지 않는다.
- 로컬 수정, commit, PR CI, merge, 기기 적용 상태를 구분한다. 본문 작성만으로 구현·테스트 통과·배포 완료를 표시하지 않는다.

## 수용 기준

- [ ] 실제 결과 headline의 ±3,600/±7,200초가 각각 1시간/2시간이며 0분이 아니다.
- [ ] 3,601~3,659초, 직전·직후 분 경계, 음수와 24시간 이상을 N01–N12 계약대로 표시한다.
- [ ] 결과 기간은 기존 locale-aware formatter와 ARB를 사용하며 KO/EN 단복수·locale 전환이 정상이다.
- [ ] 제거된 오타 helper 참조가 남지 않고 별도 중복 formatter를 만들지 않았다.
- [ ] 실제 EarlyLateScreen의 수정 전 실패와 수정 후 성공이 있으며 helper 단위 성공만으로 끝내지 않았다.
- [ ] 초 버림, abs, 기존 suffix/색상/응원 문구 선택, 완료 계산과 저장·점수 정책을 유지한다.
- [ ] 작은 화면/200%의 직접 영향 표본·접근성 결과를 기록하고, 기존 U08 문제와 미실행 조건을 정확히 남겼다.
- [ ] 관련 회귀/analyze/통합 CI의 실제 source SHA 및 결과를 기록했다. 앱 전체 mobile E2E 완료 여부와 분리했다.

### Q1 — 표시 정밀도와 수정 범위

**전담 질문 원문**

> U04 Q1 — 실제 formatter는 abs(seconds)를 분 단위로 버리면서 hours>0 && minutes>0일 때만 시간 수를 넣어 ±3600/±7200뿐 아니라 ±3601~3659도 0분이 됩니다. 결과 화면의 부호(늦음/일찍), Outcome 저장, Bloc의 메시지 선택용 ceil은 별개입니다. 권고: U04는 기존 '절댓값, 초 버림, 0~59초=0분' 표시 정책을 유지하고, hours>0이면 분이 0이어도 시간을 표시(3600/3601→1시간,3660→1시간1분,7200→2시간)하며 부호/Outcome/메시지 범주 계산은 변경하지 않습니다. 59초→1분 올림이나 정확히0초 전용 문구는 별도 제품 결정으로 남깁니다. 이 좁은 계약으로 확정할까요?

**root 답변 원문**

> Q1 채택합니다.
