# Require a verified restore preview

Backup Restore will not replace active data immediately after file selection or password entry. OnTime will first decrypt the complete backup, authenticate its integrity, check its Backup Format Version, migrate it into a staging Local Data Store, and validate all represented data. Only then will it show a Restore Preview containing the Backup Cutoff, source app version, data categories and counts, and an explicit warning that the active Local Data Store will be replaced. Replacement requires a separate final user confirmation; cancellation removes staging data and leaves active data untouched. Preview metadata will remain inside the encrypted payload, while the plaintext envelope header will contain only the format identification and cryptographic parameters needed to derive a key and decrypt it. Immediate restore and plaintext descriptive metadata were rejected because they create avoidable overwrite and privacy risks.

D05's streaming implementation review permits provisional records in a separately owned, temporary encrypted ingestion store before final authentication. That store needs no active or original database and grants neither preview nor activation authority. Only final authentication, EOF and complete bounded data and relationship validation permit batch materialization into the existing normal-restore or recovery candidate. Recovery pair records and durable key slots keep their existing post-authentication lifecycle. This adds encrypted disk I/O and brief overlap between staging stores, but avoids whole-payload memory buffering and expanding the established recovery activation protocol to unauthenticated input. Transient ingestion tables are not part of the active or portable schema. Its key remains memory-only; cancellation, failure and abandoned-file cleanup retain the existing ownership and confirmed-cleanup requirements. Plaintext temporary files remain prohibited.

D05 implementation question 5 distinguishes structural validity from historical time-zone reproducibility. Portable formats 1 and 2 do not identify the producing time-zone database. The recurrence engine counts an ordinal after gap and preparation-start filtering; excluded occurrences still consume their original ordinal. Recomputing every historical ordinal with the current database could therefore reject legitimate history. Strict civil calendar and rule membership, segment generation bounds with the constrained retained-reference exception below, count bounds, slot/ordinal uniqueness and ordering across represented schedules and exclusions, definition ownership, references and override consistency remain mandatory. An ordinal cannot exceed the number of calendar-valid rule candidates up to that slot, irrespective of time-zone filtering. Validation traverses only as far as the maximum referenced slot and charges its work to the shared budget.

For otherwise structurally valid past or completed occurrences, disagreement attributable to the missing historical time-zone provenance preserves the original values and produces an explicit, bounded uncertainty report in the preview. This is not proof of an exact historical ordinal reconstruction. For future occurrences, such disagreement blocks readiness and activation until an explicit staging-only review and complete revalidation; it never silently changes ordinals, exclusions or historical records. The A10 review path remains required work, not an assumed capability of the validator. A past null offset remains null: where the supported civil carrier plus or minus 24 hours is entirely before the fixed validation instant, a current gap or overlap does not turn that history into a future choice. A range straddling the present requires explicit review rather than an invented instant. This preserves portable historical data without relaxing provable structural invariants or granting uncertain future schedules activation authority.

### Legacy offsetless metadata and completion instants (D05 implementation Q6)

The old exporter emitted `cutoff` and `finishedAt` using `toIso8601String()` without forcing UTC, while `startedAt` explicitly used UTC. Some legitimate legacy files therefore omit the time-zone offset. Interpreting those strings in the restoring device's zone invents provenance and can normalize a DST gap. Schema 4 stores completion/start instants as epoch seconds and cannot retain an offsetless civil value plus its uncertainty without a further schema decision.

An offsetless cutoff is accepted only as strictly validated literal metadata with an explicit uncertainty flag. Its UTC carrier is not an instant: the preview must not apply `toLocal()`, and freshness/reminder/history classification must not compare it as a known timestamp. If the restored installation needs local durable-data markers in this case, it uses the actual restoration operation's current timestamp, without claiming that the backup was created at that time. Explicit-offset cutoff values retain their normal validated semantics.

Offsetless non-null `startedAt`/`finishedAt` blocks ready/apply as unsupported representation, preserving the source and active database. The app does not substitute the device zone, schedule zone or present-day offset. Explicit UTC/offset inputs must satisfy strict date, UTC year and existing database precision boundaries. New exports always emit explicit UTC for these instants and cutoff. A10 must provide explicit staging-only user resolution followed by complete revalidation; until connected, this is an acknowledged legacy compatibility limitation rather than a completed review flow. No new payload or schema is introduced by this decision.


### Preserve civil fields at the backup boundary without changing runtime semantics (D05 implementation Q7)

A provisional implementation changed the global database civil converter to return UTC DateTime carriers, preserving foreign-zone wall-clock components across device DST gaps. Existing consumers still treat that value as an instant, including null-offset conversion, countdowns, upcoming selection and adjacent/date-range comparisons. Changing only DAO expectations would conceal a product regression: a Seoul 09:00 civil reading returned as 09:00Z would be interpreted nine hours later by those consumers.

D05 restores the previous global converter and existing runtime expectations. Export snapshots, ingestion validation, candidate materialization and normal/recovery raw row copying preserve and validate the raw SQL civil text without a local DateTime normalization round trip. Verification must cover raw persisted values and portable re-export components on a device zone whose DST gap differs from the schedule zone. Earlier typed UTC-carrier readback evidence remains an intermediate result of the superseded implementation, not final D05 proof. A10 owns an explicit civil value/instant boundary and coordinated correction of all consumers with Seoul/New York regressions. D05 does not claim to fix existing runtime DST normalization. This narrower boundary prevents the bounded-backup work from introducing a new nine-hour runtime shift while retaining the evidence needed for the subsequent domain-wide correction.


### Authenticated time review and retained references (A10 implementation Q1–Q4)

An authenticated ingestion store that passed final authentication, EOF, strict JSON and resource admission may enter a separate time-review state before complete semantic validation. It retains the existing resource lease and grants no verified-preview, AppDatabase, active-pair or activation authority. Editing is limited to version-bound, explicitly identified time fields: a bounded schema-valid unknown zone, civil/occurrence choices, and strictly valid offsetless start, finish or template instants. The original literal remains in encrypted staging. Cutoff uncertainty stays metadata and does not require inventing a creation instant. Authentication, JSON, resource, ID, graph and ownership failures cannot be reclassified as repairable time choices. Independent structural checks run where possible, and the UI states when complete validation is still pending. Each edit invalidates the old preview; complete relationship, resource and time validation must precede a new preview. Process death loses the memory-only key and requires owned-file cleanup and source reselection, not a new durable repair journal.

The earlier blanket requirement that every stored recurrence reference lie before `beforeSlot` conflicts with the existing following-edit/delete workflow. Source review found that `_closeFollowing` closes generation at the anchor while protected schedules and exclusion tombstones can remain attached to the old segment. This finding is a source-based contract correction; an actual workflow-to-backup failing regression is required before claiming the defect reproduced or fixed. `beforeSlot` is the exclusive bound for additional generation. A closed segment may retain references at or beyond it only for evidenced protected/history schedules or exclusion tombstones. Original `fromSlot`, calendar/rule membership, count and calendar-ordinal upper bounds, combined slot/ordinal uniqueness and ordering, definition ownership, references and override consistency remain mandatory. An ordinary unstarted, unfrozen, incomplete future schedule does not qualify. These retained references grant no new materialization, start, reactivation or notification authority. Missing producing-rule provenance permits an explicit historical uncertainty report, never silent renumbering. Portable formats cannot prove the reference existed before closure; the limited semantics do not pretend otherwise.

The checked current and historical start writers store `startedAt` and the frozen flag together. No legitimate producer of a frozen-only portable row was found in that investigation. The existing portable invariant is therefore retained rather than relaxed for an invented compatibility case. An ambiguous active-store row is preserved with an explanation and no automatic execution; it is not deleted to make validation pass.

When future recurrence rules or ordinals need correction, a confirmed bounded following-edit plan closes the old generation interval and creates a service-owned new segment in the same series. Protected/history data and original tombstones retain their meaning. Existing materialized schedule IDs remain stable, and the proposed segment/slot/ordinal mapping is shown before confirmation. Matching overrides and exclusions carry forward; unmatched overrides require an explicit standalone-preservation decision, and unmatched exclusions remain represented with their lost applicability disclosed rather than silently resurrecting a deleted occurrence. A remaining finite count is inherited only when its derivation is provable; otherwise the user chooses a new remaining count or end. Arbitrary ID/ordinal/JSON editing is prohibited. Candidate changes are atomic and followed by complete revalidation within the existing work budget, without unbounded recurrence expansion or calling an active-store repository from staging.

Each validation pass has a fixed UTC instant. A candidate edit, active-store baseline change, loaded-rule identity change, or crossing a relevant time predicate boundary invalidates its preview and requires a complete new validation pass. A clock moving backwards before the validation instant also invalidates that authority. Final claim rechecks those conditions before replacement. A device-zone display change alone is not a durable interpretation change. This is not an arbitrary TTL or a request to revalidate every tick. These decisions are accepted requirements; the editing UI, common consumer gates and regression evidence remain A10 implementation work.

### Deterministic mapping of already materialized future schedules (A10 follow-up)

The confirmed following plan reserves matching original civil dates for overrides, exclusions and protected references before mapping ordinary unprotected materialized rows. It maps the remaining rows in original slot/ordinal order, with schedule ID as the deterministic final tie-breaker, to the remaining available new slots in order. The preview exposes every changed segment/slot/ordinal association while retaining schedule IDs. Protected references remain attached to the old segment with their recorded history unchanged; the new plan must not leave ordinary unprotected future rows in its closed tail.

If a changed rule, count or end leaves too few slots, the plan preserves unmatched ordinary rows and overrides as standalone schedules only after explicit confirmation. Their IDs, content and preparation ownership remain intact. This correction flow does not add a deletion option. Unmatched exclusion tombstones retain their original record and disclose that they no longer apply to the new rule; they are not silently recreated. The new segment count describes its slots, including the existing consumption by matching exclusions, while detached standalone schedules are counted separately. A provable inherited remaining count and an explicitly changed count are distinct; missing provenance still requires an explicit remaining count or end.

A time override consists of the civil fields, named schedule zone and selected offset together. Following edits cannot preserve only civil/offset while replacing that override's zone with the new segment default. These accepted details supplement the original Q2 decision. Their actual question and answer are recorded in `plans/audit-2026-09-23/a10-implementation-followups.md`; this section does not claim the new plan or its tests are complete.

The automatic remaining-count proposal is limited to a single open finite segment whose anchor ordinal passes the stored calendar/count/combined-reference invariants and matches a bounded current-rule scan with the same generation start, preparation threshold and lead. Its value is `old count - anchor ordinal + 1`, including the anchor. That is a calculation from the preserved count/ordinal contract and current anchor agreement, not proof of the missing historical time-zone provenance. Unknown or skipped anchors, changed future ordinals, several open following segments or unavailable evidence require explicit count/end selection. A resource-budget failure cannot be bypassed by entering a count.

The correction plan reuses the anchor's existing series-owned preparation definition. Existing valid occurrence-owned preparation overrides retain their IDs, owners and contents. A future row using a different series-owned definition is included in the explicit standalone-preservation review rather than silently cloning or changing ownership to fit the new segment. This avoids relaxing the portable preparation-ownership invariant or introducing multiple artificial segments. The standalone reference must still pass complete portable validation; the decision is not authority to waive that check.

### Removed time-zone rules on historical recurrence segments

A schema-valid unknown zone on an original recurrence prototype/segment may be preserved without rewriting its rule, boundaries, slot identities, ordinals, preparation ownership or tombstones only when conservative civil/allowed-offset bounds and explicit boundaries prove that the segment cannot generate a future occurrence at the fixed validation time. A closed segment whose `beforeSlot` is still in the future is a counterexample: being closed alone is insufficient. A count alone also does not prove that no future occurrence remains. Open or potentially future unknown rules require explicit known-zone time review and a bounded future plan followed by full validation, even when no future rows have been materialized.

Preservation still checks strict calendar and zone-independent rule membership, count bounds, combined slot/ordinal uniqueness and ordering, IDs/ownership, and the existing explicit retained-reference exception. Exact historical ordinal reproduction that depends on unavailable zone rules is disclosed as uncertain historical recurrence provenance, never as a newly verified rule. It grants no new materialization, start or alarm authority. A separately overridden future unstarted row remains subject to its own future-time checks; it cannot inherit a historical-segment exemption. Malformed graphs, exhausted budgets or absent proof remain failures. This is an accepted implementation decision; staged repair verification remains pending.
