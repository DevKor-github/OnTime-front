## 확정 동작

### 1. 삭제 가능한 대상과 범위

1. 정상 완료, 지각 완료, 비정상 완료, 준비 중이 아닌 과거 미완료 일정에 개별 삭제를 제공한다. 날짜가 오래됐다는 이유로 자동 삭제하지 않는다.
2. 반복 이력에서 삭제 대상은 **이 회차만**이다. 다른 과거/미래 회차, 반복 규칙, 공용 준비를 보존하고 해당 slot의 재생성만 방지한다. 이력 진입점에는 ‘이 회차와 이후’를 제공하지 않는다.
3. 미래 미진행 회차의 기존 범위 선택은 보존한다. 종료 이력의 일반 편집을 허용하는 변경은 아니다.
4. 실제 유효한 Preparation Run/Early Start를 포함한 준비 중 일정은 일회성/반복 모두 삭제를 차단한다. 준비 화면 복귀 또는 먼저 종료 안내를 제공한다. **일회성 started 삭제를 허용하던 기존 동작과 테스트를 의도적으로 변경한다.**
5. stale `isStarted`와 실제 유효 run 불일치는 고아 상태 검증/복구 문제다. 임의 완료 처리나 강제 삭제로 해소하지 않는다. 삭제 eligibility는 UI 추정만이 아니라 실제 실행 경계에서 검사한다.
6. 확인 화면은 선택 이력 식별, 원문 영구 삭제, 다른 일정 보존, 기존 점수 집계 유지, 앱 내 undo 없음, 외부 과거 백업 복원 시 재등장 가능성을 정확하게 설명한다. 취소하면 DB·revision·runtime·OS 요청이 바뀌지 않는다.

### 2. 데이터 삭제 transaction과 공유 원문

1. 실제 참조 그래프를 읽어 선택 Schedule, outcome 상세, schedule 고유 이름·메모·준비 및 관계를 하나의 로컬 데이터 transaction으로 제거한다. 연결 리스트 FK는 안전한 순서로 해제한다.
2. Place/Preparation definition은 다른 Schedule, Recurring Segment, Default Preparation, 사용자 템플릿 등 살아 있는 소유/참조가 없는 **해당 삭제로 영향받는 데이터만** 정리한다. 공유 판단은 ID 참조 기준이며 이름 일치로 추정하지 않는다.
3. 공유 콘텐츠는 다른 기능의 독립된 소유 데이터로 보존한다. 반복 segment 자체의 공통 이름/장소/준비가 남는 것은 선택 회차 상세를 몰래 보관하는 것과 구분한다. 선택 회차 override 등 독점 원문은 남기지 않는다.
4. 관련 없는 기존 고아 데이터를 전역 청소하지 않는다. 다른 회차·템플릿·기본 준비를 삭제하지 않는다.
5. 이미 등록된 On Time/Late aggregate, 점수 reset boundary, 다른 결과는 불변이다. Abnormal outcome은 점수 기여를 새로 만들지 않는다. 삭제된 일정 ID나 상세가 점수 명목으로 남아서는 안 된다.
6. 성공한 의미 있는 삭제는 durable revision을 정확히 1회 갱신한다. 동일한 삭제 의도의 이미 완료된 재시도는 no-op이며 revision 0회다. DB 단계 실패는 전체 rollback으로 기존 내용·점수·revision을 보존한다.
7. 반복 재생성 방지에는 도메인에 필요한 segment/slot/ordinal 최소 키만 남긴다. 삭제 일정 ID·이름·메모·개별 준비·결과 원문은 exclusion에 보관하지 않는다. 기존 count/ordinal/slot 소비 규칙을 유지한다.
8. 새 Backup Cutoff 이후 만들어진 백업에는 삭제한 개별 원문이 없다. 독립적으로 공유되는 정의와 점수 집계는 남는다. 이전에 내보낸 외부 파일은 변경하지 않는다. 명시적인 오래된 백업 복원은 삭제 전 이력을 재도입할 수 있다.

### 3. stale 확인·멱등성과 알림 정리

1. 확인된 삭제 의도는 대상 identity, 확인 당시 내용/상태 기준, data generation을 가진다. commit transaction에서 최신 기준을 다시 검사한다.
2. 확인 뒤 대상 수정·시작·완료·restore/reset·같은 ID 재생성이 있으면 typed stale/conflict로 거절하고 재조회 및 새 확인을 요구한다. 무관한 일정의 전역 revision 변화만으로 막지 않는다. 같은 ID라는 이유만으로 이전 삭제 의도를 새 객체에 적용하지 않는다.
3. 실제 OS 취소 식별자를 잃기 전에 A15/D03 공통 owner 아래 필요한 content-free ownership이 durable하게 보존됐음을 확인한다. journal 쓰기 실패 때문에 필요한 식별자 보존을 확인하지 못하면 DB 삭제를 commit하지 않고 안전한 오류를 반환한다. 단순 메모리 보존을 프로세스 사망 후 복구 보장으로 표시하지 않는다.
4. durable ownership이 보존된 이후 OS 취소 실패/unknown이면 DB 삭제 후 부분 결과가 가능하다. OS 작업을 DB transaction으로 옮기거나 둘이 원자적이라고 주장하지 않는다. 기존 pending actual provider ID와 최소 schedule ID 외에 원문·payload·fingerprint를 남기지 않는다.
5. commit 후에는 삭제 행을 재생성하지 않는다. 목록에서 지워진 사실을 유지하며 ‘이력 삭제됨, 알림 정리 확인 필요’와 명시적 재시도를 제공한다. 모든 표적 취소 확인 뒤 최소 소유권도 제거한다.
6. journal/registry 실패, unknown ownership, 응답 없는 provider를 완료로 표시하지 않는다. timeout은 사용자에게 지연을 알리는 수단이며 owner 해제나 OS 성공 근거가 아니다. 무차별 cancelAll 또는 동일 ID의 새 예약 중첩을 만들지 않는다.
7. 부분 결과 재시도는 현재 generation의 같은 정리 의도를 처리한다. DB 재삭제·revision 증가 없이 공통 owner의 cleanup을 재시도한다. old generation의 완료 callback은 새 DB/UI/registry에 영향을 주지 않는다.
8. runtime/Early Start의 해당 일정 상태는 공통 무효화/정리 규칙에 따라 제거한다. 오래된 callback이 삭제 이력을 다시 보여 주거나 다른 일정의 run을 지우지 않도록 검증한다.

### 4. 화면·접근성·오류

- swipe 삭제 외에 스크린리더·키보드로 접근할 수 있는 명시적 삭제 액션 또는 동등한 semantics action을 제공한다. 동작 이름과 대상이 읽혀야 한다.
- 한국어/영어 확인·성공·부분 결과·실패·준비 중 안내를 구분한다. 200% 텍스트와 작은 화면에서 버튼과 핵심 설명이 접근 가능해야 한다.
- 빠른 연타, 여러 액션 경로, 늦은 callback은 한 확인 의도에 대해 single-flight로 처리한다. 새 generation의 화면은 오래된 완료로 닫히거나 바뀌지 않는다.
- DB 실패는 기존 이력이 유지된 상태로 오류를 알리고 재시도할 수 있다. commit 후 OS 부분 결과를 ‘이력 삭제 실패’로 표시하거나 이력을 되살리지 않는다.
- 예외 원문, 내부 경로, DB/OS 구현 문자열을 사용자에게 노출하지 않는다. 장기 보관함/휴지통/undo/자동 retention을 추가하지 않는다.

## 구현 순서와 의존성

1. 삭제 eligibility와 확인 대상 identity/generation의 계약 및 typed 결과를 domain/use case에 정의한다. 기존 future 삭제·반복 following 정책과 이력 단일 삭제를 구분한다.
2. DAO/repository 참조 그래프와 FK를 실제 데이터로 검증하고 atomic 삭제, 공유 참조 보존, 점수 불변, 정확한 revision, 멱등을 구현한다.
3. A15/D03 owner의 durable ownership 확인 → DB commit → 취소/부분 결과/명시 재시도를 연결한다. 같은 기능의 두 번째 queue 또는 전역 cancelAll 경로를 만들지 않는다.
4. 일회성/반복 UI를 동일한 삭제 결과 계약으로 연결하고 스크린리더 접근, KO/EN 문구, 처리 중 중복 방지를 추가한다.

### Q3 — DB commit·OS 취소·stale 확인과 접근성

**전담 서브에이전트 질문 및 문구 제안**

> Q3: 삭제 확인 후 DB commit과 OS 취소를 하나의 성공으로 표시하지 않겠습니다. 권고: 삭제 intent는 확인 시 schedule identity+최신 내용/상태 기준+현재 data generation을 고정하고 transaction에서 재검사합니다. 확인 뒤 수정/시작·완료/restore/reset/같은 ID 재생성이면 typed stale/conflict 후 재조회·다시 확인하며 대상 바뀐 삭제는 실행하지 않습니다(무관 일정 revision은 차단 사유 아님). commit 전 실패는 전부 유지, commit 후 데이터는 재생성/롤백하지 않고 목록에서 제거한 상태로 ‘이력 삭제됨, 알림 정리 확인 필요’와 명시 재시도를 제공합니다. OS 정리는 A15/D03 공유 owner+actual provider ID+내용 없는 pending ownership에 맡기고 성공 확인 뒤 최소 삭제ID도 제거합니다. journal 자체 실패/unknown ownership/응답없는 provider는 완료 표시 금지, timeout으로 owner해제·cancelAll·새 예약 중첩 금지입니다. 이력별 재시도는 DB를 다시 삭제하거나 revision 올리지 않고 같은 현재세대 cleanup만 재실행하며, oldgeneration callback은새데이터/UI/registry를건드리지않습니다. 화면은 swipe 외에 스크린리더/키보드로 접근 가능한 삭제 액션, KO/EN·200% 글자·연타 single-flight·확인취소 무변경을 포함하고, ‘되돌릴 수 없음’은 앱 내 undo 없음과 외부 옛백업 복원 가능성을 구분합니다. 이 계약을 채택할까요?
>
> 문구 제안: CONTEXT relationship은 “Deleting a Schedule removes its details and its exclusively owned content; content still owned or referenced by another Schedule, Recurring Schedule, default Preparation, or Preparation template is retained for that independent purpose. Only minimal content-free delivery ownership may remain while cancellation is unresolved, and it is removed after cancellation is confirmed.” ADR0034는 ‘atomically ... local delivery registrations’를 ‘The selected Schedule and its exclusively owned details are removed in one local-data transaction; shared content remains while independently referenced. Operating-system delivery cancellation is a separate recoverable operation, and unresolved cancellation retains only the minimum content-free ownership needed to finish cleanup, with no claim of completed delivery removal.’로 정합화 권고입니다.
