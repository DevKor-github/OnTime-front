## 공식 문서로 확인한 경계

- [GitHub branch rules REST API](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch)는 active 규칙을 상위 수준까지 포함해 반환하며 disabled/evaluate 규칙은 제외한다. 존재하지 않는 branch 이름도 효과 조회가 가능하다. 그래서 규칙 목록, 상세, effective 결과를 각각 읽는다.
- [GitHub available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)는 PR review·예상 GitHub App·strict 최신 base·force/delete 규칙을 설명한다. settings 저장 성공과 개별 PR 차단은 별도 확인한다.
- [GitHub required-check 문제 해결](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)은 latest SHA, head/test-merge 구분, 최근7일 성공, skipped/neutral 허용, 조건 skip과 실패 dependency의 위험, dispatch-only check의 PR requirement 불충족, merge_group 필요를 명시한다. 이슈는 **GitHub 기본 성공 판정보다 강한 실제 suite 실행 gate**를 R02/R04에 요구한다.
- [GitHub ruleset 생성](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)은 fnmatch에서 `/` 경계, active 즉시효과, bypass를 설명한다. 단순 `*`나 검증하지 않은 `**` 문자열만 보고 모든 중첩 branch가 보호된다고 말하지 않는다.

위 공식 근거는 정책 설계를 위한 읽기 결과다. 실제 repository에서 보호를 적용·시험했다는 증거가 아니다. strict local-only/Android·iOS 제품 범위는 기존 [ADR0016](https://github.com/DevKor-github/OnTime-front/blob/28baf6c7b91c00d2c6490f597375c1dad39fc2b6/docs/adr/0016-support-local-only-on-android-and-ios.md)·[ADR0024](https://github.com/DevKor-github/OnTime-front/blob/28baf6c7b91c00d2c6490f597375c1dad39fc2b6/docs/adr/0024-enforce-no-network-in-product-builds.md)를 유지한다. GitHub 검증 도구의 network 사용을 앱 runtime network 허용으로 확대하지 않는다.

## 확정 정책

### 보호 대상과 review

1. 기존 repository ruleset **2100824**를 백업·fresh drift 확인 후 재사용한다. target은 branch, enforcement는 최종 active다. main을 명시하고 `refs/heads/release/**`, `refs/heads/hotfix/**` 계열을 포함한다. default branch alias를 유지할지 정확 main도 포함할지 최소 payload에서 명시하며 main 보호 누락을 허용하지 않는다.
2. 단일 이름(`release/v1`, `hotfix/fix`)과 중첩 이름(`release/team/v1`, `hotfix/team/fix`)을 각각 effective API로 확인한다. 필요하면 `refs/heads/release/**/*`, `refs/heads/hotfix/**/*`를 함께 사용한다. 대상 외 `feature/example`, 유사 접두사 `release-not-a-target/example`은 실수로 잠그지 않는다. matcher fixture, 가상 이름 effective 조회, 실제 branch 효과를 구별한다.
3. PR을 필수로 하고 **작성자 및 최종 pusher와 다른 적격 reviewer 1명**의 최신 변경에 대한 승인을 요구한다. stale approval 해제, last-push approval, unresolved conversation 차단을 설정한다. agent 자체 검토는 GitHub 적격 review를 대신하지 않는다.
4. force push와 branch deletion을 막고 필수 검사는 strict latest-base로 강제한다. 정상 PR 병합까지 막는 `Restrict updates`나 새 branch 생성 차단을 의미 없이 추가하지 않는다.
5. 상시 admin/role/app bypass 목록은 두지 않는다. 혼자 작업해서 approval을 구하지 못해도 self-approval, 위조 review, 자동 bypass/보호 해제로 해결하지 않는다. admin API 권한 자체는 동의나 reviewer 가용성을 증명하지 않는다.
6. CODEOWNERS, signed commits, linear history, merge queue를 이번에 새로 강제하지 않는다. 기존 허용 merge 방식과 관련 없는 정책은 보존한다. queue는 R02/R04 merge_group 실제 지원·실행 증거와 별도 운영 선택 이후에만 적용한다.

### 필수 check와 실제 실행 판정

| 품질 범위 | 현재 시작점 | 최종 requirement |
|---|---|---|
| Flutter quality | 실제 context `test`, github-actions App15368 | R04 공통 품질의 generator/정책/analyze/full unit-widget/coverage80·필수 결과를 검증하는 안정적인 실제 context |
| Android release manifest | 실제 context `release-manifest`, 같은 App15368 | 실제 release APK·packaged/merged manifest·identity 결과를 검증하는 context 유지 또는 검증된 후속 context |
| Android·iOS build/native/core smoke | 현재 미제공 | R02의 실제 필수 child/result를 검사하는 mobile aggregate context. T01/T02 미제공 행이 있으면 완료 아님. |
| Widgetbook·Play deploy·수동 dispatch-only | 보호 requirement에서 제외 | catalog 배포나 실제 store 작업을 모든 PR의 조건으로 만들지 않음. 별도 R03/R04/R05/R07/R08 경계 유지. |

- 최종 context 문자열은 상상한 이름이나 workflow title로 정하지 않는다. 실제 `pull_request` run의 check-runs, event, App ID, latest head/base/test-merge SHA에서 읽는다. 최근7일 성공 조건과 중복 job/status context를 확인한다. 동일 이름의 status/check가 혼재하면 모호성을 없앤다.
- App source를 실제 github-actions **15368**로 묶는다. 다른 integration/manual status로 같은 이름만 올려 requirement를 만족시키지 못하는지 확인한다. Actions App 바인딩은 동일 App이 발행한 다른 workflow의 변조·의미 없는 green까지 방어하지 않는다. workflow/gate 변경도 독립 리뷰 대상이며 이 보안 한계를 숨기지 않는다.
- required 설정만으로 skipped/neutral을 막을 수 없다. R02/R04 aggregate는 `always()`로 실행하고 필수 child **success**, expected case 수·목록, 필수 report, 같은 source/checkout identity를 확인해야 한다. skipped/neutral/cancelled/missing/0 tests/dependency pending은 gate failure 또는 검증 미완료다. 전체 run이 취소되어 aggregate도 미실행이면 완료로 보지 않는다.
- 다른 workflow를 조회하지 않은 aggregate가 전체 품질의 유일한 권위가 되어서는 안 된다. 필요한 독립 check들은 각각 required로 남기거나 검증된 동일 DAG에 통합한다. 이슈가 workflow 사이 결과를 자동으로 알아낸다고 가정하지 않는다.
- head의 과거 green, 다른 test-merge, dispatch-only 성공으로 최신 PR requirement를 대체하지 않는다. 최신 base 변경도 strict policy에 따라 재검증한다. PR head/base/실제 checkout/test-merge를 별도 필드로 기록한다.
- 문서-only/draft/fork도 필수 검사가 사라지지 않게 R02/R04 trigger를 유지한다. fork 승인 대기는 pending이다. untrusted PR에 production secret을 주거나 privileged event로 검사를 우회하지 않는다.

### 전환·적용 절차

1. 실행 가능한 기존 checks로 부분 보호를 적용할 수 있으나 **부분 보호 != 최종 R01 완료**다. T01/T02/R02/R04가 아직 제공하지 않은 필수 suite는 가짜 green이나 skip job으로 채우지 않는다.
2. rename 또는 reusable workflow 전환 시 **새 실제 context를 PR에서 성공 → 새 requirement 적용/read-back → 기존 context 제거** 순서를 지킨다. 그 사이 전체 품질 gate가 사라지는 빈 구간을 만들지 않는다. obsolete context 때문에 영구 pending이 되는 것도 확인한다.
3. 변경 전 원격 원본·rule source/ID·enforcement·matcher·bypass·legacy/effective와 exact payload diff를 준비한다. 적용 대상 branch, 현재 열린 PR에 미칠 lockout, 적격 reviewer 가용성, 복구 방법을 검토 가능한 상태로 만든 뒤 운영 정책 변경 권한을 판단한다. 이 설계 문서나 admin=true만으로 실제 설정 mutation을 이미 허가받았다고 간주하지 않는다.
4. 적용 직전에 다시 읽어 baseline 이후 다른 관리자가 바꾼 내용을 덮어쓰지 않는다. 변경이 생기면 최소 diff를 다시 계산한다. 원본을 백업했다고 전체를 기계적으로 PUT하여 새 필드/상위 정책을 지우지 않는다.
5. 적용 뒤 API 성공 응답만 보지 않고 ruleset 상세와 main/현재 release·hotfix의 effective rules를 재조회한다. 상위 organization/다른 규칙과의 조합, 제외 패턴, bypass, 최종 context/App/strict 값을 확인한다.
6. 문제가 생겨도 disabled 원본으로 자동 rollback하여 보호를 전부 끄지 않는다. 확인된 문제 delta만 권한 하에 수정하고 전후 결과를 남긴다. 문서에 rollback 명령이 있다는 이유로 무조건 실행하지 않는다.

## 검증 방법과 실패 행렬

main·실제 release/hotfix에 실패 코드를 넣거나 force push·delete·시험 merge를 수행하지 않는다. 먼저 read-only PR mergeability와 effective rule 증거를 수집한다. 차단 동작의 실제 negative가 필요하면 **명시 소유의 disposable target/PR와 동등한 검증 규칙**을 사용해 예상 외 성공도 제품 branch에 영향을 주지 않게 한다. 이 격리 대상 변경 역시 실제 수행할 범위·정리와 운영권한을 먼저 확정한다. 현재 조사에서 그런 branch/PR/ruleset은 생성하지 않았다.

| ID | 자극·상황 | 기대 결과와 증거 수준 |
|---|---|---|
| RP01 | disabled/list 존재와 effective[] 비교 | disabled를 active 또는 규칙 전체 부재로 오판하지 않음. 원격 readback으로 현 baseline 확인됨. |
| RP02 | main·기존 release/hotfix 및 가상 단일/중첩 이름 | 최종 active 정책의 같은 필수 rule 적용. 비대상 feature/유사 접두사는 불필요하게 잠기지 않음. 가상 matcher는 write 차단 증거가 아님. |
