# [P1][A06] 실제 준비 타이머 경로에서 단계 전환 알림을 판정하고 지연·복귀 알림 재생 방지

## 문제와 사용자 영향

준비 진행 화면은 1초마다 현재 시각으로 진행 상태를 다시 계산하지만, 실제 타이머가 보내는 `SchedulePreparationTimeRefreshRequested` 처리에는 단계 변경 알림이 없다. 알림 호출은 별도 `ScheduleTick` 처리에만 있다. 따라서 테스트에서 Tick을 직접 넣어 성공해도 정상 앱 타이머에서 단계 알림이 전달된다는 증거가 되지 않는다.

이번 수정은 단순히 refresh handler에 알림 함수를 추가하는 작업이 아니다. resume 역시 같은 refresh 이벤트를 보내므로, 원인을 구별하지 않으면 앱을 다시 연 순간 지나간 준비 단계 알림이 울릴 수 있다. 현재 서비스는 `resumed` 이외의 lifecycle을 모두 허용하고, Future를 버리는 callback 뒤에 성공을 의미하는 로그를 남긴다. 알림 허용 여부, 발송 시도, OS 표시 성공을 서로 구분해야 한다.

제품 결과는 **앱이 실행 가능하며 관찰한 신선한 자동 단계 전환에서 최대 한 번 OS 알림을 시도하는 것**이다. foreground에서는 기존 준비 화면으로 전환을 표시한다. 실제 background에서 실행되지 않은 timer나 앱이 suspend/kill된 동안 모든 단계의 정시 전달을 새로 보장하지 않는다.

## 확정 정책

### 실제 전환과 지연 보정

1. refresh 원인을 periodic/resume/restore 등으로 명확히 구별한다. 기존 시간 파생 로직을 공통으로 사용하며 Tick에 따로 누적 시간을 적용하여 또 다른 진행 기준을 만들지 않는다. 레거시 Tick이 유지되더라도 동일 전환의 알림을 별도로 발생시키지 않는다.
2. 준비 진행 계산은 기존대로 run 시작 + Preparation Action Events + wall clock이 기준이다. 단조시간은 **알림의 신선도**에만 사용한다. timer tick 수를 진행 시간이나 영속 이력으로 저장하지 않는다.
3. periodic 관찰에서 단조시간상 직전 관찰 후 **2초 이하**이고, 동일 run에서 인접한 다음 한 단계로 전환했으며, lifecycle이 계속 실제 `paused`로 관찰된 경우만 OS 알림 후보이다. 정확히 2초는 포함하고 초과는 제외한다. 상수·이유 주석·경계 테스트를 둔다.
4. phase 변경 직후 첫 관찰은 연속 background라고 간주하지 않는다. 기준점만 갱신한다. `resumed`, `inactive`, `hidden`, `detached`, unknown에서는 OS 단계 알림을 보내지 않고 이후 재생하지 않는다.
5. cold restore, resume, 2초 초과 지연, 한 번에 여러 단계 이동, wall clock 역행/큰 변경과 monotonic delta 불일치에서는 현재 진행만 반영한다. 지나간 단계나 현재 단계의 늦은 알림을 순서대로 재생하지 않는다. clock 변화 판정의 허용오차는 구현 주석과 검증에 명시하여 실제 시계 변경을 일반 timer jitter로 취급하지 않도록 한다.
6. 최초 단계, 수동 skip 결과, 마지막 단계 종료, 이미 끝난 준비에는 단계 전환 알림을 만들지 않는다. 수동 skip 후 다음 단계의 실제 자동 전환은 새 후보로 독립 판정한다.
7. foreground에서 화면이 갱신된 전환도 나중에 background로 갔다는 이유로 알림을 다시 만들지 않는다.

### 설정의 의미와 OS 표시 권한

- **Schedule Notification Setting**은 CONTEXT의 기존 정의대로 upcoming 준비 시작 예약을 제어한다. A06이 active preparation 단계까지 이 설정의 의미를 확대하지 않는다. 새로운 단계 알림 설정도 추가하지 않는다.
- 따라서 준비 시작 예약을 OFF해도 이미 실행 중인 준비의 단계 알림을 자동 중지하거나 blanket 취소하지 않는다. 이는 D03의 일반 OFF가 준비 단계/다른 목적 알림을 일괄 취소하지 않는 경계와 일치한다.
- OS 표시 권한은 독립된 경계다. 표시 권한 거부 또는 조회 실패이면 OS 단계 알림을 생략한다. 진행 UI는 정상 갱신하며 자동 OS 권한 팝업은 열지 않는다. provisional 등 기존 지원 상태는 현재 platform 계약으로 판정하고 권한 조회 결과를 표시 완료 증거로 오인하지 않는다.
- 실제 Q3 첫 답변의 설정 OFF 생략 정책은 뒤의 보충 답변으로 **철회**되었다. 아래 전체 문답에 첫 답변과 정정을 모두 보존하며 이 섹션이 최종 정책이다.

### 최대 한 번의 발송 시도와 비동기 유효성

1. 후보의 identity는 data generation + 실제 preparation run/session identity + schedule occurrence ID + step ID를 구별한다. 반복 일정 공통 Preparation ID만으로 dedupe하지 않는다. 서로 다른 회차가 같은 step ID를 써도 독립적으로 판정한다.
2. 같은 후보는 첫 await 이전에 원자적으로 소비하여 timer/legacy Tick/stream 중복 이벤트의 동시 처리에서도 최대 한 번만 시도한다. ‘소비’는 OS에 실제 표시됐다는 뜻이 아니다.
3. 동기 throw와 Future error를 모두 관찰한다. 실패나 불확실성을 성공으로 기록하거나 unhandled error로 진행을 중단시키지 않는다. error 종류만 민감정보 없이 진단한다.
4. 설정 조회가 아니라 **표시 권한**, setup 등 필요한 await 뒤 실제 show 직전에 session, generation, lifecycle, 신선도와 currentness를 재검사한다. 종료·삭제·새 prompt/session·reset/restore로 무효화된 작업은 새 OS 호출을 하지 않는다.
5. 검사를 통과한 뒤 OS 호출 전 불필요한 await를 끼우지 않는다. 이미 OS가 수락한 호출을 Dart Future 취소만으로 철회했다고 주장하지 않는다. 반환 중인 OS 부작용과 reset/restore 정리는 선행 A15/D03의 공유 직렬화/소유권 경계에 맞춰 통합한다.
6. 실패한 단계는 자동 재시도하거나 resume 때 늦게 재생하지 않는다. 다음 새 단계는 정상 판정한다. durable delivery/outbox·영속 단계 전달 이력은 추가하지 않는다.
7. run 복원 시 소비 집합이 메모리에 없다는 이유로 현재 단계 알림을 다시 보내지 않는다. 복원은 silent baseline이고 이후 실제 새 전환만 대상이다. 무효 세대/끝난 session의 메모리 tracking은 정리한다.

### 개인정보와 전달 결과

- OS 제목/본문은 기존 일반적인 준비 갱신 문구를 유지한다. Detailed Notification Content ON도 준비 이름/단계 이름 공개의 허가가 아니다.
- payload는 필요한 `type`, `scheduleId`, `stepId`만 사용한다. 일정·장소·note·준비 원문, 전체 runtime snapshot을 추가하지 않는다. 기존 A11 privacy 경계를 유지한다.
- 서비스 callback이 반환되기 전부터 `shown`으로 기록하지 않는다. 요청됨/생략/실패 같은 실제 관측 결과를 구별하고, plugin show 성공도 사용자가 OS 알림을 보았다는 보장이 아님을 검증 기록에 명시한다.
- A12 알림 tap의 현재 데이터 조회·세대 검증·실제 선택 일정 유지가 회귀하지 않아야 한다.

## 구현 범위와 의존성

포함: ScheduleBloc 실제 refresh 경로, 필요한 event origin/lifecycle 전달, 단조 관찰 시계 주입, 공통 파생 전환 판단, session/generation별 dedupe, 결과가 관찰되는 비동기 알림 경계, 표시 권한·currentness 재검사, 개인정보 유지, 실제 timer/lifecycle 테스트.

선행 순서: A13 → A14 → A15 → D03 후 A06 구현. A12의 선택 일정/session owner 및 generation 계약을 보존한다. A15/D03을 구현하기 전의 인터페이스를 가정하여 별도 scheduler/cleanup 경계를 복제하지 않는다. 구현 시 새 소스에 맞춰 이슈의 구현 파일 범위를 갱신한다.

제외: background 실행 보장, 종료된 앱의 단계별 OS 사전예약, background service/새 receiver, durable outbox, 알림 재전달 보장, 사용자 준비 이벤트 정의 변경, 일반 폼/스케줄 저장 원자성(A07/A08), 새 단계 알림 설정. CONTEXT의 기존 용어를 바꾸지 않으며 이번 결정은 새 ADR 없이 이슈에 기록한다.
