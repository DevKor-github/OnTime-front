# [P1][R02] 일반 PR에 Android·iOS 빌드와 실제 native·앱 smoke CI를 연결하고 누락 검사를 실패로 판정

## 문제와 결과 목표

일반 PR에서 Dart 분석·테스트가 통과하더라도 Swift/Kotlin, native plugin 등록, 기기용 iOS 구성, OS 서비스 연결이 깨질 수 있다. Android release APK의 manifest 검사는 이미 추가됐지만 iOS 빌드와 실제 native test 실행, 두 모바일 플랫폼의 실제 앱 smoke는 현재 PR workflow에 연결돼 있지 않다.

R02는 **동일 PR 검증 소스에서 Android·iOS 빌드, 실제 native tests, 결정적인 앱 smoke를 실행하고, 실행하지 않은 필수 검사나 사라진 결과를 성공으로 표시하지 않는 CI**를 만든다. T01/T02의 테스트 entrypoint와 증거 schema를 배선하며 별도 테스트 제품이나 중복 suite를 만들지 않는다.

- 우선순위: **P1**, 감사 R02. 전담 grill agent: `/root/grill_r02`.
- 적용 skill: `/Users/ejunpark/.agents/skills/grill-with-docs/SKILL.md`.
- 고정 조사 source: **`d73c7863a01343004ccadcd72064b563c464dd0d`**. 병행 C01 WIP와 이후 HEAD의 실행 결과는 아래 고정 소스 증거가 아니다.
- 실제 root 문답 3개로 결정했다. 이 문서 작성은 읽기·공식 문서 조사와 이 파일 작성만 수행했으며 workflow·제품·테스트·GitHub 설정을 변경하거나 Flutter/native test를 실행하지 않았다.
- **감사 baseline 정정:** “일반 PR에는 Android build가 없다”는 현재 사실이 아니다. A01 이후 Android Notification Contract가 PR에서 release APK를 빌드하고 packaged/merged manifest를 검증한다. “iOS RunnerTests가 placeholder”도 현재 사실이 아니다. A02 malformed export 입력 계약 테스트가 있으며 다만 실제 실행을 PR에서 강제하지 않는다.

T01/T02가 아직 제공하지 않은 suite/driver는 **dependency pending**이다. R02는 이미 실행 가능한 빌드와 XCTest부터 구현할 수 있지만 필수 Android native 또는 양 플랫폼 core smoke를 비운 채 완료하지 않는다. 구현 단계마다 실제 배선된 행·미배선 행을 기록하며 no-op 성공 check로 자리를 채우지 않는다.

### 유한 runtime 행렬과 toolchain

- Flutter **3.44.4**, Dart **3.12.2**, Java17 및 저장소가 잠근 Gradle/Kotlin/plugin/Pods를 사용한다. 지원 하한 Android23/iOS15 또는 제품 local-only 정책을 CI 편의를 위해 바꾸지 않는다.
- PR은 Android/iOS 각각 대표 runtime을 명시한 유한 행렬이다. Android는 실제 target/SDK와 설치 가능한 대표 image를 확인하고 API·ABI·image revision을 기록한다. iOS는 명시 Xcode 경로·SDK·runtime·device type을 검증한다. `latest`, 연결된 첫 기기, 암묵적인 기본 simulator에 의존하지 않는다.
- 조사 시 공식 [macOS26 runner 이미지 목록](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-Readme.md)에는 Xcode26.5/26.6, iOS26.5 SDK/runtime가 나온다. 이는 후보 선정 근거이며 이 저장소의 runner 할당·실제 부팅·호환 성공 증거는 아니다. 구현 시 제공 목록과 원격 runner의 `xcodebuild -version`, SDK 목록, `simctl` runtime 목록을 다시 확인하고 정확 버전을 고정한다. image가 바뀌어 필수 도구가 사라지면 조용히 다른 버전으로 fallback하지 않고 환경 실패를 남긴다.
- T02의 Android23/26/31~32/33+/target, iOS15 호환 build/pre26 fallback runtime/26+ AlarmKit runtime 및 물리 RC 행은 별도 명시 확장 실행으로 연결한다. 최신 iOS에서 fallback이 보였다고 pre26 호환성을 통과시키지 않는다. R02 대표 PR 행이 T02 전체 물리 행렬을 면제하지 않는다.
- runner가 만든 새 disposable AVD/simulator ID·run ID만 설치·permission 변경·종료·삭제 대상으로 삼는다. 기존 QA simulator `C8BA159D-A97A-458B-A5FC-B04A8B6F2848`, 연결된 사용자 기기와 다른 작업 데이터는 보존한다.

## Trigger·권한·필수 검사 계약

1. `pull_request`의 main/release/**/hotfix/** 대상과 해당 branch `push`, `workflow_dispatch`를 지원한다. `merge_group: checks_requested`도 같은 검사 경로를 지원하되 merge queue의 활성화/보호 설정은 R01에서 다룬다.
2. 모든 일반 PR에서 고유하고 안정적인 check 이름을 유지한다. 문서-only 변경이나 draft를 이유로 필수 workflow/job 전체를 skip하지 않는다. required check에 영향을 주는 rename은 R01 목록과 같이 검토한다. GitHub는 workflow filter로 빠진 required check가 pending을 유지할 수 있다고 설명하므로 필수 workflow에 path filter를 두지 않는다. [공식 workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
3. 최소 `contents: read`, checkout `persist-credentials: false`. production signing, Play/App Store, OIDC, 보호 environment secret을 PR에 제공하지 않는다. Android 일회용 key/검증용 고정 password는 production credential이 아니며 실행 종료 시 제거한다. iOS는 unsigned/device build와 simulator test로 검사한다.
4. fork PR도 같은 테스트 코드 경로를 사용한다. GitHub의 fork 승인 대기는 미실행이며 pass가 아니다. untrusted head를 `pull_request_target` 또는 높은 권한의 `workflow_run`으로 우회 실행하지 않는다. 이 구분은 GitHub의 [pull_request_target 보안 문서](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)에 근거한다.
5. aggregate는 `always()` 조건으로 실제 필수 job의 결과를 검사한다. `success` 외에 `cancelled`, `skipped`, 누락/0 tests, 필수 report 부재, dependency pending을 통과로 취급하지 않는다. 테스트 runner가 반환한 0 exit code 외에 예상 suite/case ID와 결과 원본을 확인한다. 전체 run 취소 등으로 aggregate 자체가 실행되지 못했으면 그 run 역시 성공 증거가 없다.
6. mobile aggregate는 자신의 `needs`와 artifact를 검증한다. 별도 workflow의 Flutter quality와 Android Notification Contract는 R01 필수 check 목록에 각각 포함한다. cross-workflow 결과를 실제 조회·검증하지 않은 aggregate가 전체 repository quality를 보장한다고 말하지 않는다. merge queue 검사 트리거 필요성은 [GitHub required checks 문서](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)를 따른다.

### 시간·동시 실행·실패 보존

- concurrency key는 workflow + PR 또는 검증 ref를 포함한다. 오래된 PR/merge 검증 실행만 새 실행으로 취소한다. 수동/main/release 검증은 취소하지 않는 것을 기본으로 명시하고 배포 job과 같은 그룹에 묶지 않는다. group이 다른 PR이나 다른 workflow까지 잘못 취소하지 않는지 fixture로 검증한다.
- matrix `fail-fast: false`로 반대 플랫폼의 진단을 보존한다. 초깃값 목표는 기존 Android release35분, Android native45분, iOS build/native60분, 각 smoke45분이다. 전체 job과 boot/test의 watchdog을 모두 유한하게 두며 실제 실행 시간으로 조정 근거를 남긴다. 같은 build를 job마다 무조건 반복하지 않고 같은 소스·mode·toolchain으로 재사용 가능한 산출물만 공유한다.
- `continue-on-error`, 성공할 때까지 자동 재시도, 실패 case 삭제로 green을 만들지 않는다. 수동 재실행은 원 실패 run/attempt와 후속 결과를 모두 연결한다.
- 실패 진단 업로드와 소유 target cleanup은 가능한 범위에서 always 수행한다. runner 강제 종료가 모든 cleanup hook 성공을 보장한다고 주장하지 않는다. 테스트 watchdog이 앱의 아직 반환하지 않은 OS 작업 owner를 임의 해제하는 근거가 되지 않는다.
- PR 작업 취소/시간 제한은 R02의 새 검사 기본값에 포함한다. Play package/track 직렬화, staging 환경 보호, 배포 작업의 중단 의미는 R05로 남긴다.

## Artifact·재현성·동일 소스 판정

각 job은 기계 판독 manifest와 native/Flutter 원본 결과를 연결한다. 최소 필드는 아래와 같다.

| 범주 | 필수 내용 |
|---|---|
| 소스 | PR head SHA, base SHA, 실제 checkout/merge SHA; push·merge_group이면 해당 실제 검증 SHA. `git rev-parse HEAD`와 event를 같이 기록. |
| 실행 | workflow/run ID·run attempt·job/check 이름, event, 시작/종료, command, exit/result, runner image/OS/architecture. |
| 도구·입력 | Flutter/Dart, Java/Gradle/AGP/Kotlin, Xcode/SDK/runtime, lockfile hashes, native driver version, fixture/run ID. |
| 앱·대상 | build mode/version/build number, 실제 app ID, target ID/OS/ABI, signing 종류, 실제 빌드·설치 artifact digest. |
| 검사 | 예상 case IDs와 실행/pass/fail/blocked/not_run/skipped 수, 독립 assertion 위치, injection/driver 경계, 결과 원본·log·screenshot hash. |
| 한계 | compile-only/native execution/emulator/simulator/physical 구분, unsigned/disposable signing, offline/network/device delivery 미검증 행. |

- PR head와 기본 checkout merge SHA를 하나의 `commit` 필드로 뭉개지 않는다. Android 기존 identity를 확장할 때도 이전 기록의 의미를 보존한다. 서로 다른 checkout의 build/test 결과를 같은 검증 세트로 결합하지 않는다.
- Android debug/instrumented APK, Android release validation APK, iOS simulator app/test bundle, unsigned device Release app는 서로 다른 산출물이다. 설치한 binary의 digest를 기록하고 다른 release binary에 그 결과를 붙이지 않는다. app bundle directory는 재현 가능한 파일 manifest/hash 방법을 명시한다.
- 합성 fixture의 JUnit/xcresult·테스트 manifest·필요 로그·실패 화면을 성공/실패 모두30일 보존한다. binary는 재현에 필요한 검증용 산출물만 선택적으로 저장한다. production 키·암호·사용자 DB·실사용 설치 데이터·임시 signing key는 artifact와 cache에서 제외한다.
- 필수 result/identity가 없거나 필요한 업로드가 실패하면 테스트 assertion PASS와 별도로 CI evidence 실패이며 aggregate는 통과하지 않는다. 부팅 전에 실패해 report가 없는 경우는 명확한 환경 실패 진단을 남기되 성공으로 채우지 않는다.
- cache key는 OS/architecture/toolchain/lockfile을 구별한다. dependency cache만 재사용하며 생성 Dart·제품 build output·key/data를 신뢰 가능한 새 결과 대신 복원하지 않는다. 실행용 동일 run artifact 공유는 명시 provenance/digest 검증으로만 허용한다. cold cache와 warm cache를 각각 확인해 누락된 생성 단계나 로컬 잔여물이 성공을 숨기지 않는지 검사한다.
- CI의 dependency 다운로드는 도구 실행 환경이다. 제품에 network client/권한을 추가하거나 remote telemetry를 넣는 근거가 아니다. 제품 release network/최종 APK·IPA 관찰은 R09의 별도 계약이다.

## 구현 순서와 검증 행렬

1. 기존 workflow/check 이름·source/merge 기록·실제 runner toolchain을 확정한다. T01/T02 entrypoint 상태와 필수 suite/case manifest를 읽는다.
2. 기존 Android release manifest와 Flutter quality를 유지하면서 iOS unsigned device-target build 및 RunnerTests 실제 실행을 추가한다. SDK가 AlarmKit 경로를 실제 컴파일하는지 확인한다.
3. T02 Android native 및 T01 양 플랫폼 core smoke를 같은 source에 연결한다. 테스트 의미/driver는 해당 이슈의 계약을 사용한다. 새 native framework를 R02에서 임의 도입하지 않는다.
4. 최소 권한·fork 경로·정확 triggers·bounded 실행·artifact와 aggregate를 구현한다. R01에 최종 실제 check 이름을 전달한다.
5. 아래 실패 조건을 격리된 일회성 검증 또는 gate fixture에서 확인한다. 테스트를 고장 낸 source를 일반 제품 변경으로 남기지 않는다. 각 negative는 방법/한계·원 실패·수정 후 결과를 연결한다.
6. 실제 원격 PR의 동일 merge/source에서 모든 필수 검사가 실행되고 결과 artifact를 다운로드해 manifest/hash를 다시 확인한다. 그 뒤 R04/R01/R09와 증거를 연결한다.
