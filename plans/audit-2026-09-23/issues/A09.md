# [P1][A09] 검증된 staging 복원과 runtime·알림 세대 교체를 원자적 경계로 연결

## 문제와 영향

현재 Backup Restore는 활성 DB의 durable rows를 transaction으로 교체하지만, SharedPreferences의 timed preparation·early start 상태, singleton의 시작 기록, timer·구독·준비 map, pending launch를 하나의 복원 수명으로 정리하지 않는다. 같은 일정 ID와 fingerprint를 가진 백업을 복원하면 백업에서 제외돼야 할 옛 Preparation Run이 다시 연결될 수 있다. 메모리 generation이 바뀌는 것만으로는 DB commit 직후 프로세스가 종료되는 상황이나 복원 후 도착한 옛 OS callback을 막을 수 없다.

추가로 ADR 0028은 실제 staging Local Data Store 검증 뒤 Restore Preview를 요구한다. 현재 preview는 decrypt/JSON parse/모델 검증 후 메모리 candidate를 반환하므로 이 요구를 충족한 증거가 아니다. A09는 **정상적으로 열리는 DB**에서 staging 검증, transaction 교체, crash 이후에도 유지되는 runtime 무효화, 현재 데이터로 안전한 재진입을 끝까지 연결한다. 손상 DB를 여는 복구 경로는 D02, 화면의 workflow·typed 결과는 C01의 계약을 사용한다.

우선순위 **P1**. 조사 기준 SHA는 **`dac9c5a2d2097c22f8998743db86b99e28e23e8b`**이다. 병행 중인 A14 구현 파일은 수정하지 않았다. 아래 내용은 조사와 합의된 계획이며 구현·테스트 통과 보고가 아니다.

## 확정한 동작과 구현 경계

### 1. 실제 staging 검증과 후보 수명

1. 기존 암호 suite로 전체 백업을 인증·복호화하고 지원 format을 현재 표현으로 해석한다. format 1/2와 반복 일정 호환을 보존한다.
2. 별도 임시 키로 암호화한 **실제 staging Local Data Store**에 현재 schema로 적재한다. 필요한 forward migration, 제약/참조/준비 순서·소유 관계 검사와 read-back을 완료한 후에만 preview를 만든다. 메모리 parse나 mocked port 성공만으로 대체하지 않는다.
3. staging은 앱 소유 보호된 임시 경로에 두고 Android/iOS OS 백업 및 외부 OnTime Backup에서 제외한다. sidecar/WAL/SHM까지 같은 보호·정리 대상으로 관리한다. 임시 키를 Installation Data Key 저장 위치에 넣거나 덮어쓰지 않는다. plaintext 임시 DB/원문 로그/암호 로그를 만들지 않는다.
4. immutable 검증 candidate에 C01의 현재 generation+durable revision 확인 token을 연결한다. preview 이후 파일을 다시 읽어 다른 내용을 적용하지 않는다.
5. 취소·검증 실패·stale preview·성공·후보 종료 때 staging/키/참조를 정리한다. 프로세스 종료로 남은 staging은 다음 startup에서 앱 소유 경로만 정리한다. 유효 후보가 현재 진행 중인 작업에 소유돼 있으면 UI dispose만으로 파일을 지워 실행 중 apply를 망가뜨리지 않는다.
6. cleanup 실패는 C01 typed 결과/제한 상태로 전달한다. 정상 원본 DB를 삭제하거나 설치 키를 새로 발급하여 임시 파일 정리 오류를 숨기지 않는다. 메모리 참조 해제를 안전한 zeroization이나 저장장치 완전 소거라고 과장하지 않는다.

구체 staging factory/path/key scope는 선행 구현과 실제 플랫폼 보장을 보고 정한다. 구현 전 미정인 API 이름이나 fsync 내구성을 이미 확보한 것처럼 쓰지 않는다. D05의 전체 입력 상한·timezone/graph 검증은 공유 validator로 연결하되 A09에서 실제 staging 검증을 생략하는 핑계가 되지 않는다.

### 2. 최종 확인, quiesce, 활성 DB transaction

- C01의 배타적 claim **안에서** preview generation/revision을 확인한다. 외부 check-then-act 또는 자신의 generation 증가 때문에 모든 후보가 stale이 되는 구현은 금지한다. stale이면 DB/키/runtime을 파괴하지 않고 재확인을 받는다.
- A15 단일 writer와 기존 data gate를 재사용하여 기존 DB/runtime writer, timer, stream, 진행 중 OS side effect가 안전한 경계에 이르도록 한다. 별도 coordinator, 중첩 gate, Future 무시를 실제 취소로 취급하는 구현을 만들지 않는다.
- 정상 활성 DB와 Installation Data Key는 유지한다. 검증된 staging 내용을 **한 실제 DB transaction**으로 전체 교체한다. DB 파일 rename/key swap은 D02 손상 DB 복원 범위다.
- 교체 transaction에는 외부 백업에 포함되지 않는 설치 로컬 restore/runtime generation 또는 pending-cleanup 사실을 원자적으로 기록한다. commit 이후 prefs cleanup 전 종료돼도 새 DB와 옛 runtime을 구별할 수 있어야 한다. 필요한 내부 DB 메타데이터/schema migration은 가능하지만 portable Backup Format Version/암호 suite 변경을 뜻하지 않는다.
- DB commit 전 기존 persisted runtime을 삭제하지 않는다. commit 전 실패/rollback이면 원본 durable rows와 설치 키를 보존하고 기존 run을 현재성 검사 후 재개할 수 있어야 한다. 안전을 위해 옛 OS 등록을 이미 취소했다면 원본 DB를 기준으로 같은 coordinator가 다시 조정하고, 미완료 delivery는 별도 사실로 표시한다.
- OS call이 명시적 실패/unknown으로 반환한 상태와 아직 반환하지 않은 상태를 구별한다. 후자는 UI timeout만으로 quiesce를 통과하지 못한다. 늦은 반환의 ownership은 A15가 계속 소유한다.
- commit 후에는 candidate 재사용과 DB 교체 반복을 막는다. runtime/delivery 실패는 데이터 rollback이 아니다. C01은 **데이터 복원 완료 + 후속 정리 미완료**를 표시하고 필요한 후속 단계만 retry한다.

### 3. 전 세대 runtime 제거와 새 상태 재진입

복원된 일정 목록에 있는 ID만 순회하지 않는다. 삭제된 일정의 orphan을 포함한 앱 소유 runtime namespace 전체를 세대별로 처리한다.

| 대상 | 필요한 경계 |
|---|---|
| timed snapshot/action events/elapsed/early marker/옛 confirmation marker | commit된 복원 세대와 불일치하면 같은 ID·같은 fingerprint여도 읽거나 재사용하지 않는다. bool false/IO 실패를 성공 삭제로 표시하지 않는다. |
| 시작 flight/ID Set, active run, timer/tick, notified-step set | A07/A12 owner/run/generation 경계로 멈추고 새 데이터에 영향 못 미치게 한다. |
| repository BehaviorSubject, preparation map, nearest schedule 구독 | 새 DB로 재생성 또는 명시적 clear/reload. old load의 늦은 완료가 새 map을 채우지 못한다. |
| prompt/view owner, deferred tap, native pending launch, cold getter | A12 무효화와 다음 절의 영속 delivery identity를 함께 사용한다. |
| D03 journal, Installation Data Key, 새 generation의 유효 runtime | 일반 prefs.clear로 지우지 않는다. old cleanup이 나중에 완료됐다는 이유로 새 run 상태를 제거하지 않는다. |

DB commit 직후 프로세스를 재시작해도 startup은 정상 UI/timer/native 재진입 **전에** 설치 로컬 복원 세대/cleanup marker를 읽는다. 정리가 끝나지 않으면 옛 runtime을 차단하고 멱등적으로 필요한 정리만 재개한다. 실패하면 D01/C01의 제한된 복구 상태에서 현재 사실과 retry를 제공한다. pre-runApp throw만 추가하여 흰 화면에 남기는 것은 수용하지 않는다.

복원된 durable startedAt/preparationFrozen/outcome/점수는 그대로 보존한다. DB startedAt이나 과거 Preparation Start Moment만으로 active timer·elapsed·action event·완료 결과를 생성하지 않는다. 완료되지 않은 복원 일정의 재진입은 A07/A11 명시적 확인·새 run 경계를 지킨다. 최초 durable 시작 시각을 새 run 시각으로 덮어쓰거나 완료 기록을 재집계하지 않는다. 안정된 새 DB 화면으로 돌아오는 UI는 C01에서 연결한다.

### 4. 구세대 알림과 동일 ID 안전성

- 복원은 기존 OnTime의 일정·준비 단계·표시 중 알림·native pending 등 옛 delivery를 정리한다. 다른 앱/OS 전역은 대상이 아니며 일반 일정 OFF의 범위와도 구별한다.
- D03 최소 ownership journal과 취소 엔진을 재사용한다. journal은 새 DB 내용으로 교체하거나 prefs 정리로 잃지 않는다. provider별 성공/실패/unknown은 A14의 실제 관측 기준을 따른다.
- 원문 없는 installation-local delivery generation 또는 검증 가능한 불투명 receipt identity를 예약→표시→tap 경계에 연결한다. 늦은 구세대 callback을 현재 수신 시각의 메모리 generation으로 다시 표시해서 새 DB 동일 scheduleId로 해석하지 않는다.
- payload에는 제목/장소/준비명/시각/fingerprint/시작 명령을 추가하지 않는다. 최소 세대/불투명 ID는 라우팅 안전 metadata이며 외부 백업에 포함하지 않는다. 필요한 native/Dart allowlist 버전 변경은 A11의 개인정보 경계와 함께 검증한다.
- generation 없는 legacy launch는 최초 복원 경계 전 호환을 유지할 수 있지만, 복원 경계 후에는 안전한 매핑 증거 없이 확인 화면도 열지 않는다. 악성/잘못된 ID 역시 DB 검증을 우회하지 못한다.
- 취소가 명시적 실패/unknown으로 반환한 경우 journal을 보존하면서 DB commit은 허용할 수 있으나 후속 정리 미완료다. 동일 provider ID 새 등록은 옛 취소 확인 전 금지한다. 아직 반환하지 않은 OS Future는 quiesce 완료가 아니다.
