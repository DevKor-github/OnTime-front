# [P1][A11] 준비 원문의 암호화 DB 외부 복제를 제거하고 legacy runtime·알림 payload를 안전하게 전환

## 문제와 사용자 영향

현재 `cacheFingerprint`는 hash가 아니라 일정 시각·시간대·이동/여유 시간·준비 단계 ID와 **준비 이름 원문**을 이어 붙인 문자열이다. 이 문자열이 SharedPreferences의 알림 registry, 진행 snapshot, notification payload, 플랫폼 launch payload로 복제된다. 준비 snapshot은 fingerprint와 별개로 `steps.name`에도 같은 이름을 저장한다. 상세 알림 OFF여도 숨긴 준비 이름이 암호화 Local Data Store 밖에 남는다. ScheduleBloc의 debug 로그도 fingerprint 원문을 출력한다.

이는 **화면의 비공개 문구와 저장된 payload의 최소화가 별개**라는 문제다. visible title/body만 고치거나 fingerprint getter만 hash로 바꾸면 기존 원문과 다른 복제 경로가 남는다. 이 이슈는 신규 쓰기를 최소화하고 기존 앱 소유 원문을 전수 정리하며, 진행 중 Preparation과 과거 알림 탭의 의미를 안전하게 보존한다.

감사 A11에 해당하는 P1 개인정보 경계 수정이다. 소스에서 원문 경로를 확인했으며 실제 배포 기기의 모든 저장소·OS 등록을 검증한 상태는 아니다. 코드/자동 테스트/실제 upgrade 검증을 구분한다.

## 기존 도메인 및 결정과의 정합성

- **Durable OnTime Data / Local Data Store**: 사용자 이름·기본 준비 내용·기본 duration/order의 authoritative 원천은 암호화 DB다.
- **Reconstructible App State**: 진행 시작시각, action events, 검증 가능한 ID·진행량 및 identity는 복원 가능한 runtime이다. 이름의 두 번째 원문 저장소로 쓰지 않는다.
- **Private / Detailed Notification Content**: 상세 ON도 일정명과 필요 시간대만 허용한다. 준비 이름·Place·note는 어느 모드에서도 OS로 내보내지 않는다.
- ADR 0018(설치 DB 암호화), 0022(SharedPreferences는 reconstructible state), 0029(fingerprint에 맞는 action-event 기반 진행), 0030(private 기본값)을 적용한다. 새 domain term은 없으므로 CONTEXT를 늘리지 않는다. digest/serializer 개선과 기존 정책 준수는 되돌릴 수 있는 구현 선택이어서 새 ADR를 만들지 않는다.

## 확정한 설계

### 1. 버전된 identity와 최소 데이터

1. 비정형 연결 문자열 대신 version/domain tag를 포함하는 canonical encoding과 안정적인 SHA-256을 사용한다. JSON array 등 순서와 타입이 명시된 표현으로 ID·Unicode 이름·빈 문자열·null·구분자를 구별한다. Dart의 실행별 hashCode를 영속 identity로 사용하지 않는다.
2. timing identity(일정 instant, named zone와 occurrence offset, move/spare)와 ordered shape identity(각 단계 ID/name/duration/next ID)를 분리한다. 비교 범위를 분리해 session 유효성과 A05의 실제 표시 content 동등성을 혼동하지 않는다. private 표시 content는 준비 이름 변경만으로 달라지지 않는다.
3. digest는 원문 중복을 없애고 동등성을 판단하는 수단이다. 암호화·익명화·낮은 엔트로피 이름의 사전 추측 방지라고 주장하지 않는다. 이번 작업에서 별도의 HMAC 설치 키나 DB schema를 추가하지 않는다. 새 외부 저장 필드는 필요한 최소 identity만 둔다.
4. runtime payload에는 version, 시작/저장 시각, action events, 필요한 step ID/진행량, timing/shape identity만 둔다. 준비 이름·기본 duration/order/next ID 등 domain 내용은 현재 DB에서 재구성한다. old elapsed-only snapshot의 진행량을 보존할 때도 DB 검증을 거친 ID에만 적용한다.
5. 신규 OS route payload는 필요한 schedule ID, payload version, route kind 등의 명시적 allowlist로 만든다. 불필요 content digest, schedule/preparation dump, arbitrary unknown field를 전달하지 않는다. provider 예약을 위해 꼭 필요한 시각/등록 ID와 visible title/body는 route payload와 구별한다. A05의 허용된 visible content 이외의 제목/본문을 앱 registry에 중복 영속할 필요가 있는지도 줄인다.
6. Dart·Android·iOS의 launch receive/store/URL encode/boot restore에서 allowlist를 적용한다. route extra와 debug log에 legacy fingerprint/원문이 살아남지 않도록 입력 경계부터 축소한다. 로그는 필요한 상태·식별 정보만 남긴다.

### 2. 진행 상태 전환 규칙

| 상황 | 결정 |
|---|---|
| timing과 ordered shape가 모두 같은 새 runtime | startedAt/action events/검증된 진행량을 보존하고 DB로 이름 등 화면 내용을 재구성한다. |
| 준비 이름, 단계 ID, 추가·삭제·순서, duration, next ID 변경 | 진행 transient를 무효화한다. 데이터 수정은 유지하며 자동 시작·완료·outcome 생성은 하지 않는다. |
| 일정시각·시간대/offset·move/spare 변경 | 동일하게 기존 transient를 무효화한다. 기존 prefix 기반 예외를 유지하지 않는다. |
| 동일한 legacy snapshot | 현재 DB에서 만든 기존 serializer 결과와 **exact equality**를 확인하고 별도 저장 단계의 ID/name/duration/연결/순서까지 대조한 경우만 새 runtime으로 전환한다. 문자열 delimiter parsing은 재도입하지 않는다. |
| legacy 필드 누락·손상·충돌 우려·검증 불가 | transient만 보수적으로 폐기한다. DB의 Schedule/Preparation/outcome/설정은 변경하지 않는다. 자동으로 현재 시각을 채워 유효한 run처럼 복구하지 않는다. |
| 암호화 DB 열기 실패 | legacy transient 원문을 무기한 보존하지 않고 제거한다. DB와 설치 키는 유지하고 Recovery Mode로 간다. 확인할 수 없는 진행을 복원하지 않는다. |
| 관련 early-start record | runtime 유효성과 함께 판단하며 무효화 때 잔존 early-start/memory 때문에 자동 재시작되지 않도록 통합한다. |

이 전환은 사용자 콘텐츠 migration이 아니다. 원문을 encrypted DB로 재수입하거나 old runtime을 백업의 source of truth로 사용하지 않는다. 새로운 serializer를 모두 저장한 뒤 읽도록 일관된 버전을 사용하고 실패 시 성공 marker를 남기지 않는다.

### 3. legacy registry·OS 저장·pending launch 정리

1. 초기 진입에서 현재 선택 일정뿐 아니라 앱 소유 `preparation_with_time_*`, 관련 early-start, scheduled alarm registry, iOS pending launch UserDefaults 등 known legacy 키를 전수 탐지한다. 삭제된 일정의 orphan 이름도 남지 않아야 한다. scope는 OnTime 소유로 확인된 키이며 전체 SharedPreferences를 무차별 삭제하지 않는다.
2. registry 원문은 즉시 새 최소 표현으로 바꾸되, 기존 등록의 **소유 ID/provider/cancel 재시도 정보**를 잃지 않는다. 취소에 raw payload/title/fingerprint가 필요하다고 계속 보관하지 않는다. malformed record도 검증 가능한 소유 ID만 추출하고 판정 불가능한 내용을 성공으로 취급하지 않는다.
3. 공개 plugin pending 목록을 조회해 소유권이 확인되는 legacy Schedule Notification을 찾고 공개 cancel 경로로 제거한다. registry 밖의 preparation step 알림을 무차별 cancelAll하지 않는다. 필요한 미래 eligible 일정은 authoritative DB와 최신 A05 privacy 설정으로 다시 만든다. 과거 알림을 즉시 새 알림으로 재발송하지 않는다.
4. 앱 소유 native reader는 legacy payload를 safe route 최소값으로 축소/거부하여 새 원문 복제를 막는다. third-party plugin boot receiver의 자체 저장소와 앱 소유 registry를 혼동하지 않는다.
5. pending launch는 최소화된 route 정보만 일시 보존하거나 소비하고 원문을 삭제한다. 이미 전달된 legacy tap은 ID로 현재 DB의 존재·미완료를 확인해 최신 시작 확인 화면만 연다. 오래된 fingerprint나 `start` 명령을 신뢰해 자동 시작하지 않는다. 신규 payload도 DB 재검증이 필요한 route 힌트다. 삭제/완료한 일정은 안전한 home/종료 경로로 가며 LoadingScreen에 무한히 남지 않는다.
6. cancellation/re-registration/read-back이 실패하면 최소 tombstone과 오류를 보존해 재시도하고 migration 완료로 표시하지 않는다. 앱 preference 쓰기/삭제 실패도 잡아서 실제 제거와 marker를 구분한다. 다음 시작/재시도가 멱등적이어야 한다.
7. **통제 한계:** 업데이트 후 첫 앱 실행 전에는 플러그인이 자체 과거 payload를 재예약할 수 있다. 이 경로를 현재 코드로 해결했다고 주장하지 않는다. 앱 소유 원문 정리와 공개 plugin cancel/read-back 성공 이후의 상태를 증명한다. 이미 노출된 화면·사용자 캡처·과거 OS 로그·물리 저장소의 포렌식 삭제까지 보장하지 않는다.

## 자동 회귀 테스트

합성 sentinel 준비 이름, 일정명, Place, note를 사용한다. 로그나 artifact에 실제 사용자 데이터는 넣지 않는다.

| 검사 | 기대 결과 |
|---|---|
| deterministic canonical identity | 같은 typed 입력은 실행/순서 안정적인 digest; schema/domain 변경 구별; `:`/`\|`/Unicode/빈값/null을 포함한 서로 다른 입력이 단순 연결 충돌하지 않는다. |
| timing/shape 변경 행렬 | 각 입력 변경에 해당 identity만 변화; name/content 변경과 실제 delivered content equality 분리. |
| 새로운 runtime serialize → 앱 재시작 → restore | 저장 bytes에는 준비 이름/Place/note 없음; DB 기반 화면 이름/단계 순서와 진행이 정확하다. |
| action-event run 및 legacy elapsed-only run | 각각 정의된 복원 방식과 skip/finish 동작이 유지된다. 검증되지 않은 event step ID/과거 progress를 다른 단계에 적용하지 않는다. |
| 동일한 legacy migration | 현재 DB와 exact legacy 문자열 및 별도 step fields를 비교해 진행 보존; 재저장에 legacy 원문 없음. 두 번째 실행 no-op. |
| legacy missing/malformed/delimiter ambiguity | transient만 폐기; durable DB before/after 동일; started/outcome 자동 변경 없음. |
| 단계/시각 변경 직후 복원 | 표의 모든 변경에서 stale run/early-start/memory 재사용 없음. |
| 전체 known-key migration | 비선택 일정·삭제 일정 orphan·iOS pending launch 포함; 관련 없는 앱 설정은 보존. |
| DB unavailable | raw transient 제거 시도와 Recovery Mode; DB/key 손상/삭제 없음; 청소 실패를 성공으로 기록하지 않음. |
| registry cancel 실패, 신규 예약 실패, preference 쓰기 실패 | raw 없이 재시도 evidence 보존; 완료 marker/armed false success 없음; 재시도 수렴. |
| pending OS와 registry 불일치 | 소유권 확인된 legacy pending만 정리; 현재 preparation step 표시와 unrelated notifications 보존. |
| legacy/new tap: foreground/background/cold launch | ID 확인 후 최신 화면, 원문 재저장/로그 없음; legacy automatic start 금지; 완료/삭제/null/malformed 안전 처리. cold 시작 queue/dedupe는 A12와 연결. |
| native allowlist | Android intent/boot, iOS stored launch/URL/AlarmKit intent가 unknown field와 raw fingerprint를 반사하지 않음. |
| raw sentinel 검색 | 앱 registry/runtime 신규 JSON, plugin에 전달된 신규 payload, launch preferences/query, 수집한 앱 debug logs에 금지 원문 없음. detailed ON에서도 prep/place/note 없음. |

관련 domain identity/session, data source/model, reconcile, router, logger 테스트를 갱신한다. 기존 테스트가 원문 `contains('s1:wash:...')`를 기대하는 부분은 요구 동작으로 바꾸며 단순 hash 구현을 복사한 assertion으로 대체하지 않는다. 필요 SHA-256 package는 직접 dependency로 선언하고 generator 파일을 커밋하지 않는다. analyzer/전체 Flutter 회귀 및 native build 계약 검사를 실행한 SHA에 연결한다.

## 실제 upgrade 및 개인정보 검증

Android/iOS 각각 합성 legacy profile로 다음을 준비한다: 미래 schedule notification, 상세 ON/OFF, 진행 중 action-event run, early-start, 삭제 일정 orphan, pending launch. 이전 포맷을 실제 저장한 설치에서 데이터 보존 update를 수행한다.

- 첫 실행 전 boot/update plugin 재예약 여부를 별도 기록한다. 관찰하지 않은 영역을 삭제 완료라고 하지 않는다.
- 첫 실행 후 앱 registry/runtime와 공개 OS pending read-back, 표시 중 알림 취소, 새 예약 payload, 실제 잠금화면 신규 표시를 구분해 기록한다.
- 진행 중 session이 검증될 때만 같은 elapsed/current step으로 이어지고 이름을 DB에서 읽는지 확인한다. 변경된 shape/timing은 자동 시작 없이 무효화한다.
- 기존 delivered notification tap이 최신 시작 확인 화면으로 한 번만 이동하고 실제 사용자 시작 전 durable started/outcome을 쓰지 않는지 확인한다.
- 실패 주입 후 재시작이 최소 tombstone으로 수렴하는지 확인한다. force-stop/OS 제한과 app crash를 구분한다.
- 앱 SHA·version/build number·artifact digest·기기/OS·합성 fixture revision·절차·기대/실제·pending read-back을 기록한다. 실기기 미확보 시 코드/자동 검사 통과와 기기 검증 대기를 분리해 이슈를 open으로 유지한다.

## 의존 관계 및 제외 범위

- **A05**: canonical delivered content와 digest/재등록. A11 timing/shape를 visible content와 혼합하지 않는다. 비공개 title/body 경계와 legacy cancel 실패 정책을 공통으로 적용한다.
- **A12**: cold launch 대기/중복 제거. 이 이슈가 payload 최소화와 legacy safety를 소유하고 실제 최초 launch routing은 A12와 통합 검증한다.
- **A09**: Backup Restore 후 runtime reset. migration이 복원된 DB에 old run을 연결하지 않게 lifecycle generation을 존중한다.
- **D03**: provider cancellation/read-back/retry 정책. A11 privacy cleanup의 최소 오류·재시도 구현은 필요하며 D03 완료를 핑계로 잘못된 성공 처리를 두지 않는다.
- **A01**: plugin boot receiver 연결. 올바른 receiver 연결이 legacy plugin payload 청소를 보장하지 않는다.
- **A15/C01**: reconcile 동시성·local data lifecycle gate. migration 중 새 writer가 legacy를 재생성하거나 reset/restore와 교차하지 않도록 연결한다.
- **T01/T02**: upgrade/real-device/native contract 자동화로 증거를 재사용한다.
- 암호화 suite 변경, 새 설치 HMAC 키, DB schema 추가, 서버/로그 수집/원격 분석, plugin fork/사설 JSON 수정, 모든 OS 역사 기록 삭제, 사용자 데이터 전체 reset은 제외한다.
