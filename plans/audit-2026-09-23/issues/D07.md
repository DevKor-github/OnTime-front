## 문제와 사용자 영향

백업은 템플릿의 `createdAt`과 `updatedAt`을 별도로 내보내고 읽지만, 복원은 일반 편집용 DAO에 `now: template.updatedAt`만 전달한다. 전체 교체로 기존 행이 삭제된 뒤 DAO는 `createdAt = existing?.createdAt ?? now`를 실행하므로, 원래 생성 시각이 수정 시각으로 덮인다. 이는 값의 누락이며 단순한 표시 차이가 아니다. 템플릿 목록이 `createdAt ASC`로 정렬되므로 오래된 템플릿을 나중에 편집한 사용자는 복원 후 목록 순서까지 달라질 수 있다.

예: A는 1일 생성·4일 수정, B는 2일 생성·3일 수정이다. 백업 전 A→B였던 목록이 현재 복원 경로에서는 B→A로 바뀐다. 템플릿 수·이름·준비 단계가 맞아도 이 복원은 원본 메타데이터를 보존하지 못한다. P2인 이유는 백업 자체를 열지 못하거나 일정 본문을 잃는 문제보다 우선순위는 낮지만, 정상 백업의 반복 가능한 자료 손실과 사용자 목록 순서 변경이기 때문이다.

추가로 현재 DB에서 읽은 timestamp는 local DateTime이고 그대로 ISO 문자열을 만들기 때문에 offset이 없는 백업이 생성될 수 있다. D07은 새 템플릿 timestamp 표현을 명확히 하면서 기존 offset 없는 백업의 복구 불가능한 source-zone 모호성을 숨기지 않는다.

## 확정 설계

### 일반 편집과 복원 저장의 경계

1. 일반 create/edit의 `put(now)` 계약을 유지한다. 새 템플릿은 생성·수정 시각이 동일하고, 기존 템플릿 수정은 createdAt을 유지하며 updatedAt만 명시적인 저장 시각으로 바꾼다. 일반 화면이 임의 생성 시각을 덮을 수 있는 범용 두 timestamp upsert로 바꾸지 않는다.
2. **검증된 restore 전용 저장 경로**는 createdAt과 updatedAt을 각각 필수로 받아 저장한다. 실제 API 이름은 선행 A09/D02 materializer와 맞춘다. optional parameter의 기본값으로 `now`, Cutoff, 다른 timestamp를 사용하지 않는다.
3. 전체 교체에서는 백업의 두 값이 권위다. 대상 DB에 동일 ID의 다른 템플릿이 있더라도 대상 생성일을 섞지 않는다. stage에 적재할 때와 최종 active read-back이 같은 값을 보여야 한다.
4. template 행과 모든 step의 저장은 전체 복원 transaction 또는 검증된 candidate store 적재 경계 안에 둔다. 실패한 두 번째 template/step이 부분 교체 결과를 성공으로 남기지 않는다. 일반 repository의 다른 원자성 문제를 이 변경으로 해결했다고 확대하지 않는다.
5. 과거 잘못된 restore로 이미 손실된 createdAt은 updatedAt·UUID·다른 항목 순서로 추정해 복구하지 않는다. 정상 원본 백업을 다시 복원하는 것은 사용자의 별도 명시적 전체 교체 선택이다.
6. `updatedAt < createdAt`은 기기 시계 역행으로 가능하다. D07에서 단조 시간이나 미래 시간 금지 규칙을 새로 강제하지 않는다. 두 값의 문법·지원 범위·저장 가능성은 각각 검증한다.

### UTC instant, legacy 표현과 정밀도

- 새 export의 **template.createdAt/updatedAt 두 field만** UTC ISO-8601 `Z`로 직렬화한다. Schedule civil 표현이나 모든 날짜를 일괄 UTC 전환하지 않는다. payload format 1/2 reader와 기존 crypto suite를 유지하고 D07 때문에 format 번호를 올리지 않는다.
- 명시 offset 또는 `Z`가 있는 지원 입력은 같은 UTC instant를 저장한다. 문자열 spelling, offset 표시 및 DateTime의 `isUtc` 플래그 일치는 자료 보존 판정 기준이 아니다.
- offset 없는 legacy template timestamp는 기존 parser의 현재 기기 local 해석 호환을 유지한다. 원래 source zone이 payload에 없으므로 다른 zone에서 원래 instant를 정확하게 복원한다고 보장할 수 없다. Cutoff, Schedule Time Zone, 실행 기기 또는 임의 fixture 값을 원래 source zone으로 추정하지 않는다. 새 export가 과거 모호성을 소급 해결했다는 표현을 금지한다.
- DB의 현재 epoch **초** 해상도를 유지한다. 정상 앱의 실제 저장 행→export→restore round-trip은 그 source row의 epoch instant로 동등성을 검사한다. DateTime 생성 직후의 아직 저장되지 않은 subsecond 값과 DB read-back을 혼동하지 않는다.
- `.000`과 정수 초에 해당하는 offset 정규화는 허용한다. **nonzero subsecond 입력은 D05와 공유하는 표현 가능성 validator에서 파괴적 apply 전에 명시적으로 거절**한다. 조용히 자른 뒤 정확한 보존이라고 보고하지 않는다. 과거 정상 앱 export가 실제 subsecond를 생성했다는 증거가 나오면 호환 결정을 재검토하고 기록한 후 구현한다.
- 음수 epoch와 지원 year 범위 경계도 검사한다. 전체 초로 표현 가능한 과거 시각을 단순히 음수라는 이유로 거절하지 않고, 음수 fractional 값을 `~/ 1000`으로 0 방향 절삭해 몰래 정규화하지 않는다. D05의 strict calendar/range parser를 재사용하고 동일 내용의 별도 validator를 만들지 않는다. D05보다 먼저 구현하면 공통 경계에 필요한 최소 검증을 제공한다.

### 정렬

`getAll()`의 정렬을 **createdAt ASC, id ASC**로 명시한다. 다른 createdAt 사이의 기존 순서는 유지하고, 동일 createdAt의 순서는 ID로 안정화한다. DB insertion/rowid 순서나 updatedAt을 tie-breaker로 간주하지 않는다. 동일 timestamp에 ID 역순으로 삽입해도 export/restore/독립 reopen 이후 같은 순서여야 한다. UI에 수동 정렬 또는 새 정렬 선택 기능을 추가하지 않는다.

## 의미 있는 검증 행렬

모두 **실행할 계획**이다. 호출 인자 mock 검증만으로 통과시키지 않는다. 공통 정상 fixture는 A(1일 생성·4일 수정), B(2일 생성·3일 수정), 같은 생성 timestamp의 역순 ID 두 개, 다단계 preparation을 포함한다. 읽어 온 source row를 기준으로 ID·이름·두 epoch instant·step ID/이름/분/position/nextId와 전체 목록 순서를 비교한다. 암호화 bytes는 랜덤 salt 때문에 같을 필요가 없으며 재export의 검증된 template 내용으로 비교한다.

| 번호 | 시나리오 | 필요한 결과·증거 |
|---|---|---|
| 1 | 현재 결함 재현 | 수정 전 실제 restore에서 A.createdAt이 A.updatedAt으로 바뀌고 A/B 순서가 역전하는 실패를 기록한다. 이름/count만 확인하는 성공은 불충분하다. |
| 2 | 실제 DB→암호화 export→preview→교체→독립 reopen→재export | 모든 template field와 preparation 순서/참조가 source row와 같고 A→B 순서가 유지된다. preview metadata count도 실제 read-back과 맞는다. |
| 3 | format 1/2 | 각 지원 형식의 정상 앱 생성 자료/역사 fixture와 두 timestamp를 검사한다. format 2 recurring 자료를 누락해 format 1 통과로 대체하지 않는다. |
| 4 | 대상 동일 ID의 다른 생성·수정 시각 | 전체 교체 결과는 백업의 두 값이다. 대상 메타데이터가 merge되지 않는다. |

## 수용 기준과 완료 보고

- [ ] 실제 실패하는 최소 회귀가 기존 복원의 createdAt 손실과 정렬 역전을 입증한다.
- [ ] 일반 edit/create와 검증된 restore 저장 경계가 분리되고 두 timestamp는 각각 필수 입력으로 적재된다.

- [ ] createdAt ASC/id ASC가 실제 DB와 독립 reopen에서 안정적이며 기존 서로 다른 생성일 순서를 유지한다.
- [ ] 실제 암호화 v1/v2 round-trip 및 재export가 template 전체 field/steps/순서를 비교하고 날짜 몇 개만 별도 mock한 테스트로 대체하지 않는다.
- [ ] template/step write 실패와 취소·검증 실패가 부분 활성 교체를 만들지 않는다. 원본 보존 read-back을 제출한다.
- [ ] A09 정상 staging과 D02 손상 Recovery에서 같은 materializer를 사용하고 template metadata 보존을 독립 재열기로 확인한다.

- [ ] analyze, 관련 DAO/backup/workflow 회귀 및 필요한 전체 suite를 수행하고 정확한 source SHA·명령·결과를 기록한다. generated outputs는 커밋하지 않는다.
- [ ] 이미 손실된 값의 추정 복구와 offsetless legacy의 source-zone 복구를 주장하지 않는다. 저장소 구현/통합/실기기 검증 상태를 따로 보고한다.

A09/D02 통합 또는 양 플랫폼 실증이 남아 있으면 저장소 수정과 unit 회귀를 완료한 것으로 기록하되 **D07 전체는 OPEN**으로 둔다. 아직 실행하지 않은 항목, 실제 native 암호화 검증, 실기기 파일 전달을 서로 대체하지 않는다.
