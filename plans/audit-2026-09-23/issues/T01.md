## 문제와 결과 목표

현재 테스트와 플랫폼 컴파일 검증은 상당 부분 존재하지만, 실제 `main`에서 시작해 startup/privacy boundary, DI, 설치별 암호화 저장소, 화면 입력, OS 알림 수신·탭, 준비 진행·완료, 프로세스 재실행까지 연결하는 재현 가능한 E2E suite는 없다. 여러 테스트의 개수나 성공을 더해도 이 연결이 검증되지는 않는다.

## 확정한 실행 계약

### 실제 앱 경로와 독립 기대 결과

- 정상 `main`→startup gate/bootstrap→실제 DI→실제 OS secure storage와 암호화 파일 DB→화면이 기본이다. 테스트 때문에 제품 workflow, repository, DB, 알림 서비스를 fake로 바꾸고 성공을 보고하지 않는다.
- 필요한 자동화 dependency와 entrypoint, 안정적인 접근성/테스트 식별자를 최소 범위로 추가한다. 제품 전용 테스트 화면, DB 주입, 설치 키 출력, data export debug channel을 추가하지 않는다.
- fixture는 합성 이름·장소·준비 단계·명시 시간대로 실제 onboarding/생성/편집 폼에서 만든다. 기대값은 입력한 fixture에서 독립적으로 산출한다. 생산 derive 함수 또는 테스트 내 복제 알고리즘으로 expected를 만들지 않는다.
- clock/외부 경계 injection이 필요하면 어떤 증거를 제한하는지 결과에 명시한다. 실제 OS 수신 행은 wall clock과 native provider를 사용한다. 빠른 clock 테스트를 실제 OS 전달로 바꿔 부르지 않는다.
- 준비 진행은 실제 시작 액션과 timer/lifecycle 경로로 관측한다. A07의 최초 durable startedAt과 개별 Preparation Run start를 혼동하지 않는다. 재실행 후 runtime은 A11의 검증/재확인 계약을 따르며, durable 일정 보존을 자동 진행 복구로 확대하지 않는다.
- OS 권한창·native file picker·잠금 화면·알림 탭처럼 Flutter widget tree 밖인 단계는 명시적인 native driver 또는 수동 기기 절차로 연결한다. API callback 직접 주입, registry 존재, plugin 성공 receipt만으로 실제 수신·탭을 판정하지 않는다.

### 격리·첫 실행·프로세스 재실행

- runner는 자기 소유의 새 disposable Android AVD/iOS simulator와 run ID를 만든 뒤 대상 ID·앱 ID를 기록하고 검증한다. 설치, permission 설정, 프로세스 종료, 네트워크 변경, 정리 명령은 그 대상에만 적용한다.
- 기존 QA simulator `C8BA159D-A97A-458B-A5FC-B04A8B6F2848`, 다른 작업의 simulator, 사용자 기기는 자동 선택/초기화/삭제하지 않는다. 기존 hardware는 향후 명시 지정된 QA 대상에서만 검증한다.
- 새 simulator/명시 초기화된 QA 환경의 clean-install 상태를 확인한다. iOS uninstall만으로 secure-store 키가 제거되었다고 가정하지 않는다. 제품 reset으로 사전 marker를 만든 설치도 첫 설치 cold-start와 구별한다.
- 프로세스 재실행은 외부 runner가 실제 PID를 종료하고 **동일 설치·동일 데이터**로 cold launch한 뒤 UI에서 profile/일정/완료 기록을 다시 읽는다. widget 재-pump, DI 재생성, hot restart를 process relaunch로 쓰지 않는다.
- Android Settings force-stop은 일반 프로세스 종료와 구별한다. 기기 OS 제한을 숨기거나 force-stop 중 수신을 T01에서 보장하지 않는다. 사용한 종료 방식과 PID 전후를 기록한다.
- 실패 로그·스크린샷은 합성 데이터만 보존하고 재실행으로 원 실패를 덮어쓰지 않는다. 정리도 run이 만든 기기/임시 파일/fixture에만 적용한다. fixture backup 파일의 삭제는 테스트 소유 cleanup이며 제품 reset이 외부 백업을 지운 것으로 해석하지 않는다.

### 실제 전달·오프라인·바이너리 경계

- 예약 시각, 실제 수신 시각, native provider, display/timing 권한, 앱 lifecycle을 기록한다. Android approximate/inexact 지연을 exact 성공으로 표시하지 않고 A13 정책대로 관측한다. iOS AlarmKit capability/permission과 fallback을 구별해 실제 provider를 기록한다.
- watchdog은 유한해야 한다. 초과하면 `fail` 또는 구체적 환경 원인을 가진 `blocked`로 기록하며 미수신을 pass로 바꾸지 않는다. fake clock·callback·무제한 재시도로 green을 만들지 않는다.
- 자동 emulator/simulator smoke의 debug transport는 허용된 개발 도구 경계일 뿐 release의 Product Network Boundary 증거가 아니다. 호스트 네트워크 설정을 바꾸지 않는다.
- 물리 release candidate에서 첫 실행 전 airplane mode 및 Wi-Fi/cellular가 다시 활성화되지 않았는지 확인한다. 캐시/다운로드 warm-up 없이 onboarding·local data·delivery·backup·restore·reset이 동작해야 한다.
- 비행기 모드 동작은 “트래픽이 발생할 수 없다”의 단독 증거가 아니다. 최종 APK/IPA 권한·SDK·entitlement·별도 트래픽 관측은 R09와 연결한다. 외부 file provider는 local/offline 저장 대상으로 선택하고 cloud sync를 완료했다고 주장하지 않는다.

## CI와 증거 산출물

1. 실제 app smoke의 재현 entrypoint, fixture, target 검사, 실행 명령, 결과 JSON schema, 스크린샷/로그 경로 및 제한을 저장소에 둔다. 구현 전 정확한 runner API/OS 지원은 잠긴 Flutter/plugin/native toolchain과 공식 문서로 확인하며, 이 이슈는 실행되지 않은 명령을 성공 로그처럼 제시하지 않는다.
2. 기존 Flutter Testing의 generator·analyze·unit/widget·80% coverage gate를 유지한다. 모바일 빌드/job wiring은 R02, 검증 소스와 배포 연결은 R04, enforcement는 R01과 연결한다. Android emulator와 iOS simulator의 결정적인 core app smoke를 PR 목표로 둔다.
3. 각 실행 결과에는 `sourceSha`, 필요 시 `mergeSha`, build mode, version/build, artifact digest, OS/기기/대상ID, locale, schedule/device time zone, fixture/run ID, 시작·종료 시간, permission/provider, expected/actual, assertion/evidence 위치, 사용한 injection, `pass|fail|blocked|not_run`을 기록한다. 실제 설치한 artifact와 다른 artifact digest를 연결하지 않는다.
4. native UI를 지원하지 않는 자동 경로는 driver 또는 명시 기기 행을 남긴다. skipped job이나 실행하지 않은 수동 절차는 pass가 아니다. hardware/signing이 없으면 정확한 행과 사유를 남기고 OPEN을 유지한다.
5. 실패 artifact를 `always` 등 적절한 경로로 보존하고 timeout·driver 오류·앱 오류를 구별한다. 원 실패와 재실행 결과를 모두 남긴다. 비밀번호, Installation Data Key, 실제 사용자 데이터, 서명 비밀은 출력하지 않는다.
6. 기존 929 host tests, packaged-manifest CI, 이전 반복 iOS QA는 해당 SHA와 증거 수준으로 연결한다. 기존 통과 수치를 T01의 신규 E2E 통과로 합산하지 않는다. CI 성공, 실제 기기 성공, PR 병합, store 배포는 별도 상태다.

## 의존성과 실행 순서

- **선행 제품 안정성:** A01–A15 중 실제 delivery/start/run/복원·reset 경로, D01–D05의 startup/key/store/restore 안정성, U01의 삭제 계약. 현재 구현 상태를 다시 읽고 누락된 제품 결함은 원 이슈에서 해결한 뒤 동일 fixture로 재검증한다.
- **테스트 재사용:** [T03 #613](https://github.com/DevKor-github/OnTime-front/issues/613), [T04 #614](https://github.com/DevKor-github/OnTime-front/issues/614); T02는 native UI·권한/lockscreen·SQLCipher/Keychain·provider 조합을 소유한다. T01은 실제 app 성공 여정의 연결을 소유한다.
- **CI/출시 연결:** R02 native/mobile job, R04 같은 소스 품질·배포, R01 required checks, R09 최종 artifact와 offline/traffic. 미구현 CI 보호를 이미 적용됐다고 적지 않는다.
- 순서: 고정 소스/대상 manifest와 fixture → 정상 main app 자동 core → native picker/수신·탭 bridge → 실제 프로세스 재실행 → 양 플랫폼 PR job 연결 → 물리 RC offline 여정 → 원격 결과/실제 artifact read-back → 이슈 조건 평가.

- [ ] 정상 main/startup/DI/암호화 저장소를 실행하는 재현 가능한 Android·iOS core app smoke가 있으며 실제 양 플랫폼 실행 기록이 있다.
