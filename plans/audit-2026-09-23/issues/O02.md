# [O02][P1] local-only 실제 바이너리·배포 범위에 맞춰 개인정보 정책과 양 스토어 신고를 검증하고 원격 적용 증거 연결

## 문제와 목표

앱 안에서는 서버 계정과 외부 전송이 없는 local-only 제품을 설명하지만, 개인정보·Data Safety 문서는 계정 인증, FCM, 서버 API, 원격 analytics를 현행 동작처럼 설명한다. 이전에 Play Console에 저장했다는 문서는 2026-05-10 기록이며 현재 콘솔 또는 공개 페이지를 이번 조사에서 읽은 증거가 아니다. 새 RC에 Firebase가 없다는 소스 사실만으로 package 전체 신고를 ‘수집 없음’으로 바꾸면, 아직 배포 중인 이전 버전의 관행을 빠뜨릴 수 있다.

O02는 **최종 실제 제품의 데이터 흐름, 스토어 신고 적용 범위, 앱 번들·공개 개인정보 정책, 실제 저장·제출·공개 상태**를 연결한다. 확인되지 않은 법적 사실이나 기존 사용자 데이터 삭제를 선언하지 않는다. 저장소 정비가 끝나도 외부 검증·적용이 남으면 O02 전체는 OPEN이다.

## 정책·용어 경계

`CONTEXT.md`의 Local Profile, Durable OnTime Data, Local Data Reset, OnTime Backup, User-Initiated External Navigation, Product Network Boundary를 재사용한다. 새 도메인 용어·ADR은 필요하지 않다. ADR 0011/0016/0017/0018/0020/0024/0030/0033의 기존 결정을 유지한다.

- Local Profile은 로그인 계정이 아니다. Local Data Reset은 현 설치가 소유한 데이터·키·OS 등록·복구 상태를 정리하며 외부로 내보낸 백업, 기존 서버 계정, 수신된 지원 메일을 삭제하는 기능이 아니다.
- 일정·장소·메모에 사용자가 민감한 내용을 입력할 수 있으므로 ‘개인정보를 전혀 다루지 않는다’고 포괄 표현하지 않는다. 기기 안에서의 접근/저장, 스토어 정의상 collection/sharing, 외부 지원 처리를 각각 판단한다.
- 사용자 선택 backup/provider·외부 browser/mail 처리는 앱의 자동 네트워크 요청과 구별한다. 외부 전달이라고 모두 앱 수집도 아니며, OS가 처리한다고 모두 면제도 아니다. 각 경로의 수신자·실제 전달값·현재 스토어 정의를 명시한다.
- 데이터베이스·백업 암호화가 metadata 익명화, 네트워크 전송 암호화 답변, 모든 E2E 예외를 자동으로 충족하지 않는다. key/password·file metadata·header·provider가 실제 볼 수 있는 범위를 각각 확인한다.
- platform backup/transfer 제외는 ADR 0017의 best-effort 요청이다. 모든 OS/OEM 이동을 절대 차단한다는 문구 금지.
- 구 서버형 앱의 서비스·삭제 요청·보존 의무를 신제품 문서 정비만으로 종료하지 않는다. 반대로 과거 설명에 맞추기 위해 서버/auth/analytics를 새 앱에 재도입하지 않는다.
- 새 동의 팝업·추적 SDK·WebView·자동 정책 fetch·network permission을 이 이슈를 이유로 넣지 않는다.

### 스토어 적용 범위와 신고 worksheet

1. Play `club.devkor.ontime`의 app identity, 각 현재 track/버전/지역/사용자 대상/rollout 상태, 현재 배포 중인 legacy artifact를 read-only로 확인한다. internal-only 예외는 해당 사실이 확인된 행에만 적용한다. 다른 package로 착각하지 않는다.
2. Apple은 실제 app record ID·bundle ID·플랫폼·배포 버전/현재 제공 상태를 확인한다. repo iOS 폴더가 곧 공개 App Store 앱의 존재라는 뜻은 아니다. 접근/record 확인 실패는 unknown이다.
3. new local-only RC와 전체 신고 범위를 별도 표로 둔다. legacy 배포가 확인되면 old/new 버전별 설명과 global 답변의 집계를 유지하고 담당자가 실제 배포 전환을 판단한다. 이슈를 맞추기 위해 구 artifact 배포를 임의 중단하지 않는다.
4. 각 실제 console 필드에 기존 값/제안 값/근거/영향 버전/확인자/적용 상태를 기록한다. collection/sharing, purpose, required/optional, encryption in transit, deletion, account creation, Apple linked/tracking, policy URL을 실제 보이는 필드 기준으로 매핑한다. collection이 없을 때 나타나지 않는 질문에 임의 Yes/N/A를 만들어 저장하지 않는다.
5. SDK privacy manifest/required reason API 검토는 R09/R02 최종 archive 근거에 연결하고 store label과 동일 개념으로 취급하지 않는다. source dependency 또는 unsigned typecheck만으로 서명 artifact SDK 집합을 증명하지 않는다.

### 정책·번들 UI·metadata 변경

- 기존 privacy/Data Safety/계정삭제 문서의 역사 원문과 날짜·과거 승인 pending은 보존한다. 현행 정책과 과거 증거의 링크를 명확히 하고 새 운영 worksheet를 동일 진입점에서 찾게 한다. O01의 역사 표시와 충돌하지 않도록 합친다.
- 하나의 승인된 policy revision에 KO/EN 본문, 확인된 운영주체/문의 경로, 적용 제품·버전 범위, 실제 시행일을 연결한다. 소스 default 날짜·임의 미래 시행일·이전 연락처를 자동 신뢰하지 않는다.

- 문의 수단은 실제 확인된 연락처를 읽고 복사할 수 있게 한다. 외부 mail을 지원하면 기존 명시 OS 위임 경계만 사용하고 앱 데이터·로그·백업을 자동 첨부하지 않는다. 지원을 위해 이름/email 계정 필드를 앱에 추가하지 않는다.
- privacy flow와 연결되는 My Data/Recovery의 partial reset·백업 설명을 실제 receipt와 대조한다. D03/C01/A09 구현을 O02에서 대체하지 않는다.

## 증거 identity·외부 적용·보관

각 RC의 source commit, lockfiles digest, build/workflow run+attempt, Android package/version/AAB digest·설치 split 집합·signing identity, iOS bundle/version/archive/IPA digest·signing identity를 R04/R08/R09와 연결한다. store가 재서명·가공한 배포물은 원본과 byte-identical이라 하지 않고 store receipt 및 그 변환 관계를 기록한다. SDK/source/설정이 바뀌면 영향을 받는 데이터 흐름 판단을 재검토한다.

정책 bundle/public HTML revision·digest, KO/EN 번역 대조, 실제 visible text, 변경 전후 field-answer diff, 화면 캡처의 artifact identity를 연결한다. HTML 원본 byte hash와 visible policy text/version은 구별한다. CDN/locale/encoding 차이를 처리한다는 이유로 옛 본문을 동일하다고 정규화하지 않는다.

공개 게시와 콘솔 저장·제출은 정확한 payload·대상·적용 범위가 검토 가능하고 해당 쓰기 권한이 확인된 다음 실행한다. 이번 설계는 이를 실행하거나 승인하지 않았다. 이후 적용 시에는 다음을 별도로 read-back한다.

- public URL의 final redirect/status/content type·title·정책 revision/본문·hash, 무로그인 접근, 로그인/다운로드/PDF/geo 제한 여부. 하나의 네트워크에서 HTTP 200만으로 전 지역 접근 가능을 보증하지 않는다.
- Play/Apple의 실제 app identity·field 값 및 saved/draft, submitted, reviewed/accepted, 공개 label/listing 상태. 저장 성공 ≠ 제출, 제출 ≠ 승인, 승인 ≠ 모든 지역의 즉시 공개.
- 공개 앱 설명·KO/EN 스크린샷·policy 링크의 사용자 관찰 결과. CDN 지연이 있으면 실제 옛 본문이 남은 상태를 기록하고 pending으로 둔다.
- 스크린샷은 필요한 app/field/value/status만 포함한다. credentials, private console 계정 정보, 키, 실제 사용자 데이터·메일 내용은 commit/issue/artifact에 넣지 않는다.

## 수용 기준

- [ ] 고정된 최종 source/lock/Android·iOS artifact 및 실제 store 배포 범위를 구별한 inventory가 있다. unknown과 N/A의 근거가 있다.
- [ ] F01–F11의 처리주체·목적·수신자·보존/삭제·보호·사용자 선택·스토어 정의별 판단이 실제 근거와 연결된다.
- [ ] legacy server 버전/계정·삭제 경로를 확인 없이 삭제·폐기·수집 없음으로 선언하지 않았다. 기존 원문과 당시 증거가 보존된다.
- [ ] 현재 정책 revision의 KO/EN 번들·확인된 문의·시행일·운영주체가 정비되고 offline 접근/접근성 검증을 통과한다.
- [ ] 승인·유효성이 확인된 policy URL만 tap 기반 OS 외부 navigation으로 제공하며 자동 요청·WebView·민감값 전달이 없다. 실패 후 앱 상태를 보존한다.
- [ ] final RC 데이터 흐름과 Play/Apple 실제 적용 범위의 field-answer old→new 제안이 완전하다. source-only ‘수집 없음’ 판정이 없다.
- [ ] 실제 지원/hosting/연령/관할/retention 사실과 관련 승인·책임 미확인이 해소되거나 명시 pending으로 남아 있으며, pending을 두고 전체 완료하지 않는다.
- [ ] KO/EN listing·실제 RC screenshots가 계정/서버/위치/알람 기능을 오도하지 않고 identity/hash·locale 증거가 있다.
- [ ] P01–P22 검증 결과가 테스트 레벨별 기록된다. 실제 실행이 필요한 행에 fixture만 있는 상태는 pass가 아니다.
- [ ] 권한 있는 공개 적용 뒤 public URL·본문 revision·무로그인 접근 및 console saved/submitted/reviewed/public 각각 authoritative read-back을 저장했다.
- [ ] 해당 배포 범위에서 실제 공개 정책·label·metadata가 검토된 최종 데이터 흐름과 일치한다. 외부 게시/신고/검증이 남으면 repo 구현 상태만 별도 기록하고 O02는 OPEN이다.
- [ ] 법률 적합성·영구 무통신·모든 OS 데이터이동 차단을 포괄 보증하지 않았으며, 구체적 증거와 남은 한계를 기록했다.

### 질문 1 — 신고 범위·구 서버형 버전

**agent 실제 질문**

> O02 질문 1 — 신고 범위를 ‘새 local-only RC 하나’로 한정하면 안 되는 점부터 확정하고 싶습니다. 권고: R09가 식별한 최종 Android/iOS 바이너리 데이터 흐름과 별도로 Play package club.devkor.ontime의 현재 배포 대상 버전·track·지역 및 Apple app record/platform을 read-only inventory로 확인한 뒤 신고 범위를 정합니다.
