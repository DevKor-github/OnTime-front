# [P2][D06] 최초 미백업 변경부터 30일을 계산하고 Home·My Data에 닫을 수 있는 백업 안내 제공

## 문제와 결과

현재 성공한 백업 이후의 변경이 남아 있을 때 백업 안내는 `lastDurableDataAt`에서 30일을 계산한다. 사용자가 매일 일정을 수정하면 이 시각이 매일 바뀌므로, 한 달 이상 백업하지 않은 변경이 있어도 안내가 계속 뒤로 밀린다. 안내는 My Data 안의 텍스트에만 있고 닫기나 재표시 정책이 없다. ADR 0035가 약속한 dismissible, non-blocking in-app reminder를 충족하지 못한다.

이 이슈는 **성공한 export의 Backup Cutoff 이후 최초 durable commit부터 30일을 세고, 정상 Home과 My Data에서 비차단 안내 및 7일 숨김을 제공**한다. export 중 새 편집, 파일 저장 뒤 상태 기록 실패, 복원·초기화, 기존 설치의 알 수 없는 과거 시각, 앱 재시작과 기기 시계 변경까지 같은 경계에서 처리한다. 백업 파일이 외부에 계속 존재하거나 안전하게 동기화됐다고 보장하지 않는다.

우선순위 P2. 데이터 유실을 직접 일으키는 A02/A08/A09/D01/D02 및 이들의 transaction/lifecycle 계약이 선행한다. 이 문서는 전담 `/root/grill_d06`이 grill-with-docs를 사용해 root와 한 번에 한 질문씩 실제 네 문답을 완료한 **구현 계획**이다. 제품 구현·테스트 통과·기기 확인 보고가 아니다.

## 확정한 age·snapshot 계약

1. `Backup Freshness`의 Never Exported / No Changes Since Export / Unexported Changes 의미를 유지한다. 마지막 변경일과 최초 미백업 변경 시각을 혼용하지 않는다. 안내용 dirty episode는 성공한 export cutoff 이후 최초 미백업 durable commit에서 시작해 그 변경들이 성공 export에 포함될 때 끝난다. 구현 상태 식별이며 새 제품 glossary 항목은 만들지 않는다.
2. 30일은 UTC instant 기준 720시간이다. 테스트 가능하도록 clock을 주입한다. 매일 추가 변경해도 episode의 최초 시각은 밀리지 않는다. no-op, rollback, timer snapshot, 알림 registry, 조회, 화면 진입, 안내 닫기는 durable content revision/age를 바꾸지 않는다.
3. 현재 설치의 durable revision, 최초 미백업 revision/시각, 단일 export snapshot 경계 및 그 이후 첫 durable commit을 원자적으로 구별하는 **최소 유계 installation-local metadata**를 사용한다. 매 revision 전체 변경 이력을 영구 누적하지 않는다. 구체 저장 구조는 최신 schema와 gate 소유권을 확인한 뒤 구현한다.
4. 예: 1일에 A를 수정하고 35일에 revision 10 snapshot을 export하는 중 B를 수정했다면, 저장 성공 뒤 A의 오래된 age는 해소하고 B가 commit된 35일의 시각을 새 age로 남긴다. B 뒤 C를 계속 수정해도 B의 시각을 유지한다. export 중 일반 편집을 전역 busy로 막아 이 문제를 회피하지 않는다.
5. provider 성공 확인과 freshness metadata commit은 별개다. 취소/실패/metadata commit 실패는 기존 age를 해소하지 않는다. provider가 파일을 저장한 사실은 A02/C01 partial receipt로 유지하며 동일 attempt의 허용된 metadata-only retry는 provider를 다시 호출하거나 암호를 다시 요구해 재수출하지 않는다.
6. retry receipt는 원문 없는 attempt identity, store incarnation, snapshot revision/cutoff 및 당시 이후 첫 변경 경계에 묶인다. retry 전 새 변경이 생겨도 그 age를 보존한다. 이후 새 export가 성공했거나 restore/reset으로 store가 달라졌다면 옛 receipt가 최신 cutoff, first dirty, snooze를 되돌리지 못한다. superseded/obsolete 결과를 명시하고 동일 시도 재호출도 멱등적으로 처리한다.
7. 목적지 URI/경로/권한, 비밀번호, 원문은 metadata나 receipt에 보관하지 않는다. native 저장 성공 증거를 잃은 프로세스 재시작에서는 파일 저장을 성공으로 추정하지 않는다. 재시작 전 이미 영속화한 freshness 성공은 정상 DB read-back으로 유지한다.
8. 각 durable writer의 실제 transaction에서 revision/age가 함께 commit/rollback해야 한다. schedule aggregate/반복 일정/준비·템플릿/profile·설정/결과 경로를 목록화한다. 기존 구조의 revision writer를 재사용하며 별도 일반 transaction framework를 만들지 않는다. metadata만 쓰는 동작 때문에 content watch가 거짓 사용자 변경을 만들지 않게 한다.

## migration·복원·초기화

| 상태 | 정책 |
|---|---|
| 새 설치, 자동 빈 profile만 존재 | reminder 없음. 일정 row 수만으로 데이터 유무를 추정하지 않는다. |
| 사용자의 최초 durable commit | 현재 설치 commit 시각부터 30일. onboarding/설정/기본 준비/템플릿/결과 등 전체 backup 범위를 포함한다. 자동 기본값과 사용자 명시 저장의 동일 값은 기존 durable/no-op 계약을 따른다. |
| legacy 현재 revision == 기록된 성공 export revision | 기존 clean 상태 유지. migration 자체가 dirty를 만들지 않는다. |
| legacy 데이터가 있고 정확한 첫 미백업 시각 근거 없음 | age unknown으로 보존. 첫 정상 진입부터 비차단 안내 허용. ‘백업하지 않은 변경이 있습니다’와 같이 표시하고 정확한 일수 또는 ‘30일 이상’을 주장하지 않는다. lastDurableDataAt을 정확한 최초 시각으로 재명명하지 않는다. |
| 성공한 정상 복원 A09 / 손상 저장소 복원 D02 | Never Exported, 현재 설치의 복원 commit 기준으로 새 30일 시작. 외부 source cutoff/export 이력/숨김을 가져오지 않는다. 백업은 현재 설치의 성공 export 증거가 아니다. |
| 복원 취소·commit 전 실패 | 원본 freshness/age/snooze 보존. staging 검증만으로 메타데이터 변경 없음. |
| 복원 commit 후 후속 정리 실패 | 새 데이터/새 age는 보존. C01/D01 제한 상태에서는 reminder를 띄우지 않는다. 후속 정리 재시도가 새 복원/age 재설정이 아님. |
| Local Data Reset | 설치 소유 age/snooze/pending metadata도 제거. 외부 백업 삭제를 약속하지 않는다. old async receipt는 새 빈 profile을 변경하지 못함. |

신규 metadata는 portable backup format 1/2에 포함하지 않고 암호 suite도 바꾸지 않는다. D04의 versioned migration/snapshot/파일 fixture 경로로 설치 데이터를 보존하고 실패 rollback을 검증한다. A08의 병행 schema 3을 선점해 수정하지 않으며, 실제 구현 착수 시 최신 schema에서 새 migration을 결정한다. A08 store incarnation과 A09/D02의 active store/runtime 세대를 재사용해 같은 revision 숫자의 다른 저장소를 구별한다.

## 안내와 7일 숨김

- 정상 Home 목록에 inline 카드, My Data에는 freshness를 항상 표시하고 동일 reminder 카드를 공유한다. 모달·진입 차단·전역 overlay를 만들지 않는다. ‘백업하기’는 기존 My Data 화면으로 이동만 하며 password prompt/picker를 자동 실행하지 않는다.
- ‘7일 뒤 다시 알림’은 168시간 snooze다. store/dirty episode identity에 결합하고 추가 변경·앱 재시작으로 해제하지 않는다. 단순 닫기 성공을 content revision 변경이나 백업 완료로 해석하지 않는다.
- export가 모든 현재 변경을 포함하면 episode/snooze 종료. cutoff 이후 변경만 남으면 새 episode/새 30일이다. 취소/실패/metadata 실패/백업 화면을 여는 행위는 age/snooze를 자동 갱신하지 않는다. metadata-only retry도 새 episode에 오래된 숨김을 붙이지 못한다.
- Home/My Data 간 공유 상태, 정상 resume, foreground에서 30일·7일 경계 도달 시 재평가한다. 단일 bounded timer를 기존 lifecycle/clock 구조에 연결하고 dispose/background 때 정리한다. 매초 DB polling, OS reminder, background job, 서버 시각 조회, 자동 export는 없다.
- startup, onboarding, Recovery Mode, active Preparation Run 위에는 표시하지 않는다. 안내를 숨겼다는 이유로 My Data의 수동 백업/복원 기능을 제거하지 않는다. 실패 상태가 데이터 손실 또는 백업 성공처럼 보이지 않게 한다.
- snooze 저장 실패 시 같은 mounted 화면에서 임시 숨김은 허용하되 ‘7일 숨김 저장 완료’를 표시하지 않는다. 안전한 오류와 명시적 재시도를 제공하고 재실행 시 다시 나타날 수 있음을 알린다. Home의 실패로 정상 일정 사용을 막지 않는다.
- freshness 읽기 실패는 clean이나 Never Exported로 임의 치환하지 않는다. My Data의 C01 재시도·늦은 request/generation 방어를 유지하며 Home에도 raw exception 없는 안전한 상태를 제공한다. reset/restore/route 변경 뒤 old Future가 새 화면 카드/오류/숨김을 덮지 못한다.
- KO/EN, 좁은 화면, 200% 텍스트, screen reader 이름·읽기 순서·버튼 초점, route pop/revisit, 중복 탭을 검증한다. 현재 시점·최초 미백업 age·마지막 export cutoff의 표시 의미를 분리한다. 외부 파일의 현재 존재/동기화 여부는 알 수 없다.

### 기기 시계 변경

age가 음수면 0으로 clamp한다. 기기 시계가 앞으로 이동해 due가 되면 안내 기준으로만 사용하며 실제 720시간 경과를 입증한다고 주장하지 않는다. 신뢰 서버 시각은 도입하지 않는다.

snooze start/end는 같은 UTC 정밀도로 기록·비교한다. 파싱 불가, end < start, 기간 >168h, now < start이면 잘못된 숨김을 유지하지 않고 due를 재평가한다. foreground에서 이전 관측보다 UTC가 역행한 경우 기존 snooze를 조기 종료한다. 정상 foreground에서는 최초 관측의 남은 기간(최대168h)을 monotonic 타이머에도 묶는다. 단순 submillisecond 표현/정규화 차이를 역행으로 오판하지 않는다. resume/재시작은 저장 경계와 현재 UTC를 다시 읽고 단일 timer를 재설정한다.

프로세스 종료 중 start/end 내부로만 이동한 기기 시계 조작은 로컬 기록만으로 정확히 검출할 수 없다. 따라서 ‘실제 7일을 반드시 보장한다’고 하지 않는다. 이 한계를 숨기려고 계속 원격 시각을 가져오거나 백그라운드 추적을 추가하지 않는다.

## ADR 0035 보충안

최초 미백업 시각을 알 수 없는 기존 설치에서 조용히 30일을 새로 기다리는 대안과 즉시 비차단 안내하는 대안, 복원 source cutoff와 현 설치 commit 중 기준 선택, durable snooze/clock 보수성은 실제 지속 상태·사용자 경험 trade-off다. 새 ADR 번호를 늘리기보다 기존 ADR 0035에 아래 문단을 추가하고 구현과 함께 검증한다. 이 전담 agent는 D06.md만 수정하도록 위임받았으므로 공유 ADR/CONTEXT를 지금 수정하지 않았다. 기존 Backup Freshness/Cutoff 용어로 충분하며 구현 필드·timer 정책을 glossary에 넣지 않는다.

> Reminder age begins at the first committed durable change not represented by the latest successful export on this installation. A successful export clears only changes at or before its Backup Cutoff; changes committed while export is in progress retain their own earliest unexported time. Export cancellation, failure, or failure to record freshness does not clear that age. Export metadata and reminder dismissal are installation-local and are excluded from OnTime Backup. A restore starts a new Never Exported reminder period at its commit on the destination installation rather than inheriting the source cutoff or dismissal. For existing installations whose first unexported time cannot be established, OnTime may show a non-blocking reminder immediately without claiming that 30 days have elapsed. We choose this conservative notice over inventing history or postponing unknown unexported changes for another month. Normal Home and My Data share a seven-day dismissal tied to the current unexported-change episode; the freshness status and manual backup remain available. Thirty days and seven days mean 720 and 168 hours measured against the local UTC clock. Invalid dismissal intervals and observed clock reversal end suppression conservatively. Without a trusted external clock, OnTime does not promise exact real-world elapsed-time detection across process termination and clock changes. No system reminder, automatic export, external destination retention, or remote clock service is introduced.

## 완료 기준

- [ ] 최초 미백업 durable commit부터 720시간을 계산하고 매일 편집하는 negative 회귀가 해결됐다.
- [ ] export cutoff와 그 후 첫 편집을 원자적으로 구분하고 취소/실패/metadata 실패/old retry/새 export/restore 경쟁에서 age가 보존된다.
- [ ] provider 성공 partial receipt와 metadata-only retry를 C01/A02 경계에서 구현했다. provider 중복 호출·비밀번호/목적지 보관·성공 추정이 없다.
- [ ] 실제 schema migration과 file reopen 테스트로 legacy clean/unknown/empty를 구별하고 migration 실패 시 원본 보존을 확인했다.
- [ ] 정상/손상 restore와 reset에서 현 설치 commit·새 identity·old async 방어 및 metadata 제외가 검증됐다.
- [ ] Home/My Data 비차단 카드와 168시간 snooze, 수동 backup 접근, 저장/조회 실패·late UI·lifecycle 처리가 일관된다.
- [ ] timer/clock 역행·전진/invalid interval/재시작 검출 한계를 테스트·문서에 기록했고 remote clock·OS reminder·자동 backup이 없다.
- [ ] KO/EN, 좁은 화면, 200% 텍스트, 접근성 이름/초점과 Android/iOS 소유 QA 실행 증거를 구분해 남겼다.
- [ ] ADR 0035 보충을 적용하고 관련 lifecycle/backup 문서의 표현을 일치시켰다. glossary에 구현 필드를 추가하지 않았다.
- [ ] format/분석/관련 unit·widget/full suite 및 coverage·생성 산출물 정책 검사를 수행하고 실제 명령·SHA·결과를 기록했다. 실패/미실행 검사는 통과로 적지 않았다.

제품 코드와 자동 검증을 끝내도 native 실행 또는 선행 A09/D02 통합 증거가 없으면 이슈는 OPEN으로 유지하고 구현 완료/검증 대기를 분리한다. 외부 파일을 찾아 삭제하는 기능, store 배포, 운영 기기 데이터 변경은 이 완료 조건이 아니다.
