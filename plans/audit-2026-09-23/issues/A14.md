# [P1][A14] 현재 권한·선택 provider·플랫폼 예약 관측을 대조하고 확인되지 않은 예약을 정상으로 표시하지 않기

## 문제와 사용자 영향

현재 재조정은 저장된 예약의 내용·시각·provider 지원 여부가 같으면 기존 record를 그대로 유지한다. 현재 권한을 읽고 계산한 `deliveryPolicy.activeProvider`는 이 유지 판단에 사용되지 않으며, 실제 플랫폼 예약 목록도 대조하지 않는다. iOS AlarmKit 권한을 철회해 notification fallback이 필요해졌는데도 이전 AlarmKit record를 유지하거나, OS에서 예약이 사라졌는데 registry record만으로 `armed`로 계산할 수 있다. My Page도 registry에 AlarmKit record가 하나라도 있으면 현재 권한이나 취소 실패보다 먼저 알람 상태를 표시한다.

반대 방향도 문제가 된다. AlarmKit 권한을 허용해도 fallback provider가 여전히 지원된다는 이유로 이전 notification 예약을 그대로 둘 수 있다. 정상처럼 보이는 상태와 실제 선택 가능한 전달 경로가 어긋나면 사용자는 준비 시작 알림을 믿고 기다리지만 예약이 없거나 다른 방식으로 동작할 수 있다.

감사 판정은 **P1 · 논리 확인, OS 상황 재현 필요**다. 아래는 구현 전 설계·문답 기록이며 실제 OS에서 알림 유실을 재현했거나 구현을 완료했다는 증거가 아니다.

## 기존 결정과 정합성

- ADR 0008: Android는 notification 경험이며 full-screen native policy=false를 유지한다.
- ADR 0009: iOS **Alarm Status**는 현재 실제 AlarmKit 전달에만 사용한다. fallback은 **Notification Status**다.
- ADR 0010: 사용 가능한 fallback이 있으면 비차단 전달을 유지한다. 다만 이전 provider의 취소가 미확인인 경우 새 provider를 중복 등록하지 않는 경계가 있다.
- ADR 0019: 현재 로컬 데이터의 미래 대상과 플랫폼 용량으로 재조정한다. 관측만으로 Durable OnTime Data를 수정하거나 지난 일정 알림을 재발행하지 않는다.
- CONTEXT의 **Reconstructible App State**, **Schedule Notification Coverage**, **No Scheduled Notification**, **Alarm Status**, **Notification Status**로 제품 동작을 설명할 수 있다. present/absent/unknown, source, receipt는 구현 계약이므로 glossary에 넣지 않는다.
- 플랫폼별 관측과 안전한 교체는 기존 정책을 구현하는 선택이며 새로 되돌리기 어려운 제품 정책을 만들지 않는다. 새 ADR을 추가하지 않는다.

## 확정한 동작

### 현재 전달 정책과 실제 결과를 분리

각 재조정은 현재 capability·권한·알림 설정을 먼저 읽고 기존 전달 정책에서 선호 provider를 계산한다. 기존 record가 현재 provider와 다르면 단순히 지원 가능하다는 이유로 유지하지 않는다. A13이 정한 actual exact/inexact mode 변경 재등록도 함께 존중한다.

`activeProvider`는 이번 실행의 선택 정책이지 모든 예약이 그 provider에서 성공했다는 결과가 아니다. native 등록 실패 후 fallback만 성공했으면 해당 대상은 실제 fallback receipt로 기록한다. 실패, 취소 대기, 관측 불가는 성공 개수에 포함하지 않는다. 부분 성공을 하나의 provider 이름으로 덮지 않는다.

### 플랫폼별 관측 증거

관측 계약은 `present / absent / unknown`과 출처를 구분한다. 예외, unsupported, method channel 실패, parse 실패를 성공한 빈 목록으로 바꾸지 않는다. provider별 목록은 한 재조정에서 배치로 얻고 대상 ID와 대조할 수 있다. registry와 동일성 비교에는 기존 content/fingerprint/time 및 A13 actual timing 결과를 유지한다.

| 플랫폼 경로 | 증거와 동작 | 주장할 수 없는 것 |
|---|---|---|
| iOS notification | 실제 OS pending 목록의 대상 소유 ID를 대조한다. 미래 desired 대상이 absent이면 현재 데이터로 복구한다. | pending 존재가 실제 사용자 수신이나 예정 시각 도착을 보장하지 않는다. |
| iOS AlarmKit | 지원 OS/build에서 `AlarmManager.alarms`를 읽고 해당 클라이언트의 소유 ID를 대조한다. 조회 실패는 unknown이다. | 목록 누락만으로 과거 알람을 다시 울리거나 사용자 행동/일정 완료를 추정하지 않는다. |
| Android local notification | cache 관측을 OS 관측과 구분한다. 기존 시작/resume/설정·일정 변경/명시적 재조정에서 현재 미래 대상을 동일 안정 ID로 재적용하고 실제 provider 성공 receipt를 갱신한다. | cache present/absent를 OS 생존/부재 증거로 부르지 않는다. 최근 예약 요청 성공도 실제 도착 보장이 아니다. |
| 이전 Android native record | 기존 provider 및 native ID/cancel 경계를 통해 정리한다. 새 native 등록은 금지한다. | local-notification cache를 native provider 취소 증거로 재사용하지 않는다. |

새 주기적 polling, 임의 TTL, background 재등록 loop를 추가하지 않는다. 동일 Android 대상의 재적용은 안정 ID를 유지하며 불필요한 cancel→새 ID 발급을 하지 않는다. A05의 content/privacy 변경 취소 규칙이나 이미 남은 cancellationPending을 우회하는 수단으로 재적용을 사용하지 않는다.

### provider 교체 및 취소 확인

AlarmKit→fallback과 fallback→AlarmKit 모두 **이전 등록 취소 확인 후 교체**한다. 이전 경로가 살아 있을 수 있는데 다른 provider를 무조건 추가해 같은 일정이 두 번 울리는 상태를 만들지 않는다.

| 조건 | 처리 |
|---|---|
| 신뢰할 수 있는 해당 provider OS 목록에서 owned ID absent | 이미 제거된 것으로 판단해 현재 desired 대상의 교체를 진행할 수 있다. |
| Android fallback public cancel 성공 + 이후 plugin cache에서 동일 ID 부재 | `취소 요청 성공 및 캐시 제거 확인`으로 기록하고 교체를 진행한다. OS absent 증명으로 부르지 않는다. |
| Android cancel 오류 / cache 조회 오류 / 호출 뒤 cache 잔존 | 보류한다. cache absent 단독으로 cancel 오류를 덮지 않는다. |
| iOS 취소 호출 성공 + 후속 OS pending/AlarmKit 목록 absent | 교체를 진행한다. |
| iOS 취소 실패 또는 후속 목록 unknown/present | 최소 ownership tombstone을 유지하고 그 일정의 새 provider 예약을 보류한다. |
| 이전 native 취소 성공 여부를 해당 경계에서 확인할 수 없음 | 해당 provider ownership을 보존하고 확인 필요로 남긴다. 다른 provider cache로 성공 처리하지 않는다. |

취소 실패는 `cancellationPending` 등 기존 소유권 증거를 보존하고 활성 성공 수에서 제외한다. 다음 정상 재조정 또는 명시적 재시도로 복구한다. OFF·완료·삭제 대상도 취소 실패 증거를 지우지 않는다. 전체 reset/restore의 취소 프로토콜을 이번 이슈에서 완료했다고 주장하지 않는다.

### orphan과 소유권

소유권은 registry의 **provider+ID**, 엄격히 검증된 OnTime schedule payload 또는 해당 AlarmKit 소유 namespace로 확인한다. 확인된 orphan 중 현재 desired 대상이 아닌 등록은 해당 ID만 취소하고, 취소 실패 시 최소 소유권 정보를 남긴다. registry가 없는데 목록에 있다는 이유만으로 모든 알림을 삭제하지 않는다.

unrelated 알림과 준비 단계 알림에 `cancelAll`을 적용하지 않는다. 소유권이 불명확하면 임의 삭제하지 않고 관측 한계로 남긴다. 과거·완료·삭제 일정은 누락 복구 대상이 아니며 알림을 다시 울리지 않는다. 반복 일정은 현재 유효 미래 Schedule Occurrence와 최근 60개 선택을 따른다.

### 사용자에게 보이는 상태

- A13의 OFF/표시 권한/actual timing/미래 대상 없음 우선순위를 유지한다. A14는 관측 실패·취소 대기·provider 불일치·부분 실패를 그 상태 집계에 반영한다.
- registry에 record가 있다는 이유로 현재 `알람`, `정확 알림`, 정상 예약을 표시하지 않는다. 실제 현재 대상과 성공한 결과를 기준으로 집계한다.
- 대상 전체를 확인할 수 없는 상태는 `확인 필요`, 일부 실패는 `일부 예약 실패` 등 사용자 언어로 표현한다. 내부 provider, cache, receipt 용어를 그대로 노출하지 않는다.
- 사용자 OFF라도 취소 실패가 있으면 단순히 완전히 꺼졌다고 오해하지 않도록 미완료 정리를 안내한다. 권한 복구는 자동 설정 이동이나 반복 팝업이 아니라 기존 명시적 사용자 경로를 사용한다.
- 미래 대상이 없으면 **예약된 알림 없음**이다. 권한 허용이나 과거 registry record만으로 정상 예약을 만들어 표시하지 않는다.
- OS 권한 철회부터 다음 앱 실행 전 공백, 취소 미확인으로 교체를 보류하는 공백은 보장하지 않는다. iOS pending 확인과 Android 최근 요청 성공을 실제 알림 도착 증거로 표현하지 않는다.

## 수용 기준과 검증 계획

- [ ] 현재 permission과 activeProvider를 기존 record 유지/교체 판정 전에 계산한다. capability 동일·권한 변경 없음이라는 부정확한 추정으로 record를 유지하지 않는다.
- [ ] AlarmKit granted→denied + notification granted에서 기존 AlarmKit을 확인해 취소하고 fallback으로 교체한다. 반대 방향도 기존 fallback 취소 확인 뒤 AlarmKit으로 교체한다.
- [ ] 둘 다 사용 불가이면 이전 record가 정상/armed로 집계되지 않는다. 알림 OFF·완료·삭제의 취소 실패도 성공으로 집계하지 않는다.
- [ ] native 시도 실패→fallback 성공이면 실제 fallback provider receipt를 보존한다. 정책상 선호 provider를 결과로 덮지 않는다.

4. `minimalScheduleRoutePayload`는 type과 scheduleId를 검증하며 알 수 없는 추가 필드를 최소 route로 제거한다. fallback orphan 관측은 이 검증과 실제 platform ID를 함께 사용하고, registry의 provider+ID와 충돌할 때 임의 소유권을 만들어내지 않는다. 알림 제목·본문을 새 registry/log에 저장할 필요가 없다.

### 수정 허용 후 적용할 변경 순서

1. 작은 관측 모델을 domain에 추가한다. provider별 source, 조회 성공 여부, 대상별 present/absent/unknown, 최소 소유 ID를 표현한다. 최신 관측은 reconstructible 결과이며 과거 receipt만으로 다음 실행의 OS 생존을 가정하지 않는다.
2. `NotificationService`/fallback adapter에 public pending 목록 관측을 추가한다. AndroidPluginCache와 iOSNotificationCenter 출처를 명시하고 실패를 보존한다. `AlarmSchedulerService`/iOS native channel은 AlarmKit 목록을 기존 deterministic UUID와 대조한다. Android native는 새 등록을 활성화하지 않고 과거 소유 ID 취소 경계만 다룬다.
3. reconcile의 기존 A13 정책 계산 뒤 provider별 관측을 얻는다. 현재 activeProvider 불일치·내용/timing 변경·삭제·완료는 취소/교체 대상, iOS에서 유효 미래 ID 부재는 복구 대상, unknown은 확인 필요 대상으로 나눈다. Android의 현재 미래 대상은 동일 안정 ID로 재적용한다. 현재 기준시각을 지나 버린 대상을 다시 울리지 않는다.
4. provider 교체 전에 플랫폼별 취소 완료 기준을 적용한다. 실제 OS absent 또는 성공한 cancel+해당 플랫폼 후속 read-back 기준을 만족하지 못하면 tombstone과 기존 ID를 보존한다. Android fallback cache absent 단독으로 cancel 오류를 덮지 않는다. registry 쓰기와 오류 경계에서 unknown record의 소유권이 최종 replaceAll로 사라지지 않게 한다.
5. 확인된 fallback orphan을 최소 소유 정보로 정리한다. unrelated/준비 단계 알림, 매핑할 수 없는 AlarmKit UUID는 임의로 삭제하지 않는다. 새 iOS 예약도 가능한 post-schedule OS 관측을 대조하고 관측 불가를 완전 성공으로 집계하지 않는다. 미래 coverage 60개와 반복 회차 선정을 유지한다.
6. A13 순수 상태 집계에 확인 필요/부분 실패를 연결한다. OFF 상태에서 남은 취소 증거도 보이게 하고 기존 명시적 재시도 또는 정상 reconcile이 정리를 재시도할 수 있게 한다. 기술 source명은 UI에 노출하지 않는다.
7. 수정 허용 및 A13 baseline 확정 후에만 의미 있는 fake provider 모델과 method-channel/widget 회귀를 보강한다. fake 관측은 실제 fake schedule/cancel 상태를 반영해야 하며 기본값을 무조건 present로 만들어 검증을 통과시키지 않는다. provider 전환·unknown·native 오류 뒤 fallback receipt·취소 read-back·orphan ownership·반복 회차/용량·OFF 정리를 검증한다. 실제 기기 결과는 별도 pending으로 관리한다.

전체 reconcile dirty rerun/reset 직렬화는 A15/D03 영역이다. 이번 준비 메모는 해당 경쟁 문제를 해결했다고 가정하지 않는다.

### 실제로 바뀐 동작

- `DeliveryObservation`이 source, 성공한 목록 조회와 unknown, 최소 platform ID/scheduleId를 분리한다. Android public pending은 **plugin cache**로, iOS notification은 **Notification Center**로, native 목록은 **AlarmKit**으로 표현한다. 제목·본문을 관측 모델이나 추가 저장소에 복제하지 않는다.
- iOS native channel의 `getPendingNativeAlarms`는 실제 SDK의 throwing `AlarmManager.alarms`를 사용한다. 기존 scheduleId→UUID 함수로 후보 ID만 대조하며, 후보에 매핑할 수 없는 UUID 개수는 미확정 소유권으로 반환한다. 오류/unsupported/손상된 channel 응답은 빈 목록으로 바꾸지 않는다.
- 현재 permission으로 계산한 activeProvider와 기존 provider가 다르면 취소·교체한다. iOS의 기존 예약은 OS 목록에서 확인될 때 유지하고, 미래 대상의 OS 부재는 복구한다. 조회 unknown이면 소유권을 보존하고 성공 수에서 제외한다.
- Android는 기존 정상 재조정 흐름에서 같은 실제 소유 ID로 재적용한다. 과거 버전의 ID가 현재 `stableAlarmId` 계산값과 달라도, 내용·provider·timing이 같은 기존 요청을 갱신할 때 원래 ID를 보존하여 두 요청이 생기지 않게 한다. 알림 route가 registry의 소유 일정과 충돌하는 경우에는 기존 소유 ID를 취소한 뒤 올바른 route로 복구한다.
- 새 등록과 취소의 외부 부작용 전에 최소 ownership과 cancellationPending을 registry에 기록한다. native 등록 호출의 오류가 실제 OS 쓰기 뒤 발생했을 가능성도 고려해 정리를 확인한 뒤 fallback을 시도한다. 정리 실패이면 다른 provider를 추가하지 않는다. 실패 후 다음 실행이 정리할 ID를 잃지 않는다.
- fallback cancel은 public cancel 성공 후 해당 플랫폼의 pending read-back에서 ID 부재까지 확인한다. Android는 이를 **취소 요청 성공 및 캐시 제거 확인**으로만 해석한다. iOS native는 신뢰할 수 있는 기존 OS 부재 또는 cancel 뒤 OS 부재로 완료한다. 취소 오류/후속 조회 실패/잔존은 보류한다.
- 과거 Android native 취소는 args/AlarmManager 부재를 성공으로 처리하지 않는다. 기존 activity·legacy broadcast 토큰을 각각 취소하고 후속 토큰 부재를 확인한다. 이 역시 전체 OS 예약 목록 관측이라는 뜻이 아니며 새 Android native 등록은 여전히 금지된다.
- 검증된 fallback orphan은 실제 platform ID로만 정리한다. unrelated/준비 단계 알림과 소유권 미확정 AlarmKit UUID는 임의 삭제하지 않는다. OFF에도 native 조회 실패/미확정 UUID를 확인하며, ON·OFF 모두 일정/registry가 0개라는 이유로 관측 실패를 정상 빈 상태로 바꾸지 않는다.
- A13의 actual timing·상태 집계를 유지하면서 `꺼짐 · 알림 취소 확인 필요` / `Off · cancellation needs checking`를 추가했다. OFF에서도 My Page의 정상 재조정·resume가 미완료 정리를 다시 확인한다. 완료되면 정상 OFF로 돌아간다.
