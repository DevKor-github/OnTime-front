# [P1][C01] 저장·백업 복원·초기화의 workflow와 단계별 결과를 UI에서 분리

## 문제와 영향

현재 내 데이터 화면이 BackupService, LocalDataResetService, ReconcileAlarmsUseCase를 직접 조합한다. 복원 DB transaction이 성공한 뒤 알림 재등록만 실패해도 화면은 전체 작업을 실패로 표시한다. 사용자가 같은 백업 복원을 다시 실행하면 이미 성공한 데이터 교체를 반복한다. 일정 저장에서도 일정 저장과 알림 조정이 먼저 실행되고 custom preparation 저장이 뒤따라, 사용자에게 표시하는 성공/실패와 실제 저장 상태가 달라질 수 있다. 복구 화면의 reset에는 예외 처리조차 없어 실패 시 busy 상태가 남을 수 있다.

C01은 이 실제 경계들을 application/domain workflow와 typed 결과로 연결하는 구조 개선이다. 모든 Bloc이나 use case를 일괄 재작성하는 작업이 아니다. 원자적 DB 변경과 OS·파일·runtime 후속 작업을 하나의 transaction으로 포장하지 않고, 각각 무엇이 완료됐는지 호출자가 정확히 알도록 한다.

우선순위 **P1**. 조사 기준은 **`bca81bcca8fc94aaa1d2c205aae6ec4f63ca3b04`**이다. A13의 별도 WIP가 동시에 있었으나 이번 조사에서는 이를 수정하지 않았다. 아래는 합의된 구현 계획이며 테스트 통과 또는 제품 적용 보고가 아니다.

## 확정한 구조와 책임

### 구체적인 세 가지 workflow 경계

1. **일정 저장**: 기존 create/update FormSubmission을 유지하면서 A08의 schedule/place/preparation/revision aggregate transaction에 연결한다. 최종 DB commit 이후에만 A15 delivery coordinator에 요청한다. 반복 series/occurrence, frozen 회차, preparation ownership, revision 규칙을 보존한다.
2. **백업 내보내기·확정 복원**: 암호 입력, 파일 선택, 검증된 preview, 최종 확인은 사용자 상호작용이다. snapshot/export 및 restore의 DB/runtime/delivery 순서는 workflow가 담당한다. A02 파일 저장 receipt와 A09 staging/replacement/runtime 정책을 재사용한다.
3. **Local Data Reset**: 정상 화면과 Recovery Mode가 동일한 domain command/result 및 D03 cleanup engine/journal을 사용한다. 화면별 별도 삭제 조합을 만들지 않는다. DB/키를 열 수 없는 상태에서도 안전하게 reset 결과를 전달해야 하며 초기화 의도 없이 데이터를 삭제하지 않는다.

Domain은 operation별 command, 결과, 필요한 repository/backup/runtime/delivery port만 안다. Flutter `BuildContext`, dialog, router, Drift 구현, native picker/channel, key/files 구현을 domain으로 옮기지 않는다. data/core adapter가 구체 transaction·암호화·파일·OS 작업을 수행하고 workflow는 전후 순서 및 작업 소유권을 담당한다. 클래스/파일 이름은 구현 시 기존 선행 인터페이스를 보고 정하며 이슈가 불필요한 추상 계층 개수를 강제하지 않는다.

UI는 입력과 확인, 상태 표시, 안전한 결과 문구, 명시적 재시도와 navigation을 담당한다. MyDataScreen/RecoveryScreen은 concrete BackupService/ResetService/Reconcile를 직접 조합하지 않는다. 화면의 수명과 작업의 수명을 구별하며 widget이 dispose됐다고 전송된 native 요청이나 DB Future가 취소된 것으로 간주하지 않는다.

### 결과와 실패 사실

| 상태/사실 | 사용자 표시와 재시도 경계 |
|---|---|
| 사용자 취소 | 저장·복원·초기화 성공을 표시하지 않는다. 변경 전 취소면 기존 durable data를 보존한다. |
| 검증 실패 또는 stale preview | 파괴 작업 전에 멈추고 안전한 이유와 재선택/재확인 경로를 제공한다. |
| busy / unavailable | 경쟁 작업이 실제로 진행 중인지 DB가 더 이상 사용 가능하지 않은지 구별한다. 다른 작업을 중첩 실행하지 않는다. |
| DB commit 전 실패 | 데이터 변경 성공으로 표시하지 않는다. 입력을 보존하고 currentness 재검사 후 재시도를 허용한다. |
| DB commit 성공 + 후속 runtime/delivery 미완료 | 저장·복원 성공 사실을 유지한다. 알림 정리/재등록 등 실제 남은 단계만 재시도하며 durable mutation을 반복하지 않는다. |
| export 파일 저장 성공 + freshness 갱신 실패 | A02 의미를 그대로 유지한다. 파일 선택 UI handoff를 실제 저장 완료로 위조하지 않으며, metadata 실패 때문에 파일 쓰기를 자동 반복하지 않는다. |
| reset 데이터 삭제 완료 + 알림 정리 미확정 | D03 단계별 결과를 표시하고 journal을 보존한다. 완전 초기화 성공이나 새 profile 생성으로 진행하지 않는다. |
| 모든 요구 단계 완료 | 해당 작업의 실제 complete 결과만 표시하고 허용된 다음 화면으로 이동한다. |

결과 이름은 예시이며 sealed type/enum 구조는 구현 시 정한다. 적어도 commit 여부, 후속 단계와 재시도 가능성, operation identity/currentness를 잃지 않아야 한다. raw exception 문자열을 사용자 문구로 전달하지 않는다. 안전한 오류 코드와 한국어/영어 l10n으로 변환하고 OS/IO 메시지 속 경로·사용자 원문·암호를 로그나 UI에 노출하지 않는다. '복구 중'은 실제 작업 중일 때만 표시한다. 일반 freshness 조회 실패도 무한 '확인 중'에 남거나 unhandled error가 되지 않게 상태로 받는다.

### 검증된 preview와 적용 사이의 변경

- immutable validated backup candidate와 **현재 data generation + durable revision**을 묶은 메모리 전용 확인 token을 만든다. candidate는 A09/D02의 실제 staging 검증 계약을 충족한 것만 받는다.
- apply는 기존 gate/A15 replacement 경계의 exclusive claim 안에서 generation/revision을 다시 확인한다. 외부에서 확인한 뒤 나중에 들어가는 check-then-act 방식은 허용하지 않는다.
- 현재 gate는 replacement 진입 시 자체 generation을 먼저 올리므로, exclusive claim 당시의 이전 generation/revision과 교체 후 발급 세대를 구별해야 한다. 자기 작업의 증가 때문에 모든 preview를 stale로 판정하거나 이 문제를 피하려고 안전 검사를 제거하지 않는다.
- exclusive 획득 → 기존 generation/revision 검증 → 유효한 교체 작업의 세대 발급 순서 또는 동등한 claim receipt로 **한 번의 교체 시도 경계**를 만든다. A12의 pending tap 무효화 보장을 약화하지 않는다.
- 값이 바뀌었으면 DB/키/runtime의 파괴적 작업 전에 멈추고 최신 현재 상태에 맞는 대체 경고/preview를 다시 확인한다. snapshot 이후 export의 일반 편집 허용을 없애는 전체 편집 잠금으로 해결하지 않는다. revision은 기존 durable 변경 정의를 따르며 timer tick 같은 reconstructible 변경으로 부풀리지 않는다.
- 한 token의 동시 commit은 같은 pending receipt 공유를 권장한다. 구현상 busy 결과라면 typed로 명시하되 두 번 commit되면 안 된다. commit 후 token 재사용은 금지한다.
- 파일을 다시 읽어 preview와 다른 내용을 적용하지 않는다. commit 전 DB 실패의 retry는 동일 candidate를 재사용할 수 있지만 currentness를 재검사한다. commit 이후 delivery retry는 DB 교체를 다시 실행하지 않는다.
- password를 controller 밖의 장기 상태, 로그, journal, preference에 남기지 않는다. 후보/암호/확인 token의 불필요한 메모리 참조는 취소·route 종료·성공·세대 교체 시 해제한다. 이미 진행 중인 작업에 필요한 참조는 owner가 최종 결과/정리까지 소유한다. 메모리 참조 해제를 secure zeroization 보장이라고 과장하지 않는다.
- route exit, 새 알림 선택, restore/reset 세대 교체 후 늦은 완료는 새 화면에 이전 snackbar/navigation을 실행하지 않는다. 실제 부작용의 책임은 기존 coordinator/owner가 끝까지 유지한다.

### transaction과 외부 작업

DB 원자성은 A08/A09/A04/A07의 실제 data transaction에서 보장한다. OS 알림 취소·예약, 파일 picker, 암호화, 사용자 확인을 DB transaction 안에서 await하지 않는다. 기존 gate와 A15 single writer를 재사용하고 nested gate run, 두 번째 lifecycle coordinator, generic retry/workflow framework를 만들지 않는다. 후속 실패를 'DB rollback됨'으로 바꾸거나 성공한 durable command를 재실행해서 해결하지 않는다.

## 의존성·구현 순서·제외 범위

| 항목 | 소유와 C01 연결 |
|---|---|
| A02/A03 | native export/import receipt, snapshot cutoff, picker 취소, 파일 저장과 metadata 구분을 재사용한다. 기존 code verification이 새로운 staging gap을 해결한 증거는 아니다. |
| A04 | 부분 profile 수정, 점수/revision transaction을 보존한다. 전체 profile 덮어쓰기로 회귀하지 않는다. |
| A11/A12 | privacy, active-run 재확인, notification pending/owner/generation invalidation을 유지한다. old operation이 새 선택/세션을 변경하지 않는다. |
| A13/A14/A15 | 실제 delivery status/관측/미확정 결과와 단일 OS writer를 재사용한다. C01이 또 다른 알림 coordinator를 만들지 않는다. |
