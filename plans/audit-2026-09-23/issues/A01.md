# [P0][A01] Android 예약 알림 receiver와 재부팅·업데이트 복구 연결 복원

## 문제와 사용자 영향

사용자가 미래 일정의 준비 시작 알림을 예약해도, Android가 예약 시점에 호출하는 `flutter_local_notifications`의 수신 컴포넌트가 앱 manifest에 없다. Dart 예약 호출 및 앱의 예약 기록이 성공한 것과 실제 사용자에게 알림이 전달되는 것은 서로 다른 결과다. 준비 시작을 놓칠 수 있으므로 해당 기능을 제공하는 다음 배포 전에 해결할 P0 항목이다.

2026-09-23 감사 **A01**에 대응한다. 현 단계의 판정은 **소스/고정 dependency 계약으로 누락 확인, 기기 실패 재현 미실행**이다. 이 이슈 본문 작성은 구현 완료가 아니다.

## 제품 용어 및 기존 결정과의 정합성

- **Android Schedule Notification**: Android에서 사용자를 준비 시작으로 안내하는 알림 표현이다. 전체 화면 Alarm을 새로 제공하는 이슈가 아니다.
- **Preparation Start Moment**: 준비를 시작해야 할 의도된 시점이다.
- **Fallback Notification**: 정밀 전달 경로를 사용할 수 없을 때의 알림 경로다. 현재 구현의 timing 정책 변경은 A13에서 다룬다.
- **Schedule Notification Coverage**: 플랫폼 용량 안에서 전달 예약이 걸린 가까운 미래 일정 범위다. 이 이슈에서 용량 정책을 변경하지 않는다.

기존 `CONTEXT.md`의 용어를 그대로 사용하므로 신규 용어 추가가 없다. ADR 0008(알림 기반 Android 전달), 0010(fallback 유지), 0019(플랫폼 용량 및 재부팅 후 재등록)과 일치한다. manifest 계약 누락의 되돌리기 쉬운 수정이므로 별도 ADR은 만들지 않는다.

## 합의한 구현 범위

1. `android/app/src/main/AndroidManifest.xml`의 application 아래 다음 컴포넌트를 `android:exported="false"`로 선언한다.
   - `com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver`
   - `com.dexterous.flutterlocalnotifications.ScheduledNotificationBootReceiver`
2. BootReceiver intent filter에 다음 action을 정확히 연결한다.
   - `android.intent.action.BOOT_COMPLETED`
   - `android.intent.action.MY_PACKAGE_REPLACED`
   - `android.intent.action.QUICKBOOT_POWERON`
   - `com.htc.intent.action.QUICKBOOT_POWERON`
3. 기존 RECEIVE_BOOT_COMPLETED 권한을 유지한다. 전체 화면 권한이나 USE_EXACT_ALARM 권한을 추가하는 방식으로 우회하지 않는다.
4. 기존 자체 native receiver는 별도 역할이므로 무작정 교체·삭제하지 않는다.
5. source manifest 회귀 검사와 **release merged manifest 검사**를 마련한다. XML 구조를 기준으로 두 클래스, disabled/exported 속성, boot actions, 필요한 권한을 확인한다. 소스 문자열 존재만으로 검증을 끝내지 않는다.
6. 실제 release build 산출물에서 검사하고, receiver 누락·잘못된 이름·exported=true·disabled·action 누락을 넣은 음성 fixture가 검사 실패하는지 확인한다. 생성된 merged manifest는 커밋하지 않는다.
7. 기기 절차와 결과 기록 양식을 문서화하고 결과를 본 이슈/연결 PR에 첨부한다.

## 제외 범위와 의존 관계

- **A12**: 종료 상태에서 알림 탭 → 대상 일정 라우팅. A01은 전달 자체를 검증한다. 탭 라우팅이 별도로 실패하면 A12에서 추적한다.
- **A13**: 정밀 timing 권한과 inexact/exact 예약 모드 분리. 이 이슈에서 현재 모드를 변경하지 않는다.
- **A14**: 권한 변경/OS 예약 유실 이후 provider reconcile의 전체 정확성.
- **A15/D03**: concurrent reconcile 및 취소 실패 후 정리 재시도.
- **T02/R02**: 범용 네이티브 계약 테스트·PR Android build 확대. A01의 manifest 검사는 이 작업의 선행 사례로 재사용할 수 있으나 광범위한 CI 재설계가 A01 수정의 선행 조건은 아니다.
- iOS 전달, foreground service, full-screen alarm 도입, notification action 버튼 추가, plugin 버전 업그레이드는 제외한다.
- 기존 Android release Gradle은 release task에서 signing 입력을 요구한다. 검증 전용 적절한 signing 환경/CI를 준비하며 production secret 노출이나 release signing 정책 완화로 해결하지 않는다.

## 위험과 완료 판정

- XML 수정을 했다는 사실은 OS에서 해당 알림이 실제 표시됐다는 증거가 아니다.
- source manifest와 dependency manifest는 최종 병합 artifact와 다를 수 있다. release merged manifest 검사가 반드시 필요하다.
- 예약 시각과 수신 시각은 inexact 정책/OS 절전의 영향을 받는다. 지연을 관찰해 기록하고, receiver 누락과 timing 정책 문제를 분리한다.
- 재부팅/업데이트 때 플러그인 예약 복원과 앱의 별도 재조정이 중복되지 않는지 확인한다.
