# [P1][A07] 준비 시작 저장 실패 후 재시도와 동시 호출의 멱등성 보장

## 문제와 영향

준비 시작의 첫 DB 쓰기가 실패하면 singleton use case가 해당 일정 ID를 이미 성공한 것으로 기억하여 같은 앱 실행 중 재시도를 무시한다. 동시에 도착한 두 번째 호출도 첫 쓰기가 끝나기 전에 성공한 것처럼 반환한다. 이 문제는 단순 메모리 Set 정리에 그치지 않는다. 실제 repository는 매번 시작 시각을 덮어쓰고 일정과 backup freshness revision을 별도로 저장하며, Bloc과 화면은 저장 완료 이전에 시작 상태를 선점하거나 준비 화면으로 이동한다.

사용자가 준비 시작을 눌렀는데 DB에는 시작되지 않았거나, 재시도했는데 아무 일도 일어나지 않거나, 같은 준비의 시작 시각이 바뀌는 결과를 막는다. 반복 일정은 공통 series/preparation definition이 아니라 **개별 Schedule Occurrence**를 기준으로 처리한다.

우선순위 **P1**, 감사 finding 확인 유지. 이 문서는 **`b9f959db9b52806818d998fb6bb38298bc37b50e`**의 소스와 기존 문서를 read-only로 재평가한 계획이며 구현·테스트 통과 보고가 아니다. A12와 upstream 반복 일정 구현이 통합된 상태를 기준으로 한다.

## 도메인과 최종 결정

기존 [CONTEXT](https://github.com/DevKor-github/OnTime-front/blob/b9f959db9b52806818d998fb6bb38298bc37b50e/CONTEXT.md), [ADR 0029](https://github.com/DevKor-github/OnTime-front/blob/b9f959db9b52806818d998fb6bb38298bc37b50e/docs/adr/0029-derive-preparation-runs-from-action-events.md), [ADR 0022](https://github.com/DevKor-github/OnTime-front/blob/b9f959db9b52806818d998fb6bb38298bc37b50e/docs/adr/0022-use-encrypted-drift-as-the-local-data-source.md), [ADR 0013](https://github.com/DevKor-github/OnTime-front/blob/b9f959db9b52806818d998fb6bb38298bc37b50e/docs/adr/0013-replace-durable-data-on-backup-restore.md)의 용어와 경계를 유지한다. 새 용어/ADR는 추가하지 않는다.

### DB 시작 사실과 Preparation Run을 구별한다

1. durable 시작 성공은 일정의 시작 상태, **최초 `schedule.startedAt`**, `preparationFrozen`, `dataRevision`이 하나의 DB transaction으로 commit된 시점이다. 일부만 저장되면 실패이고 모두 rollback되어야 한다.
2. 동일 회차의 중복·동시·앱 재시작 후 start 호출은 최초 durable 시작 시각을 보존한다. 변경 없는 멱등 호출은 revision을 불필요하게 증가시키지 않는다. 완료된 회차/삭제된 ID를 다시 시작하지 않는다.
3. **Preparation Run 시작 시각**은 사용자의 해당 시작 action에 속한다. 동일 run/동일 시작 시도의 중복 또는 실패 재시도는 최초 확정한 run 시각을 유지한다. 재시도 시점의 `now`로 timer를 다시 시작하지 않는다.
4. A11 fingerprint 불일치 등으로 재확인한 뒤 사용자가 명시적으로 **새 run**을 시작하면 새 run identity와 새 시각을 한 번 정한다. 이때 일정의 최초 durable `startedAt`은 덮어쓰지 않는다. 기존 DB 시작 사실을 재기록했다는 이유로 revision을 다시 증가시키지 않는다.
5. Backup Restore는 active session을 가져오지 않는다. 복원된 DB `startedAt` 하나만 보고 active run을 자동 생성하거나, `requiresConfirmation`/현재 fingerprint 검사를 우회하지 않는다.
6. 자동 준비 경계와 finish에서 사용하던 유효 시각 규칙을 별도로 보존한다. 모든 시작을 무조건 현재시각으로 치환하지 않는다.

### pending, 실패, 후속 부분 실패

- 동일 data generation + occurrence의 진행 중 시작은 singleflight로 묶어 모든 caller가 같은 실제 성공/실패 결과를 기다린다. 첫 요청이 pending인데 두 번째가 조기 성공하면 안 된다. 실패 뒤 flight/pending 표식은 정리하여 새 시도가 가능해야 한다.
- 메모리 성공 Set이 DB 사실을 대체하지 않는다. 종료·삭제·generation 교체 후 오래된 성공 표식이 새 데이터의 같은 ID를 막지 않아야 한다.
- DB commit 전 실패는 현재 확인 화면을 유지하고 재시도 가능한 오류를 표시한다. 성공처럼 `/alarmScreen`으로 먼저 이동하거나 timer를 시작하지 않는다. Bloc pending/early-start guard와 버튼 상태도 복구한다.
- DB commit 뒤 marker/snapshot 저장 또는 알림 취소가 실패하면 이미 시작된 사실을 거짓 rollback하지 않는다. 같은 run으로 timer를 진행하고 실제 후속 부분 오류를 알리며 필요한 단계만 멱등 복구한다. 사용자가 다시 누른 것이 이미 commit된 run의 복구이면 새 run으로 오인하지 않는다.
- ‘복구 중’은 실제 복구 작업이 진행 중일 때만 사용한다. 무한 자동 retry는 추가하지 않는다. 명시적 재시도 또는 기존 resume/reconcile 기회에서 한 번씩 복구하고 계속 실패하면 실패 상태를 유지한다.
- snapshot 재시도는 시작 당시의 빈 actionEvents를 재저장하지 않는다. 같은 run의 **최신 projection**과 revision/currentness를 확인하여 그동안 발생한 skip/finish를 보존한다. 완료 뒤 늦게 도착한 start 후속 작업이 run을 부활시키지 않는다.
- 알림 취소의 미확정/실패는 A14/A15/D03의 ownership evidence를 유지한다. DB transaction 안에서 OS 취소/reconcile을 await하여 긴 DB lock을 만들지 않는다.

### 비동기 수명과 A12 유지

- 모든 후속 비동기 작업은 generation + owner + run identity를 검사한다. restore/reset/new prompt/new run/종료로 교체된 이전 결과는 새 UI, 새 runtime marker, 새 session을 변경하지 않는다.
- 같은 ID를 가진 새 generation은 이전 flight를 공유하지 않는다. 이미 시작된 DB/OS 부작용의 정리는 선행 A15/D03 경계에 맞춘다. Dart Future를 무시한 것을 실제 native/DB 취소로 표현하지 않는다.
- A12의 선택 회차 유지와 prompt/view owner 수명을 보존하면서 실제 버튼 → 저장 결과 → 화면 이동을 연결한다. owner를 미리 소비하여 DB 실패 뒤 확인 화면/재시도가 사라지지 않아야 한다. 저장 중 다른 알림을 선택하거나 route를 나가면 이전 성공 결과가 새 선택을 덮거나 이전 route로 다시 이동하지 않아야 한다.
- 서로 다른 반복 회차가 같은 Preparation/step ID를 공유해도 각각 독립적으로 시작한다. 한 회차의 성공/실패가 다른 회차를 차단하지 않는다.

## 구현 범위와 의존성

포함: ScheduleRepository 시작 transaction 및 멱등 반환 계약, 실제 저장된 시각/상태 전달, SchedulePreparationSessionUseCase singleflight와 단계별 결과, early marker/snapshot 후속 복구, ScheduleBloc pending/오류/currentness 처리, ScheduleStartScreen 및 알림 확인 경로의 성공 후 이동, 관련 localization, 실제 repository/Bloc/widget 회귀 검증.

구현 순서: **A13 → A14 → A15 → D03 → A06 → A07**. 선행 구현 이후 최신 인터페이스를 다시 읽고 공유 OS 직렬화/소유권/세대 경계를 재사용한다. A11 privacy/confirmation, A12 선택 일정과 owner, upstream 반복 일정의 frozen 회차 계약을 유지한다. A08의 일반 일정 저장 원자성을 모두 대신하지 않지만 준비 시작에 필요한 transaction은 A07에서 끝낸다.

제외: 서버/동기화, 준비 action 의미 재정의, 백업에 active session 추가, 새로운 영속 outbox, 전역 generic retry framework, OS 전달 성공 보장, 점수 정책 변경, 완료된 일정 재개 기능. 생성 Dart 출력은 필요한 경우 로컬 재생성하되 커밋하지 않는다.

## 수용 기준과 검증 계획

아래는 **예정된 검증**이다. 아직 실행하거나 통과하지 않았다. 호출 횟수만 확인하는 fake 테스트로 실제 DB 원자성이나 사용자 재시도 성공을 대신하지 않는다.

| 시나리오 | 기대 결과 / 증거 |
|---|---|
| 첫 일정 write 실패 → 두 번째 성공 | 최초 요청 실패가 관측되고 DB/성공 표식이 남지 않음. 같은 instance와 ID로 두 번째 요청 성공, 실제 DB started/frozen/시각/revision 확인. |
| 일정 update 성공 직후 revision write 실패 | 실제 Drift fault injection으로 transaction 전체 rollback. 시작 상태/최초 시각/revision이 모두 이전 값이며 재시도 성공. |
| 동일 ID 동시 시작 성공 | Completer로 첫 쓰기를 멈춘 동안 두 번째도 pending. 해제 후 두 caller 성공, 한 durable 전이와 최초 시각/한 revision. |
| 동일 ID 동시 시작 실패 | 두 caller 모두 동일한 실패 의미를 관측. unhandled error 없음. 새 호출은 새 시도로 성공 가능. |
| 서로 다른 ID 동시 시작 | 한 ID 실패/지연이 다른 회차의 시작을 잘못 dedupe하지 않음. |
| 성공 후 순차 중복 | 최초 startedAt/frozen 유지, revision 추가 없음, runtime 시작 시각도 같은 run이면 유지. |
| 새 repository/use case instance | 메모리 Set 없이 기존 DB 시작을 멱등 처리. 최초 durable 시각 보존. |
| 삭제/완료 회차 | 시작 거부를 typed 결과/오류로 관측; 완료 상태와 점수/결과/revision을 변경하지 않음. |
| start 대 finish/delete 경합 | 최종 DB가 완료/삭제 후 다시 started로 되돌아가지 않음. 지연된 후속 snapshot/marker도 run을 부활시키지 않음. |
| DB commit 전 explicit Start 실패 | 실제 화면에서 버튼 클릭 → DB 지연/오류 → 확인 화면 유지와 오류 → 재클릭 → 저장 성공 후 준비 화면. 단순 Bloc 이벤트 주입만으로 대체하지 않음. |
| 빠른 두 번 클릭 | pending 표시/버튼 보호와 singleflight가 함께 동작하고 중복 navigation/새 run 없음. |
| DB commit 후 early marker 실패 | 이미 시작된 사실/timer 유지, 부분 오류 표시, 같은 run 시각으로 필요한 후속 저장만 재시도. |
| DB commit 후 snapshot 실패 | durable 시작은 유지. 재시도 시각으로 timer reset 없음. 현재 actionEvents 보존. |
| DB commit 후 OS 취소 실패/unknown | 시작 자체를 미시작으로 표시하지 않음. A14/A15/D03 ownership evidence 보존, 후속 제한 재시도. |
| snapshot retry 도중 skip | 최신 skip event와 파생 진행을 보존. 처음의 빈 이벤트 배열로 덮지 않음. |
| snapshot retry 도중 finish | 완료 상태를 보존하고 오래된 run snapshot을 재생성하지 않음. |
| runtime write 실패 뒤 앱 재시작 | DB 시작 사실은 남지만 없는/무효 runtime을 DB 시각 하나로 자동 복원하지 않음. A11 확인 경계 유지. |
| fingerprint 불일치 후 명시적 새 시작 | 새 run identity/시각은 독립적이고 retry 간 고정. 일정 최초 durable startedAt은 유지. |
| Backup Restore | active session이 복원되지 않음. 같은 ID의 새 generation이 이전 Set/flight에 막히지 않음. |
| reset/restore 중 지연 완료 | 오래된 DB/OS 작업은 공유 경계에서 처리되고 이전 결과/후속 저장이 새 generation/화면/session을 변경하지 않음. |
| 저장 중 다른 알림 선택 | 이전 owner 결과가 새 선택 일정/확인 화면을 덮지 않음. A12 selected preparation/view owner 회귀 없음. |
| 저장 중 확인 route 이탈 | 늦은 성공이 이전 route로 되돌리거나 현재 화면을 강제 이동하지 않음. commit 전 실패에서 owner가 미리 소비되어 재시도가 막히지 않음. |
| 반복 회차 두 개 | 공통 준비 정의라도 occurrence별 최초 시작/실패 재시도가 독립. frozen 회차가 materialize/edit로 다시 변경되지 않음. |
