# [P1][D03] 알림 취소 실패의 소유권을 보존하고 중단된 로컬 초기화를 재개

## 문제와 사용자 영향

개별/전체 알림 취소가 플랫폼에서 실패해도 앱은 registry를 삭제한다. Local Data Reset은 취소 오류를 무시하고 `SharedPreferences.clear()`로 남은 취소 식별자까지 지운다. 다음 시작의 복구도 오류를 삼킨 뒤 reset marker를 제거하므로, 사용자에게 초기화 완료를 보여 준 뒤 과거 일정 알림이 울릴 수 있다. 데이터 삭제와 OS 전달 정리의 실제 완료 상태가 다르지만 현재 반환값과 화면이 이를 구분하지 않는다.

2026-09-23 감사 **D03 / P1**의 상세 명세다. 조사와 아래 실제 문답으로 범위를 확정했으며 구현·장애 재현·실기기 검증 완료 문서가 아니다. A05가 reconcile의 일부 취소 실패를 보존하고 A11이 원문을 축소한 현재 상태를 출발점으로 삼는다. 해당 수정을 다시 별도로 만들지 않는다.

## 도메인 및 기존 결정

- **Local Data Reset**은 모든 OnTime 설치 데이터와 delivery registration을 제거하는 명시적 파괴 작업이다. 외부로 내보낸 **OnTime Backup**은 대상이 아니다.
- CONTEXT와 ADR 0020은 중단된 reset을 다음 시작에 재개하고 정리 완료 전 새 **Local Profile** 생성을 막는다. marker 존재만으로 이 계약이 지켜지는 것은 아니다.
- **Recovery Mode**는 새 empty profile로 우회하는 경로가 아니다. 일반 저장소 오류만으로 DB/키를 지우지 않으며, 사용자가 이미 확정하고 영속 기록된 reset 의도가 있을 때만 삭제를 재개한다.
- **Durable OnTime Data**의 권위는 암호화 DB다. 아래 journal은 사용자 데이터를 복원하는 별도 DB가 아니라 OS 부작용의 최소 소유권/정리 증거다.
- **Private Notification Content** 및 A11의 원문 최소화 계약을 지킨다. tombstone을 명분으로 일정명·장소·준비명·raw payload·fingerprint를 다시 보관하지 않는다.
- Android/iOS local-only 범위, 새 Android native 등록 금지, 반복 일정 규칙, schema 2, backup v2, nearest eligible 60개 예약 용량을 유지한다.
- journal, tombstone, intent, receipt, generation은 구현 개념이다. 새 제품 용어를 만들지 않으며 CONTEXT를 구현 명세로 확장하지 않는다. ADR 0020의 기존 복구 약속을 구현하는 범위이고, 저장 매체 선택도 아직 확정하지 않았으므로 이번 문서에서 새 ADR를 만들지 않는다.

## 확정한 처리 계약

### 하나의 취소 엔진과 사실에 맞는 부분 결과

1. 개별 취소, 전체 일정 취소, reconcile, privacy cleanup, reset/bootstrap, restore의 알림 정리가 동일한 provider 취소/관측 계약을 사용한다. 별도 reset 전용 provider 로직을 복제하지 않는다.
2. A15의 작은 side-effect coordinator를 유일한 런타임 writer로 사용한다. bootstrap은 일반 writer가 시작되기 전에 같은 포맷/정리 엔진을 실행한다. 별도 전역 작업 프레임워크·이벤트 소싱·중첩 lock을 만들지 않는다.
3. provider+실제 취소 ID별 결과를 집계하여 complete / partial / unconfirmed를 구분한다. typed 결과의 구체 클래스 이름은 구현 사항이다. 한 항목 실패가 확인된 다른 항목 정리를 막거나 전체 성공으로 바뀌지 않는다.
4. 확인된 항목만 제거한다. 취소 실패/unknown은 최소 journal ownership과 기존 `cancellationPending` 표현으로 남고 정상 armed 수에서 제외된다. 실패한 같은 소유 ID/provider를 새 예약으로 덮지 않는다. provider 변경도 A14의 이전 provider 취소 확인 규칙을 유지한다.
5. 일정 삭제·완료와 OFF 선호 등 이미 성공한 DB 작업을 OS 취소 실패 때문에 롤백하거나 다시 실행하지 않는다. 재시도는 delivery 정리 단계만 재개하여 중복 점수·중복 완료·이미 삭제된 일정 재삭제 오류를 만들지 않는다.
6. startup/resume의 기존 진입점, 실제 mutation/reconcile, 명시적 재시도에서 수렴한다. 오류 자체가 무한 루프를 만들거나 새 polling/background scheduler를 추가하지 않는다.

### A14의 플랫폼별 취소 확인을 재사용

| 관측/결과 | 처리와 증거 이름 |
|---|---|
| 해당 provider의 신뢰할 수 있는 OS 목록에서 소유 ID absent | 이미 없음으로 정리할 수 있다. unrelated ID/다른 provider 목록은 근거가 아니다. |
| Android fallback public cancel 성공 + 후속 plugin cache 부재 | 취소 요청 성공 및 캐시 제거 확인. OS AlarmManager 전체 부재를 증명했다고 쓰지 않는다. |
| Android cancel 오류, cache 조회 오류, 호출 후 cache 잔존 | 미완료로 보존한다. cache absent만으로 cancel 오류를 덮지 않는다. |
| iOS notification/AlarmKit 취소 후 해당 OS 목록 absent | 확인된 정리로 진행한다. pending 부재와 실제 과거 화면/캡처 삭제는 다르다. |
| iOS 취소 실패, 조회 unknown/present, unsupported | tombstone을 유지한다. 예외·parse 실패를 성공한 빈 목록으로 바꾸지 않는다. |

조회가 없는 provider를 임의로 성공 처리하지 않는다. 관측 출처를 내부 결과에 보존하고 UI에는 확인 필요/일부 정리 실패 같은 사용자 문구를 사용한다. 이 문서의 관측 정책은 A14에서 확정한 계약의 재사용이며 D03에서 native 관측 API를 중복 설계하지 않는다.

### OS 부작용 이전의 최소 영속 소유권

1. 예약/취소를 provider에 보내기 **전에** 안정적인 취소 ID와 미확정 intent를 영속 저장하고 read-back한다. OS 예약 성공 후 registry 저장 전 프로세스 사망도 추적할 수 있어야 한다.
2. journal은 provider, 안정 취소 ID, 필요한 generation/상태/포맷 버전 및 reset 의도/단계 정도만 저장한다. 시각, 일정/준비 원문, 원본 payload, DB 사본, 설치 키를 넣지 않는다. 취소를 위해 schedule ID가 필요하면 최소 취소 식별자로만 사용한다.
3. provider 결과가 확인되고 registry에 반영됐어도 journal의 유일한 활성 ownership 증거를 없애지 않는다. 실제 취소가 확인될 때까지 남겨 reset·registry 손실·프로세스 재시작 시 복구한다.
4. journal은 설치 DB/설치 키, 일반 `preferences.clear()`, restore의 DB 교체와 독립적이어야 한다. OnTime Backup 내용에 포함하지 않고 실제 경로에 Android/iOS 플랫폼 백업 제외를 적용한다. ADR 0017의 OS/제조사 한계까지 절대 방지라고 과장하지 않는다.
5. 저장 실패 시 새 OS side effect를 시작하지 않고 이전 유효 파일/증거를 보존한다. 가능한 메모리 상태만으로 프로세스 사망까지 보장했다고 주장하지 않는다.
6. legacy registry/공개 provider 목록에서 검증 가능한 provider+취소 ID만 이관한다. malformed 개별 record의 사용 가능한 최소 ID는 살리되 raw 내용은 이관하지 않는다. 완전히 손상돼 소유권을 알 수 없으면 빈 성공으로 치환하지 않고 A14 관측을 통한 복구 및 확인 필요 상태로 남긴다.
7. 원문 제거와 소유권 손상 복구를 혼동하지 않는다. 손상된 blob 전체를 새 진단 파일·로그에 복사하지 않고, 임의의 다른 알림을 지우거나 '오류 지우기'로 초기화 완료를 위조하지 않는다.
8. 완료 항목만 compact한다. 저장 개수 상한/TTL을 이유로 미확인 ownership을 버리지 않는다. 기존 60개 신규 예약 용량 정책은 그대로다.

**구현 때 확정할 저장 세부사항:** 후보는 DB와 별도인 application support의 작은 versioned 파일을 임시 파일 쓰기→원자 교체→read-back하는 방식이다. 같은 파일시스템의 rename, 이전 유효 세대 보존, 저장 실패/부분 파일/지원하지 않는 버전/읽기 실패의 처리, Android 백업 제외 실제 경로, iOS exclude-from-backup 속성을 검토하고 테스트한 뒤 선택한다. 현재 저장 매체·파일명·flush/fsync 정책을 구현 완료로 확정하지 않는다. read-back은 write 호출 이후 읽을 수 있다는 증거이며 갑작스러운 전원 손실·저장장치 수준 durability까지 자동으로 증명하지 않는다.

### Local Data Reset의 단계와 재시작

1. 사용자 확인 뒤 A12/A15 gate에서 새 구세대 요청을 막고 quiesce한다. 아직 provider에 보내지 않은 오래된 예약은 시작하지 않는다. 이미 보낸 요청은 반환/정리 경계까지 A15가 소유한다.
2. reset 의도 및 최소 journal을 영속 저장/read-back한 뒤 파괴적 단계에 들어간다. marker/journal 저장이나 확인 실패 시 DB·키를 삭제하지 않는다.
3. provider가 실패/unknown으로 **반환한** 경우 최소 journal과 marker를 유지하면서 안전하게 quiesce된 경계에서 DB·키·원문 삭제를 진행할 수 있다. 이미 사용자가 삭제하기로 한 원문을 취소 실패 때문에 무기한 보존하지 않는다.
4. 아직 반환하지 않은 OS 호출은 UI timeout으로 취소된 것으로 보지 않는다. timeout이 직렬 경계 해제를 의미하지 않으며 A15는 늦은 반환을 계속 회수한다. 안전한 quiesce 경계까지의 단계만 진행한다. 새 profile/신세대 등록을 차단하고 제한된 대기 뒤 미완료 단계, 재시도, 앱 다시 열기를 안내한다.
5. DB 가족 파일, 설치 키, 일반 preferences, preparation/early-start/runtime, legacy token, OnTime-owned 일정/준비 단계/표시 중 알림, native pending launch의 정리 상태를 별도로 다룬다. 실패한 단계만 다음 시작에 멱등적으로 재개한다. 외부 백업 파일은 건드리지 않는다.
6. 일반 일정 OFF는 준비 단계/다른 목적 알림에 blanket cancelAll을 사용하지 않는다. **전체 Local Data Reset에서만** OnTime 앱 범위 public cancelAll을 보조 수단으로 사용할 수 있다. 다른 앱/OS 전역 알림은 대상이 아니며 cancelAll 반환만으로 다른 provider나 journal을 모두 제거하지 않는다.
7. 완료 순서는 **모든 삭제 단계 및 provider 확인 → 완료 journal 영속/read-back → reset marker 제거/read-back → 잔여 완료 journal 정리**다. 마지막 정리 실패는 다음 시작에 완료 상태를 멱등적으로 처리하며 이미 완료한 DB 삭제를 새 데이터에 다시 수행하면 안 된다.
8. marker가 없어도 journal에 명시적인 미완료 reset intent가 있으면 reset 복구를 우선한다. 반대로 정상 active ownership 또는 일반 예약의 미확정 intent만으로 reset을 추정하여 DB를 삭제하거나 새 사용 전체를 차단하지 않는다. 일반 미확정 intent는 A14/A15가 관측·취소·조정한다.
9. legacy reset marker가 있지만 새 journal은 없는 upgrade도 다룬다. 남은 registry 및 확인 가능한 OS 소유권을 먼저 복구하며 과거 preferences 삭제로 사라진 증거를 되찾았다고 추정하지 않는다. 확인 불가능한 정리는 미완료로 표시한다.
10. 일반 정리 실패, DB 삭제 실패, 키 삭제 실패, marker 제거 실패는 다른 단계다. 모든 단계가 확인되기 전 `모두 초기화됨` 또는 새 프로필 생성으로 진행하지 않는다. 완료 후 재시작이라는 기존 정책을 유지하며 닫힌 DB를 그대로 재사용하지 않는다.

### 사용자 화면과 최소 시작 복구

- 정상 reset 완료, 데이터 삭제 후 일부 알림 정리 미확인, 삭제 자체 미완료, journal 저장 전 실패를 구분한다. 실제 삭제를 확인한 뒤에만 `기기 내 데이터 삭제됨, 일부 알림 정리 확인 필요` 같은 문구를 사용한다.
- 한국어/영어에 사용자 문구와 명시적 재시도를 제공한다. raw provider 예외, 일정 내용, journal JSON을 화면/로그에 노출하지 않는다. 자동 반복 팝업은 없다.
- reset 완료 화면, My Data 경로, 기존 Recovery Mode 경로가 같은 결과를 소비한다. 오류에서 작업 중 상태를 해제하되 삭제가 진행된 뒤 일반 편집 화면으로 돌아가면 안 된다.
- `runApp` 전 bootstrap 실패/미완료를 typed recovery 상태로 UI에 전달하는 **D01의 최소 선행 경계**가 필요하다. D03에서 예외만 throw해 영구 흰 화면을 만드는 것은 수용하지 않는다. 정상 DB나 설치 키를 열지 않고도 reset 정리 상태·재시도를 제공해야 한다.
- A12의 pending launch/generation 계약으로 reset 전 탭이 옛 확인 화면을 다시 열지 못하게 한다. ID만 남은 payload도 reset 이후 실행 권한이 아니다.
- D01 전체 startup 오류 대응, D02 손상 DB 복원, U05 앱 전체 현지화를 D03 완료로 포함하지 않는다.

### restore 경계

restore는 journal을 새 DB의 일부로 교체하지 않는다. 구세대 취소 실패 ownership을 유지하고 같은 ID 재사용은 A15 직렬 경계 및 A14 취소 확인 후에만 허용한다. 복원된 DB를 읽는 재등록은 새 generation/gate 해제 이후다. DB commit/rollback과 session 초기화의 전체 계약은 A09/C01이 소유하며 D03가 별도 restore transaction을 구현하지 않는다.

## 수용 기준과 회귀 검증

합성 ID/민감 원문 sentinel을 가진 fake provider·저장소 및 임시 DB/파일만 사용한다. 현재 사용자의 실제 DB 또는 기존 시뮬레이터 앱 데이터를 삭제하여 테스트하지 않는다.

- 실제 LocalDataResetService와 DB/DI 전 LocalDataLifecycle이 같은 owner와 LocalResetProtocol을 사용한다. provider 취소가 반환하지 않으면 owner를 유지하고 10초 후 대기 안내만 표시한다. 반환한 실패는 최소 취소 기록으로 보존하고 사용자가 요청한 원문 삭제는 별도 단계로 진행한다.
