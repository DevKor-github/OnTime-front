## 문제와 사용자 영향

Schedule은 named time zone과 선택 occurrence offset을 저장하지만 생성·편집 화면에서 시간대를 고르는 동작이 없다. 기기와 다른 시간대의 약속을 정확하게 입력하기 어렵고, 달력 상세와 홈에서는 원래 시각과 기기 환산 시각을 구별할 수 없다. 서울 2026-09-25 09:00 약속이 뉴욕에서 2026-09-24 20:00에 해당해도 날짜 차이를 설명하지 못한다. 모델에 timeZoneId가 있다는 사실만으로 이 제품 요구가 구현된 것은 아니다.

U02는 [A10 #608](https://github.com/DevKor-github/OnTime-front/issues/608)의 공통 civil/instant 해석 및 최소 UI를 재사용하여 선택·취소·확인·표시·접근성의 사용자 흐름을 완성하고 검증한다. A10과 다른 resolver, 별도 시간대 정책, 두 번째 DB writer를 만들지 않는다. 같은 변경으로 두 이슈의 수용조건을 충족할 수 있으나 이슈별 증거와 미완료 조건은 따로 기록한다.

## 확정 제품 계약

### 오프라인 시간대 선택

1. 번들 tzdb에서 지원되는 IANA zone 전체를 도시명/식별자로 검색한다. 번들 KO/EN 표시 이름을 사용할 수 있으며 번역·검색·시간대 규칙을 받기 위한 서버/API/위치 조회는 도입하지 않는다. 미번역 항목은 식별자로 명확하게 찾을 수 있어야 한다.
2. 현재 기기 시간대와 현재 draft 선택을 상단에 구별한다. device 조회 실패는 실패 상태로 표시하고 UTC로 가장하지 않는다. UTC는 사용자가 직접 선택할 수 있다.
3. offset만 고르는 목록, CST 같은 중의적 약어만 있는 목록, 기기 설정 화면으로 보내는 동작으로 대체하지 않는다. 검색 결과 없음에서도 입력 수정/취소가 가능하다.
4. 기존 civil 날짜·시각을 유지하면서 선택 zone의 occurrence를 다시 해석한다. 선택은 초안에만 적용한다. picker 취소는 선택 직전 초안을 보존하고 DB·revision·OS 예약에 영향을 주지 않는다.
5. alias/canonical 처리는 A10/D05의 호환 계약을 재사용한다. 저장된 역사적 zone 원문을 목록 열기나 조회만으로 정규화하지 않는다. 미지원 저장 zone도 원문과 수정 필요 이유를 표시한다.
6. 최종 저장에서 변경 전/후 약속 instant와 기기 환산의 차이를 확인한다. 최초 생성은 이전 약속이 없으므로 선택한 civil/zone/occurrence 및 기기 환산을 확인한다. 의미가 다른 중복 확인 모달을 추가하기보다 실제 저장·반복 검토 흐름에 통합한다.

- 서로 다른 zone은 같은 offset이어도 다른 zone이라는 사실을 보조표시한다. canonical alias가 같은 zone으로 해석되는 기준은 공통 A10/D05 계약을 사용한다.
- 날짜가 다르면 반드시 양쪽 날짜를 쓴다. zone은 식별 가능한 이름/ID를 포함하며 약어만으로 표시하지 않는다.
- offset은 해당 occurrence 기준이다. 현재 device offset이나 현재 날짜의 DST offset으로 과거/미래 표시를 계산하지 않는다. 저장된 초 단위 offset을 표시가 손실시키거나 더 정밀한 값이라고 오인시키지 않는다.
- KO/EN, 기기 12/24시간, 날짜 형식, 접근성 읽기 순서를 공통 formatter/presentation 모델로 맞춘다. U05 전체 문구 개편과 혼동하지 않고 U02가 추가·변경한 모든 문자열은 ARB에 넣는다.

### 초안·비동기·오류 상태

- 최초 초안은 감지에 성공한 device zone을 기본값으로 캡처한다. 이후 기기 이동/resume은 device equivalent만 갱신하며 civil/선택 zone/offset을 자동 변경하지 않는다.
- 명시적인 zone/날짜/시각 변경은 이전 occurrence 선택, 겹침 검사, 반복 review 승인을 무효화한다. 최신 draft revision의 해석·검사만 반영하고 늦게 도착한 이전 결과는 폐기한다.
- 다시 해석한 결과가 유일하면 유일 후보를 표시할 수 있다. 이전 ambiguous offset을 새 zone/날짜에도 무조건 재사용하지 않는다.
- gap은 다음 유효 civil을 제안하되 자동 이동·저장하지 않는다. overlap은 두 발생의 offset/instant/device equivalent를 구별하고 명시 선택 전 저장을 막는다. unknown zone은 정확한 환산값을 꾸며내지 않는다.
- 반복의 occurrence/following scope, gap skip, first/second 정책, frozen/exclusion/override를 유지한다. 일반 단발 gap 차단을 반복 expansion 전체의 새로운 정책으로 덮지 않는다. 변경 범위의 실제 첫 회차/준비 시작/유한 회차를 새 review에서 확인한다.
- 과거/시작/완료는 자동 이동하지 않는다. 역사 offset 불확실 상태도 추측 확정하지 않는다. 저장 실패/취소는 입력을 보존하되 실제 commit이 성공한 뒤 오래된 draft를 다시 적용하지 않는다.
- 다른 편집/restore/reset 세대 충돌은 재검토한다. 최종 확인 전 DB·알림 mutation은 0이다. 확인 뒤 저장은 A08 원자 workflow, 알림 취소/재예약은 A15/D03 owner를 사용한다. 저장 성공과 알림 실패는 서로 다른 결과로 알리고 저장 전체를 실패한 것처럼 재삽입하지 않는다.

### Q3 — draft 수명과 DST·반복·경쟁

**Agent 질문 원문**

> U02 Q3: 편집 도중 device zone 변경·빠른 zone 전환·DST 선택·반복 범위의 상태 전이를 고정할까요? 권장: 첫 draft는 감지한 device zone을 기본값으로 캡처하되 이후 resume/device 이동은 device equivalent만 새로 계산하고 사용자의 civil/선택 zone/offset을 덮지 않습니다. zone·날짜·시각을 명시 변경하면 이전 offset/겹침검사/반복검토 승인을 무효화하고 가장 최신 draft의 해석 결과만 적용합니다(늦은 비동기 결과 폐기). gap은 다음 유효 시각 제안+명시수정 전 저장차단, overlap은 두 발생의 offset과 기기 환산 시각을 보여준 뒤 명시선택합니다. 반복은 기존 scope 선택(이번/이후 등)·first/second 정책·gap skip·frozen/exclusion/override를 유지하고, zone 변경으로 달라지는 첫 회차/준비시작/영향 회차를 새 review에서 확인하며 과거/시작/완료는 이동하지 않습니다. 저장 실패/취소는 입력 보존, 다른 편집/restore/reset 세대 충돌은 재검토하며 확인 전 DB·알림 변경은 0으로 정할까요?

**Root 답변 원문**

> Q3 답변: 권고안을 채택한다. 최초 draft 기본 zone은 성공적으로 감지한 device zone을 캡처하고, 이후 device 이동/resume은 보조표시만 갱신하며 civil/선택zone/선택offset을 조용히 덮지 않는다. 명시적인 zone/날짜/시각 변경은 이전 occurrence 선택 및 겹침·반복 review 승인을 무효화하고 최신 draft revision에 해당하는 비동기 결과만 적용한다. 단, 다시 해석해 유일 occurrence라면 자동으로 유일 후보를 표시할 수 있으나 이전 ambiguous 선택을 무조건 재활용하지 않는다. gap은 제안만 하고 명시수정 전 저장금지, overlap은 서로 다른offset/instant/device환산을 구별해 선택하게 한다. 반복 기존scope/first-second/gap skip/frozen/exclusion/override 규칙을 보존하고 선택범위의 실제 변경 영향(첫회차·준비시작·유한회차)을 새review에서 보여준다. 과거·시작·완료는 자동이동하지 않는다. 저장 실패·선택취소는 입력을 보존하되 성공한 실제commit 이후 과거draft를 재적용하지 않는다. 다른편집/restore/reset세대충돌은 재검토하며 최종확인 전 DB/알림 mutation 0이다. A08의 원자저장과 A15/D03의 취소후재예약 경계를 사용하고 UI 자체에 별도writer를 만들지 않는다. 충분하면 실제3문답·보충전체와 UI별수용기준/테스트행렬/원격Issue연결을 문서로 동결해라. 추가중요결정이있으면 하나씩 물어라.
