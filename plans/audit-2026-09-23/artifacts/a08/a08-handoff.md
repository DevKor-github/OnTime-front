## Result and design

- Production create/edit FormSubmission uses a single aggregate port. Schedule user fields, owned/copy-safe place, preparation mode/reference/owned steps, referenced former-owned definition cleanup, and exactly one durable revision commit together. A fault rolls all of them back. Custom step IDs are retained by position on edits; source template/default IDs are never adopted. Shared place renames create a new owned place instead of modifying another schedule's row.
- Fresh create drafts read default preparation and their baseline together; edit drafts read schedule, effective preparation, optional recurring segment and baseline in one transaction. Alarm planning materializes first and reads its immutable schedule/preparation snapshot in one transaction. Actual encrypted backup cutoff races produce a complete old aggregate, followed by a complete new live aggregate.
- Schema 3 adds nullable installation-local store/aggregate identities, versions and last mutation receipt metadata. Triggers assign identities before they are observable at the operation boundary and observe existing purpose-specific writers. An explicit stable rootSegmentId survives split and clock reversal. Definition/template/default/custom/place dependencies invalidate only dependent aggregate/root versions. Materializing new occurrences alone does not advance user-edit versions.
- New absent-target intents additionally fence the durable revision. An unrelated durable edit may conservatively reject a new create; the UI preserves inputs and requires explicit current-state review and a fresh intent. Existing edits use aggregate dependencies, not a global revision fence. The normalized intent digest also binds the captured baseline, preventing an old create from adopting a newly recreated row even if a caller reuses the mutation ID.
- Same current store/aggregate and durable identity+digest+version receipt can acknowledge a lost result without another commit. Plain matching contents cannot. Ordinary and following receipts survive actual file-DB close/reopen with a new memory gate; following retry works even after its original occurrence row was removed by the split. These tests are not native process-kill/device crash claims.
- Existing recurring create/occurrence/following transactions remain the write engine. Direct recurring create now raises typed conflict for an existing series. Only the aggregate receipt boundary may acknowledge a user retry. Unused RecurringSchedulesUseCase.save was removed after callsite search; read/review/delete APIs remain.
- Ordinary create explicitly constructs only user-owned fields; protected metadata injection is rejected. Existing edits issue partial user-field UPDATEs and recheck start/completion/frozen/preparation-start time. Legacy DAO create/update also strip concurrency metadata and read back post-trigger rows in the same transaction, preventing old persisted whole rows from rewinding version/receipt metadata.
- Schedule watch uses one SQL schedule/place snapshot with all dependency tables declared and preserves ascending scheduleTime. It does not create a second asyncMap read transaction. Actual subscribers do not observe rollback values, including an assertion after a committed drain barrier and before the next successful write.
- C01 integration returns durable receipt plus notification delivery status. DB success followed by reconcile failure is visibly committed; retry invokes only notification follow-up. Concurrent identical workflow saves coalesce. Generation is checked after asynchronous reconciliation. Opaque form ownership plus mutation ID and current route guard every asynchronous result/modal continuation. A partial receipt from form A cannot replace form B's real save.

## Compatibility / integration obligations

- Backup payload remains version 2; legacy versions 1 and 2 are accepted. Installation identities, root identity and receipts are excluded from portable payloads, including a strict recurring-segment key allowlist during decoding. Restore inserts obtain fresh store and aggregate identities. Existing profile upserts, partial settings/outcome updates and normal reopen preserve them.
- **A09 / D02 must issue a fresh store incarnation when replacing data, even if a future implementation preserves the profile row or user IDs/revisions.** Current backup revision is backup revision+1 and is not assumed monotonic across restore. Never substitute revision equality or memory generation=0 for store identity.
- Historical v2 fixture is an actual baseline Drift SQLite DDL dump. v1 is explicitly a reconstruction from that dump using the verified historical table diff, not a historical v1 binary execution. README includes full SHAs, method and hashes. Actual file SQLite migration checks v1/v2→3, legacy user/protected/order/recurring fields, identity preservation/reopen/upsert, atomic migration failure rollback and future-version refusal. Device SQLCipher migration remains D04's separate evidence boundary.
- New ADR 0037 records the real schema/conservative-create tradeoff. CONTEXT was not used as an implementation log.
