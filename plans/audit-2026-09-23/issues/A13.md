# [P1][A13] Android 알림 표시와 정확 시각 권한을 분리하고 실제 예약 모드에 맞게 상태를 표시

## 문제와 사용자 영향

Android Schedule Notification은 full-screen Alarm과 다른 제품 경험이다. 하지만 현재 Android full-screen native policy가 false인 것을 정확 시각 capability까지 없는 것으로 취급하여 정확 권한 조회·요청 경로를 건너뛴다. local notification은 정확 권한 유무와 관계없이 항상 `inexactAllowWhileIdle`로 예약된다. 사용자가 이미 정확 시각 권한을 허용해도 OnTime의 준비 시작 알림은 계속 근사 예약된다.

또한 provider가 `localNotification`이라는 사실만으로는 실제 예약이 exact였는지 inexact였는지 알 수 없다. 현재 registry와 UI는 이 차이를 기록하지 않는다. 단순히 scheduling mode 한 줄을 바꾸거나 권한 granted만으로 정확 상태를 표시하면 권한 변경 후 기존 예약이 그대로 남고, fallback 성공·부분 실패를 정확 예약 성공처럼 보여 줄 수 있다.

이번 범위는 Android 알림 표시 권한, 정확 시각 capability/권한, 실제 예약 모드를 분리하여 실제 결과와 안내가 일치하게 만드는 것이다. Android full-screen policy는 false를 유지하며 iOS AlarmKit/notification 제품 정책을 바꾸지 않는다.

## 기존 도메인 및 결정과의 정합성

- CONTEXT의 **Android Schedule Notification**은 알림 경험이며 full-screen **Alarm**과 다르다.
- **Exact Timing Permission**은 표시 권한과 별개이고 실제 기기 보고로 확인한다.
- 정확 시각 권한이 없지만 표시 권한이 있으면 **Approximate Notification Timing**이며 알림 OFF가 아니다.
- 유효한 미래 예약이 없을 때는 **No Scheduled Notification**이다. capability가 granted인 것만으로 예약을 만들어 보이지 않는다.
- ADR 0008의 notification 기반 Android 정책, ADR 0010의 비차단 fallback, ADR 0019의 현재 로컬 데이터 기반 재조정을 적용한다.
- 기존 용어로 설명 가능하므로 CONTEXT에 구현 필드나 API 이름을 넣지 않는다. 권한 안내 시점·mode 기록은 되돌릴 수 있는 구현/UX 선택이며 새 ADR을 만들지 않는다.

## 확정한 제품 동작

### 독립적으로 판단할 세 가지

1. **알림 표시 가능 여부:** notification permission과 사용자 알림 ON/OFF. OFF·표시 거부는 timing보다 우선한다. exact 가능만으로 활성/예약 성공이라 하지 않는다.
2. **현재 정확 시각 가능 여부:** Android timing capability와 fresh OS permission. native full-screen 지원 여부에 의존하지 않는다. 상태 안내와 수동 설정 경로에 사용한다.
3. **실제 등록 결과:** 대상별 성공한 exact/inexact mode, 실패, cancellationPending. scheduling 호출 결과가 fallback이면 fallback 실제 mode를 기록한다. 권한 granted 값을 성공 record에 그대로 복사하지 않는다.

### 예약과 권한 변경

| 조건 | 동작 |
|---|---|
| Android 표시 허용 + 정확 권한 허용 | 예약 직전 fresh 확인 후 `exactAllowWhileIdle`로 예약한다. 실제 성공 뒤 exact 결과를 남긴다. |
| Android 표시 허용 + 정확 권한 거부/확인 불가 | 알림 ON을 유지하고 근사 모드로 예약한다. 미확인을 granted로 만들지 않는다. |
| 정확 예약 호출에서 `exact_alarms_not_permitted` | 같은 대상의 inexact 예약을 한 번 시도한다. 성공 시 실제 inexact를 기록한다. |
| 그 외 scheduling 오류 | 일반 오류를 숨기거나 권한 거부로 재해석하지 않는다. 실패를 caller/reconcile로 전달한다. |
| 근사 재시도도 실패 | 예약 성공을 기록하지 않는다. 기존 취소·실패 소유권 증거를 보존한다. |
| 다음 시작/resume 때 denied→granted 또는 granted→denied | 현재 미래 대상을 새 mode로 재등록한다. registry/provider 존재만으로 건너뛰지 않는다. |
| mode 없는 legacy registry | 정확 예약 증거로 취급하지 않는다. 다음 reconcile에서 현재 권한으로 재등록한 실제 결과를 기록한다. 소유권 ID와 cancellationPending은 유지한다. |
| iOS | 기존 AlarmKit/notification 선택과 표시 정책을 보존한다. Android timing permission 경로를 호출하지 않는다. |

mode metadata는 reconstructible registration state이다. 새 필드 누락·손상으로 전체 registry를 빈 목록으로 만들거나 취소 소유권을 잃지 않는다. A05의 content identity, A11의 최소 payload·개인정보 경계를 유지한다. 실제 mode receipt가 필요하면 service return type/record 전이를 최소 범위로 바꿀 수 있다.

권한 철회→다음 실행 전에는 OS가 앱을 종료하고 기존 exact를 지울 수 있다. 이 구간을 항상 자동 fallback으로 보장하지 않는다. 다음 앱 실행/resume에서 재조정한다. plugin boot restore가 정확 권한 없음 상태에서 inexact로 자동 교체한다고 가정하지 않는다.

### 안내 및 상태

- 최초 알림 활성화 때 건너뛸 수 있는 정확 시각 안내를 한 번 제공한다. 표시 허용/ON이면 근사 예약을 먼저 유지하고 안내를 차단 조건으로 만들지 않는다.
- OS 설정은 사용자가 명시적으로 `설정하기`를 선택할 때만 연다. 시작/resume/자동 작업에서 반복 팝업이나 자동 설정 이동을 하지 않는다.
- My Page에는 정확/근사 가능 여부와 수동 설정 경로를 지속해서 제공한다. 큰 별도 온보딩 흐름을 추가하지 않는다.
- 정확 API 사용이 정시 도착 보장을 뜻하지 않음을 짧고 명확하게 설명한다. OS·절전·기기 영향 가능성을 알리고 권한 없음이 알림 OFF처럼 보이지 않게 한다.
- 주상태는 actual scheduling result가 기준이다. 유효한 미래 대상 **전체**가 actual exact 성공인 경우만 정확 상태다. mixed/전체 inexact는 일부/전체 근사를 표시한다. 부분 성공·실패·cancellationPending을 정확 성공으로 숨기지 않는다.
- 미래 대상이 0개면 `예약된 알림 없음`을 유지한다. 현재 timing permission은 보조 정보로 제공한다.
- 사용자 OFF/표시 권한 거부는 timing 상태보다 우선 표시한다. 새로운 UI가 일반 설정 저장 race를 확대하지 않도록 기존 저장 경로를 존중한다.

A14/A15를 따로 다룬다는 이유로 A13 권한 변경 후 mode 재등록과 실제 결과 전달을 빠뜨리지는 않는다. A12가 선행 구현되므로 해당 인터페이스·회귀를 새 HEAD에서 다시 읽고 순차 통합한다.

### 실제 변경

- Android 정확 시각 조회/요청은 plugin 공개 API를 이용하며 full-screen native capability와 독립적이다. 알림 표시 권한은 그대로 별도 확인한다.
- 예약 직전 권한 확인 후 exact/inexact를 선택한다. exact 예약 중 명시적 `exact_alarms_not_permitted`만 같은 등록 ID로 inexact 한 번 재시도한다. 실제 성공 mode를 service 반환값으로 전달하고 registry에 보관한다. 다른 오류·재시도 실패는 성공으로 바꾸지 않는다.
- `notificationTiming` 누락/손상은 unknown이다. Android에서는 다음 재조정 때 교체하지만 registry 전체나 소유권을 버리지 않는다. mode 변경은 기존 stale 취소 경로에 포함하며 취소 실패 기록은 `cancellationPending`으로 남는다.
- 표시 권한 거부로 keep하지 못하는 기존 기록 역시 먼저 취소 경로로 보낸다. 검토 중 발견한 “keep만 금지하고 stale 취소를 누락하면 소유권을 잃는” 위험을 보완했고, 표시 거부+취소 예외 회귀로 최종 registry를 검증했다.
- My Page는 새로운 reconcile 결과와 직후 registry를 읽어 전체 exact 성공, 근사, mixed, 부분 실패, 권한 거부, OFF, 빈 상태를 구분한다. iOS fallback의 기존 unknown mode는 Android exact 증거를 요구하지 않고 notification 정책을 유지한다. timing 가능 여부는 보조 정보다.
- 최초 알림 사용 가능 시 안전한 home 진입 또는 My Page의 명시적 활성화에서 건너뛸 수 있는 안내를 한 번 제공한다. 먼저 근사 예약을 시도하고 사용자가 설정 열기를 선택해야 OS 요청을 호출한다. 이후 resume/route 변경은 seen marker를 확인하여 반복 안내하지 않는다.
- 교육 eligibility가 진행되는 동안 route나 Local Data generation이 바뀌면 dialog를 띄우거나 seen marker를 소비하지 않는다. 실제 dialog presentation 직전에 다시 확인하고, 명시적 설정 선택 뒤에도 확인한다. 늦은 permission 응답 중 다른 route 이동 및 데이터 교체를 각각 widget test로 검증했다.
- Android full-screen false, 최소 route payload, 기존 notification content/privacy identity, 최근 60개 capacity, 반복 일정 integration 및 iOS 선택 정책을 보존했다. 새 generator annotation/DB schema는 추가하지 않았다. 추가된 ARB 문구와 추적되는 localization Dart 출력은 `flutter gen-l10n`으로 갱신했다.

실제 Android 기기에서 잠금/프로세스 종료/Doze/권한 변경/재부팅 시 예정시각과 실제 도착시각을 비교하지 않았다. OS exact 권한 철회 후 다음 앱 실행 전 공백 및 plugin boot 자동 fallback 미보장은 여전히 플랫폼 한계다. iOS 실제 기기 회귀와 release artifact/배포 적용 확인도 이 로컬 검증과 구별한다.

현 상태는 **code verified / device pending**이다. shared tracking, GitHub 본문 read-back, commit/push는 root가 담당하며 이 전담 에이전트는 수행하지 않았다.

작업 중 main에 반복 일정 PR #590(merge `2b02fb770324de291488f3c74fe503dc063e2459`)이 들어왔다. 알림 후보는 단독·반복 회차를 함께 반환하게 되었으므로 A13의 actual mode 기록/권한 변경 재등록/60개 한도와 실패 보존 회귀에 혼합 후보를 포함한다. 정확/근사 권한 정책은 동일하게 적용하며 반복 기능을 별도 구현하거나 되돌리지 않는다. 구현 전에 선행 A12와 통합된 최신 source를 다시 읽는다.

## 실제 registry 왕복 누락 후속 수정

A14 검토에서 privacy sanitizer `_safe`가 새 timing 필드를 누락해 실제 datasource 저장/재조회에서 mode가 사라짐을 발견했다. 기존734개 검증은 이 경계를 포함하지 않았다. 후속 커밋 `edfff97c4806fb2d154c324edf8965b1feb218e0`에서 현재 유효한 record의 `notificationTiming`을 보존한다.

실제 `AlarmRegistryLocalDataSourceImpl`과 SharedPreferences API를 사용하는 테스트 **10개가 통과**했다. 새6개는 exact/approximate/platformDefault × cancellationPending true/false를 저장하고 raw 저장 mode, 새 datasource 첫 조회, 두번째 sanitize 조회, 기존 content/ownership 필드 전체의 동등성을 검증한다. SharedPreferences mock 초기값 backend이며 물리 기기 disk/restart 증거가 아니다. 전담 실행은 exit0, `00:00 +10: All tests passed!`; root는 두파일 diff와 assertions를 확인했다. 상세 해시는 `a13-persistence-validation.json`이다. 이 후속 커밋의 전체원격CI와 실기기 검증은 별도로 확인한다.
