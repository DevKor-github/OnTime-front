# Select the recovery database and key as one active pair

A damaged-store Backup Restore cannot atomically replace a fixed database file and a secure-storage key in two independent systems. D02 therefore prepares and verifies a separate encrypted candidate store with its own device-bound key slot, then selects that immutable pair through a versioned, app-owned active-store manifest; a minimal recovery journal and authoritative read-back resolve interrupted activation without deleting the original pair or treating an ambiguous state as a fresh installation.

The active store epoch identifies the selected pair, while the runtime generation inside that database belongs to A09's transactional restore boundary. A normal restore changes only the database runtime generation; it does not rewrite the manifest or replace the installation key. Candidate cleanup state and its initial generation exist before activation, so the manifest selects a consistent candidate rather than coordinating a second commit.

Old material remains until the new pair has been reopened and verified after restart, then pending cleanup removes it. A committed restore is not automatically rolled back because cleanup failed. Missing or corrupt manifests with prior-manifest or in-progress evidence enter Recovery Mode instead of falling back to the legacy pair or creating an empty store. Platform flush/rename behavior and failure recovery require implementation tests; this decision does not assert power-loss durability or report D02 as implemented.

This deliberately adds bounded inactive key material and an installation-local pointer instead of overwriting the sole fixed key slot. There remains exactly one active Installation Data Key. The decision and rejected alternative were resolved in the actual D02 grill transcript in `plans/audit-2026-09-23/issues/D02.md`; file/key ownership, reset cleanup, preview currentness, and mobile acceptance remain part of that issue.


Restart read-back requires a new native application process, not another service instance, Dart isolate, or dependency graph in the committing process. A process-lifetime opaque nonce obtained through the existing platform channel distinguishes the committing process from the subsequent startup without introducing a device or user identifier. An unavailable identity keeps recovery pending. Activation therefore reports applied data with restart and cleanup still required; OnTime does not force termination or promise an OS relaunch. Only authoritative manifest/journal resolution and encrypted-store validation in the new process permit retired-pair cleanup and normal startup. Host-injected identities, child-process tests, and physical-device restart evidence remain distinct.

The pair manifest and bounded activation/inventory record have a dedicated file adapter. The manifest selects the active pair; the record owns intent, candidate/retired material and incomplete work. Delivery ownership stays in the existing alarm journal, and the existing operation coordinator, data gate and reset protocol retain their responsibilities. Reservation read-back precedes key-slot creation. At most one unconfirmed candidate is allowed, and uncertain cleanup blocks further candidate creation. Explicit reset preserves its slot inventory through file deletion until key deletion is confirmed, then removes the remaining metadata. This separation avoids coupling storage recovery metadata to notification schemas or losing key cleanup authority during reset.

Explicit recovery also distinguishes pair authority from legacy cutover evidence. Reset intent is resolved first, then pair authority. Only a legacy selection enters the fixed-store initial-creation/cutover path. For an explicitly restored active pair, a missing or invalid cutover marker can be repaired only after the current startup has actually validated its encryption, schema and runtime state, followed by allowlisted legacy cleanup and marker read-back. This does not authorize clearing current local preferences or deleting the preserved original pair. A versioned pair-use marker in device-bound secure storage is confirmed before first activation; any surviving pair-use, owned-file, journal or temporary-record evidence prevents absent metadata from being interpreted as an implicit fresh installation. Inaccessible storage remains unknown and pending, never absent.

A narrowly bounded interrupted-first-publication recovery is allowed when manifest absence is authoritative, exactly one supported confirmed intent and consistent inventory remain, a new native process has revalidated the same target pair and the original observed identity, and no conflicting staged or later activation evidence exists. An explicit recovery action may republish only that intent's identical target descriptor and epoch. It neither imports the backup again nor rewrites the target DB, regenerates a key, allocates an epoch or deletes the original. This covers a crash after the pair-use marker but before manifest publication, and a lost manifest only where the same lineage remains provable. Corrupt or unsupported metadata, I/O uncertainty, a different descriptor or a conflicting later generation remain preservation states. The operation owner persists and the outcome remains undetermined until authoritative read-back confirms selection. This is an explicit same-intent exception to read-only authority retry, not a general fallback to a guessed active store.

When activation stops at a confirmed intent and authoritative read-back still selects the original pair, read-only retry alone can leave recovery permanently pending. The user may explicitly stop that same unapplied recovery instead of broadening the publication exception to replace an existing manifest. This requires intact single-intent lineage, unchanged original file/key identity, no evidence that the target was activated or that a later generation exists, and no conflicting pending metadata. A durable cancellation-in-progress record must precede deletion of only the owned target and its exact unpublished manifest bytes. Inventory and the gate remain until file/key absence is verified; a completed-cancelled record cannot conceal unfinished cleanup. Interrupted cancellation resumes the same cleanup. The original manifest and pair remain untouched. Only confirmed cancellation permits a new preview and confirmation; it does not prove that the damaged original can enter the normal app. Unknown authority or any evidence of target activation remains preservation mode, never rollback. This trade-off was resolved in implementation Q6 after reproducing the known-original retry dead end.

Verification before the first ready stage binds the originally confirmed candidate runtime identity and requires a new native process. After ready, the manifest continues to select the file/key pair, while normal A09 in-place restore may legitimately rotate the database runtime identity. Later startup therefore validates the existing selected encrypted file, supported schema, integrity/foreign keys and current local-profile runtime invariants, rather than requiring permanent equality with the initial candidate identity. A currently pending normal restore finishes through A09 cleanup before cutover repair and app entry. Missing, empty, linked or unreadable selected files never gain creation authority from a ready record or surviving key. Only the owned reserved-candidate path may create a recovery database. This preserves the distinction between store epoch and database runtime generation while requiring current evidence before marker repair.

An explicit first-publication retry may also finish a failed pair-use marker stage, but only for a legacy-original intent still at confirmed, with no activated or later-generation evidence. After all same-intent/new-process/current-target/original-identity checks and authoritative marker absence, the same version marker is written and read back before publishing the existing target. An acknowledged exact marker value can resolve a lost write response; a missing, invalid, unsupported or unreadable receipt never authorizes publication. This exception does not recreate history for a nonlegacy original or a previously activated pair. Automatic startup remains read-only with respect to manifest publication, and the operation stays owned through unresolved Futures. This bounded Q8 retry avoids a permanent wait after the first marker write fails without expanding Q5 into a general metadata repair path.
