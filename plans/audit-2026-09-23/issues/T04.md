# [P1][T04] 실제 사용자·타이머·프로필 이벤트 경로를 검증하고 제품 계약과 어긋난 테스트 기대값·복제 알고리즘 교체

## 문제와 결과 목표

기존 테스트 중 일부는 실제 앱이 사용하지 않는 이벤트를 직접 주입하거나 상태 객체만 생성한다. 또 완료 일정의 삭제를 숨기는 현재 동작을 기대값으로 고정하고, 테스트 fake가 생산 코드의 준비 진행 복원과 prompt 판정 알고리즘을 다시 구현한다. 이런 테스트가 통과해도 사용자 진입점과 실제 workflow가 연결되어 있는지, 실패 후 데이터가 보존되는지 증명할 수 없다.

T04는 **제품 계약에서 독립적으로 도출한 기대 결과를 실제 진입점→제품 workflow→관측 가능한 상태·저장소·외부 경계까지 연결**한다. 기능 변경은 원래 제품 이슈와 함께 수행하고, 그 변경을 재현하는 회귀·잘못된 oracle 수정·테스트 이중 구현 제거를 담당한다. 기존에 유효한 상태/equality/helper 테스트와 단순 I/O fake를 무조건 없애지 않는다. 삭제한 테스트 수나 coverage 상승 자체가 목표가 아니다.

- 우선순위: **P1**, 감사 항목 T04.
- 조사 기준: **`e6c1438ebcd641386081bb5aa5569e1b7da7ee15`**. 아래 소스 근거는 이 고정 커밋의 내용이다.
- 병행 A07 작업은 preparation use case, Bloc 및 일부 테스트를 변경하고 있다. 이슈 구현 시 그 확정 API/receipt와 증거를 재사용하며, 작업 중인 파일을 고정 커밋의 구현·검증 결과로 인용하지 않는다.

## 확정한 테스트 계약

### 1. 실제 진입점과 직접 이벤트 단위 검증의 구별

- Timer 회귀는 clock을 전진시켜 제품이 생성한 periodic Timer가 실제 refresh를 발생시키도록 한다. 직접 ScheduleTick/Refresh를 add한 unit은 유효할 수 있으나 실제 scheduler 연결 증거로 세지 않는다.
- 화면 연결은 실제 tap/접근성 액션, 앱 lifecycle 전달, 실제 stream emission을 사용한다. callback을 직접 호출하거나 최종 state를 stub하는 검증은 그 제한을 기록한다.
- A06의 신선도·연속 paused·최대 한 번 시도·cold restore/resume 무재생·privacy·권한 및 generation 경계를 재사용한다. 테스트 개수 증가를 위해 동일 행렬을 복제하지 않는다.
- 성공 판정은 필요한 실제 결과로 한다. UI만 사라진 것과 DB에서 삭제된 것, plugin 요청 수락과 OS 표시, 가짜 저장소 값 변경과 durable 저장소 재열기 결과를 구별한다.

### 2. Local Profile 준비 상태의 실제 흐름

Auth라는 기존 코드 명칭은 서버 로그인 계약을 뜻하지 않는다. `Local Profile`, `Recovery Mode`, `Local Data Reset` 등 기존 용어를 그대로 사용한다. 광범위 rename은 C06에 남긴다.

1. 초기 loading에서 실제 load 성공 후 privacy migration 성공, 그다음 user stream 연결 순서를 확인한다. 어느 단계의 실패인지 독립 제어하고 뒤 단계가 잘못 시작되지 않는지 관찰한다.
2. 최초 정상 로드에서 유효한 empty/incomplete는 onboarding, ready profile은 정상 화면으로 전이한다. 이전에 ready였는데 예상치 않게 row가 없어진 경우에는 명시 reset/restore lifecycle과 구별한다. 누락을 새 설치로 오인하여 임의 profile을 만들거나 onboarding으로 덮지 않고 설명 가능한 복구 상태를 제공한다.
3. load/privacy/user stream 실패는 기존 데이터와 키를 보존한 Recovery Mode다. 정상 Schedule 구독 및 새 예약을 위한 reconciliation을 시작하지 않는다. 이는 D01/D03/A11이 소유한 필요한 privacy cleanup이나 확정된 초기화 복구 자체를 금지하는 뜻이 아니다.
4. 동일 구독 요청, 같은 ready emission 반복으로 활성 subscription·timer·초기 reconciliation이 중복 생성되지 않는다. 실제 profile 변경은 최신 UI에 반영하고, 필요한 후속 reconciliation은 기존 A15 coalescing/owner를 따른다. 모든 emission당 영구적으로 요청 1회 같은 과도한 기대를 고정하지 않는다.
5. retry는 이전 stream 구독 취소의 완료와 세대 검사를 거친 새 시도다. load/privacy/stream/zero-delay 등 await 뒤 currentness를 확인한다. close, 더 최신 emission, reset/restore generation 변경 후 이전 작업은 새 runtime에 후속 구독·예약·화면 전이를 적용하지 않는다.
6. 현재 구현에 없는 stream recovery나 currentness, 중복 구독 방어는 D01/C06의 제품 변경으로 연결하고 회귀와 함께 수정한다. 현재 결함을 테스트 기대값으로 합리화하지 않는다.

### 3. 완료 이력 삭제의 잘못된 기대값 교체

정책은 [U01 #611](https://github.com/DevKor-github/OnTime-front/issues/611)이 소유한다. 완료/지각/비정상 및 과거 미완료 이력은 명시 확인 후 단일 삭제하며, 반복 이력은 이 회차만 삭제한다. 실제 유효한 준비 중 run/early session은 종료 안내와 함께 삭제를 차단한다. 완료 이력 편집을 함께 허용하지 않는다.

- 현재 ‘완료 삭제 숨김’/‘진행 중 삭제 가능’ 기대값은 U01 제품 변경과 같은 작업에서 수정한다. 제품이 아직 미구현인 상태에서 기대값만 바꾸거나 fake에 미래 행동을 만들어 pass시키지 않는다.
- 실제 삭제 액션→확인/취소→제품 workflow→transaction 결과→목록/상세 갱신을 검증한다. 반환값이나 버튼 수만 확인하지 않는다.
- 선택 원문·전용 자원의 삭제, 공유 자원의 보존, 익명 점수 집계의 불변, 반복 규칙/다른 회차 보존 및 exclusion은 실제 저장소 read-back과 새 instance에서 확인한다.
- confirmation 후 stale/generation 충돌, commit 전 실패 보존, commit 후 OS 정리 pending, 현재 세대 명시 재시도의 동작은 U01/A15/D03/T03 기준을 사용한다. 원문 삭제와 OS 정리 완료를 하나의 성공으로 섞지 않는다.
- U01의 KO/EN·200% 글자·접근 가능한 삭제 액션 및 실제 기기 수용 기준은 별도로 남긴다. 호스트 widget 테스트로 그 전부가 완료되었다고 하지 않는다.

### 4. 복제 fake와 oracle 정리

실제 `SchedulePreparationSessionUseCase`를 사용하고 repository/clock/channel 등 I/O 경계에서만 입력, fault, 타이밍을 제어한다. read/write spy나 명시 반환 fixture는 유지할 수 있다. 도메인 시간 파생·replay·prompt 유효성·부분 결과 판정을 fake 안에 다시 쓰지 않는다. 필요하면 작고 이름이 분명한 fixture builder를 공유하되 다른 test 파일의 실행부나 알고리즘에 의존하는 제2 제품 구현을 만들지 않는다.

기대 결과는 생산 derive 함수를 다시 호출해 얻지 않는다. 다음과 같은 작은 고정 UTC 산술 표를 기준으로 한다.

| 입력/관찰 시각 | 독립 기대 |
|---|---|
| 세 단계 60/120/60초, 명시 run 시작 `t0`, `t0 + 90초` | 첫 단계 완료, 두 번째 단계 경과 30초, 세 번째 0초. |
| `t0 + 90초`에 사용자가 실제 skip action 수행 | 현재 두 번째 단계를 건너뛰어 세 번째 경과 0초로 이동. |
| 그 run의 `t0 + 105초` | 세 번째 경과 15초. 해당 skip을 시간 경과로 두 번 적용하지 않음. |
| 같은 action 목록을 저장한 뒤 새 session/use case instance로 복원 | 같은 관찰 시각에 동일한 단계/경과. run identity·marker 보존/현재성은 별도 관찰. |

고정 UTC와 명시 run 기준으로 시간대 불확실성을 분리한다. 이 표를 일반 replay oracle 엔진으로 확장하지 않는다. invalid/confirmation-required 상태는 생산 workflow가 보존해야 하는 marker를 실제로 기록하고, 새 instance가 그것을 읽어 명시 시작 전 중단된 상태를 유지하는지 검증한다. fake가 지운 marker를 테스트가 다시 넣는 보정을 제거한다. T03의 실제 저장소/암호문/프로세스 실험과 중복되는 경우 같은 artifact를 연결한다.

- [ ] fake clock/latch/명시 상태 대기와 bounded watchdog으로 경계를 제어한다. 무작위 sleep, 통과할 때까지 rerun, 광범위 pumpAndSettle로 실패를 숨기지 않는다.

- [ ] 실제 storage read-back, in-memory boundary, host plugin/channel, host process, Android/iOS 관측을 다른 evidence level로 기록한다. T03의 저장소/프로세스 증거는 재사용하고 같은 harness를 복제하지 않는다.
- [ ] tests/analyze/CI의 실행 소스 SHA, 명령, test 이름, fixture provenance, artifact hash 및 실제 결과를 남긴다. 비공개 사용자 데이터나 실사용 설치를 fixture로 사용하지 않는다.
- [ ] 원래 제품 의존성·기기 조건을 충족하지 못한 행은 명시적으로 남긴다. 단순 coverage 또는 수량 증가, stub 결과, 아직 실행하지 않은 시나리오로 완료 선언하지 않는다.
